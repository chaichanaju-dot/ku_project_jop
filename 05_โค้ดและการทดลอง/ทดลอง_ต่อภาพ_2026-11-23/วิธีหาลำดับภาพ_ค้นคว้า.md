# จะรู้ได้อย่างไรว่าภาพไหนต่อกับภาพไหน — บันทึกค้นคว้าและผลทดลอง

> เขียนโดย Claude กับมะขาม · 23 พ.ย. 2569 · ใช้ประกอบ `ต่อภาพ_แกน.py`
> **ตัวเลขทุกตัวในข้อ 2–4 ผู้จัดทำคำนวณเอง** จากภาพในโฟลเดอร์ `04_ภาพและข้อมูลสนาม/ภาพโดรน_Agisoft` (อ่านอย่างเดียว ไม่แก้ต้นฉบับ)
> ข้อความจากแหล่งภายนอกในข้อ 1 ยกมาตามต้นฉบับ มีที่อยู่กำกับ และบอกไว้ว่าข้อไหนเปิดอ่านต้นฉบับแล้ว ข้อไหนยัง

## สรุปสั้นที่สุด

- **ลำดับภาพหาจากเนื้อภาพเอง** โดยลองจับคู่ทุกคู่ ไม่ใช้ชื่อไฟล์ ไม่ต้องให้คนเรียง — วิธีเดียวกับงานต้นแบบของ Brown & Lowe (2007) และตัวต่อภาพของ OpenCV
- **GPS และเวลาที่ฝังในภาพ ไม่ได้ใช้วางภาพ แต่ใช้ตรวจ** — ตัดคู่ภาพที่หน้าตาเหมือนต่อกันได้แต่ระยะขัดกับ GPS และรายงานว่าผืนที่ได้ตรงกับ GPS แค่ไหน
- เหตุผล: ภาพชุดนี้กล้องบันทึกสถานะ GPS ว่า "Invalid" ทุกภาพ และงานจริงของเราบินใต้สะพานซึ่งสัญญาณ GPS ไม่แน่นอน จึงไม่ควรให้โปรแกรม **พึ่ง** GPS แต่ถ้า GPS ใช้ได้ก็ควร **ได้ประโยชน์** จากมัน
- ผลกับภาพจริง: ใส่ 21 ภาพแบบสลับลำดับและตั้งชื่อมั่ว ได้ผืนเดียว ลำดับถูกทั้ง 21 ภาพ (ทิศซ้าย→ขวาอาจกลับด้านจากลำดับถ่าย เพราะโปรแกรมไม่รู้ว่าต้นทางคือปลายไหน) ตรงกับ GPS คลาดเฉลี่ย 0.10 ม. ตลอดแนว 22.9 ม. ใช้เวลาคำนวณราว 6 วินาที

## 1. คนอื่นทำอย่างไร (ค้นจากเน็ต 23 พ.ย. 2569)

### 1.1 งานต้นแบบ: Brown & Lowe (2007) — ไม่ต้องเรียงภาพ

แหล่ง: M. Brown and D. Lowe, "Automatic Panoramic Image Stitching using Invariant Features", IJCV 2007 — <https://www.cs.ubc.ca/~lowe/papers/07brown.pdf> (**เปิดอ่านต้นฉบับแล้ว** ดึงข้อความจากไฟล์ PDF 16 หน้า)

| ประเด็น | ข้อความในเปเปอร์ |
|---|---|
| ไม่ขึ้นกับลำดับภาพ | "our method is insensitive to the ordering, orientation, scale and illumination of the input images ... and can recognise multiple panoramas in an unordered image dataset" (บทคัดย่อ) |
| หาคู่ที่น่าจะซ้อน | "each feature is matched to its k nearest neighbours in feature space (we use k = 4)" และ "We consider a constant number m images, that have the greatest number of feature matches to the current image, as potential image matches (we use m = 6)" (หัวข้อ 2–3) |
| เกณฑ์รับคู่ภาพ | "ni > α + βnf ... for a correct image match, where α = 8.0 and β = 0.3" (หัวข้อ 3.2) — ni = จำนวนจุดที่ลงรอยกัน, nf = จำนวนจุดในบริเวณที่ซ้อน |
| แยกเป็นหลายผืนเอง | "we can find panoramic sequences as connected sets of matching images. This allows us to recognise multiple panoramas in a set of images, and reject noise images which match to no other images" |
| ทำไมต้องปรับพร้อมกัน | "concatenation of pairwise homographies would cause accumulated errors and disregard multiple constraints between images" (หัวข้อ 4) |

### 1.2 ตัวต่อภาพของ OpenCV — ทำตามเปเปอร์ข้างบน

แหล่ง: ซอร์สโค้ด OpenCV สาขา 4.x `modules/stitching/src/matchers.cpp`, `stitcher.cpp`, `motion_estimators.cpp` — <https://github.com/opencv/opencv/tree/4.x/modules/stitching/src> (**อ่านซอร์สแล้ว**)

- ความมั่นใจของคู่ภาพ: `matches_info.confidence = matches_info.num_inliers / (8 + 0.3 * matches_info.matches.size());` พร้อมคอมเมนต์ว่า "These coeffs are from paper M. Brown and D. Lowe"
- ค่าตั้งต้นของ Stitcher: `setPanoConfidenceThresh(1)` และใช้จุดเด่นแบบ ORB (`setFeaturesFinder(ORB::create())`)
- โหมด SCANS ใช้ `AffineBestOf2NearestMatcher` (ซอร์สมีทั้ง `estimateAffine2D` และ `estimateAffinePartial2D` เลือกตามตัวเลือก `full_affine_`) + `AffineBasedEstimator` + `BundleAdjusterAffinePartial` = ตระกูลเดียวกับแบบจำลองเลื่อน-หมุน-ย่อขยายที่เราใช้
- ภาพที่ไม่อยู่ในกลุ่มใหญ่สุดถูกทิ้ง: `indices_ = detail::leaveBiggestComponent(features_, pairwise_matches_, (float)conf_thresh_);` คอมเมนต์ "Leave only images we are sure are from the same panorama"
- วางภาพจากต้นไม้ที่ถ่วงด้วยจำนวนจุดที่ลงรอย: `findMaxSpanningTree` (คอมเมนต์ใน `AffineBasedEstimator`: "uses number of inliers as weights") แล้วเริ่มจากจุดกึ่งกลางต้นไม้

**ทดสอบเองแล้ว (ผู้จัดทำคำนวณ):** ตัวต่อภาพสำเร็จรูปของ OpenCV (`cv2.Stitcher`, โหมด SCANS) รายงานว่าสำเร็จแต่ผืนที่ได้ครอบแค่บางส่วนของคาน เมื่อปรับเกณฑ์ `setPanoConfidenceThresh` กับชุดหลัก 21 ภาพ (ย่อ 1600 px) ผลเป็นดังนี้ —
เกณฑ์ตั้งต้น 1.0 → ผืนกว้าง 4,128 px · 0.7 → 14,607 px · 0.5 → 14,288 px · 0.3 → 4,099×3,633 px (ขนาดผิดปกติ น่าจะมีคู่หลอกปนเข้ามา ยังไม่ได้ตรวจเหตุ) · 0.1 → ล้มเหลว (error ใน OpenCV)
แสดงว่าภาพถูกตัดเพราะเกณฑ์ความมั่นใจจริง และเกณฑ์ที่เดียวกันก็เปราะ: ลดแล้วได้ภาพครบ ลดอีกก็พัง · (ตัวต่อภาพนี้ใช้จุดเด่น ORB ส่วนค่าความมั่นใจที่เราคำนวณใช้ SIFT จึงเทียบตัวเลขตรงๆ ไม่ได้ — ของเรา คู่จริงที่ใช้วางภาพ 21 จาก 87 คู่ในชุด 34 ภาพมีความมั่นใจต่ำกว่า 1)

หมายเหตุ: การรัน `cv2.Stitcher` ครั้งแรกในเครื่องนี้ล่มด้วย error ของ OpenCL (`CL_INVALID_COMMAND_QUEUE`) ต้องปิด OpenCL (`cv2.ocl.setUseOpenCL(False)`) ก่อนจึงรันได้ครบ — โปรแกรมของเราไม่ใช้ `cv2.Stitcher` จึงไม่โดน

### 1.3 โปรแกรมทำแผนที่จากภาพโดรน — ใช้ GPS/เวลา "คัดคู่" เพื่อให้เร็ว ไม่ได้ใช้แทนการจับคู่

| โปรแกรม | สิ่งที่เอกสารเขียน | แหล่ง (อ่านแล้ว) |
|---|---|---|
| OpenSfM | "The pairs can be restricted by GPS distance, capture time or file name order." · ตัวเลือก `matching_gps_neighbors`, `matching_time_neighbors`, `matching_order_neighbors` (ค่าตั้งต้น 0 ทั้งหมด), `matching_gps_distance: float = 150` | <https://opensfm.readthedocs.io/en/latest/using.html> · <https://raw.githubusercontent.com/mapillary/OpenSfM/main/opensfm/config.py> |
| OpenDroneMap | `--matcher-neighbors`: "Perform image matching with the nearest images based on GPS exif data. Set to 0 to match by triangulation. Default: 0" | <https://docs.opendronemap.org/arguments/matcher-neighbors/> |
| COLMAP | Exhaustive: "every image is matched against every other image" ใช้ได้ถ้าภาพ "up to several hundreds" · Sequential: "consecutively captured images are matched against each other" และ "image file names must be ordered sequentially" · Spatial: "matches every image against its spatial nearest neighbors ... extracts GPS information from EXIF" · Vocabulary tree: "recommended matching mode for large image collections (several thousands)" | <https://colmap.github.io/tutorial.html> |
| Agisoft Metashape | Generic preselection: "the overlapping pairs of photos are selected by matching photos using lower accuracy setting first" · Reference (Source): "selected based on the measured camera locations (if present)" · Sequential: "determined according to the sequence of photos" | คู่มือ Metashape Pro 2.1 หน้า 39 — <https://www.agisoft.com/pdf/metashape-pro_2_1_en.pdf> |

สิ่งที่ตรงกันทุกเจ้า: **GPS / เวลา / ลำดับชื่อไฟล์ เป็นตัวช่วยลดจำนวนคู่ที่ต้องลอง** ตัวตัดสินว่าต่อกันจริงไหมยังเป็นการจับคู่จุดบนภาพ · COLMAP บอกว่าถ้าภาพไม่เกินหลายร้อยให้ลองทุกคู่ได้เลย ซึ่งตรงกับขนาดงานเรา (หนึ่งชิ้นส่วนราว 20–40 ภาพ)

### 1.4 ความหมายของสถานะ GPS ในไฟล์

- EXIF `GPSStatus`: `'A' = Measurement Active`, `'V' = Measurement Void` — <https://exiftool.org/TagNames/GPS.html> (**อ่านแล้ว**)
- รายการ XMP ของ DJI ที่ ExifTool รู้จัก (เช่น `AbsoluteAltitude`, `RelativeAltitude`, `GimbalYawDegree`, `FlightYawDegree`, `GPSLatitude`, `RtkFlag`) **ไม่มี** ฟิลด์ `GpsStatus` และไม่มีฟิลด์ระยะจากเลเซอร์วัดระยะ — <https://exiftool.org/TagNames/DJI.html> (**อ่านแล้ว**)
- **ยังหาเอกสารของ DJI ที่อธิบายค่า `drone-dji:GpsStatus="Invalid"` ไม่เจอ** จึงยังบอกไม่ได้ว่าพิกัดในภาพมาจากอะไรเมื่อสถานะเป็น Invalid (ข้อ 2.2 วัดได้ว่าพิกัดขยับตามการเคลื่อนที่จริงอย่างสม่ำเสมอ แต่นั่นคือผลวัดของเรา ไม่ใช่คำอธิบายจากผู้ผลิต)

### 1.5 ที่เจอจากการค้นแต่ยังไม่ได้เปิดอ่านต้นฉบับ (ห้ามอ้างจนกว่าจะอ่าน)

- งานตรวจสะพานด้วยโดรนในที่ไม่มีสัญญาณ GNSS (ใต้พื้นสะพาน) และปัญหาภาพเรียงตัวผิดในบริเวณใต้สะพาน — <https://isprs-archives.copernicus.org/articles/XLVIII-G-2025/189/2025/isprs-archives-XLVIII-G-2025-189-2025.pdf> · <https://www.mdpi.com/2504-446X/9/10/678>
- ลวดลายโครงสร้างที่ซ้ำกันทำให้ระบุตำแหน่งสับสน (perceptual aliasing) ในคานกล่องเหล็ก — <https://isprs-archives.copernicus.org/articles/XLVIII-2-W11-2025/25/2025/isprs-archives-XLVIII-2-W11-2025-25-2025.pdf>

## 2. ในภาพของเรามีข้อมูลอะไรฝังอยู่

อ่านจาก EXIF และ XMP ของทั้ง 34 ภาพ (21 ภาพในโฟลเดอร์หลัก + 13 ภาพใน `Not use`)

### 2.1 ข้อเท็จจริงของภาพชุดนี้

- กล้อง: **DJI Mini 3 Pro** (`FC3582`) ภาพ 8064×6048 ทางยาวโฟกัส 6.72 มม. (เทียบเท่า 24 มม.)
- ถ่ายวันที่ **23 มี.ค. 2023** สองช่วง: 11:34–11:43 (13 ภาพ = `Not use`) และ 12:00–12:08 (21 ภาพ = ชุดหลัก)
- พิกัดในภาพ: ละติจูด 15.687° เหนือ ลองจิจูด 100.124° ตะวันออก
- ข้อมูลในไฟล์ไม่ตรงกับการสำรวจวันที่ 13 ต.ค. 2569 ที่ฉะเชิงเทรา (คนละวัน คนละกล้อง คนละพิกัด) **แต่เวลาและพิกัดในไฟล์อาจไม่น่าเชื่อ** เพราะกล้องบันทึกสถานะ GPS ว่า Invalid จึงสรุปที่มาของภาพจากข้อมูลในไฟล์อย่างเดียวไม่ได้
- ที่มาตามบันทึกของโครงงาน: ไดอารี่ 23 ต.ค. มีรายการ `rawdata/agisoft/` ซึ่งน่าจะเป็นโฟลเดอร์นี้ก่อนจัดโครงสร้างใหม่วันที่ 30 ต.ค. (ข้อสันนิษฐาน) · ไดอารี่ 31 ต.ค. บันทึกว่าสไลด์ซ้อมหน้า 12 ใช้ภาพ `DJI_0337.JPG` จากโฟลเดอร์นี้อยู่แล้ว (ลองใช้ `DJI_0322.JPG` ก่อนแต่รอยร้าวจาง)
- ไม่ใช่เรื่องที่ต้องรอใครยืนยันก่อนทำงานต่อ (ฉบับร่างแรกของข้อนี้เคยเขียนให้ถามอาจารย์/รุ่นพี่ก่อน — ถอนแล้ว เพราะทีมใช้ภาพชุดนี้ในสไลด์อยู่แล้ว) · ถ้าจะส่งเอกสารที่มีเนื้อภาพออกนอกทีม ให้ตัดสินใจตามกฎข้อ 2 ใน `CLAUDE.md` ของโครงงาน

## 3. ผลทดลองที่ใช้ตัดสินการออกแบบ

ทำบนภาพที่ย่อเหลือกว้าง 1600 px ทั้ง 34 ภาพ = 561 คู่

> **ที่มาของตัวเลขในข้อ 3 (เพิ่มเมื่อ 23 พ.ย. ค่ำ):** ข้อ 3 ได้จากสำเนาย่อ 1600 px ที่บีบอัด JPEG ซ้ำ (คุณภาพ 92) ด้วยสคริปต์ `e1_allpairs.py` · `e4_meta.py` · `e6.py` ส่วนข้อ 4 และตัวเลขใน PDF ได้จากไฟล์ต้นฉบับ (`final_numbers.py` · `final_numbers2.py`) จึงต่างกันเล็กน้อย เช่น คู่หลอก 0312–0313 ได้ 33 จุด ความมั่นใจ 0.73 บนสำเนา แต่ 32 จุด 0.71 บนต้นฉบับ — ทั้งสองชุดถูกต้องตามอินพุตของตัวเอง ถ้าจะอ้างในเล่มให้ใช้ชุดบนต้นฉบับ · แผนที่ตัวเลข→สคริปต์ทั้งหมดอยู่ที่ `ที่มาของตัวเลข/README.md`

1. **ลองทุกคู่ไหวไหม** — จับคู่เต็ม (จุดเด่น ~3,500 จุดต่อภาพ) ใช้ 51 มิลลิวินาทีต่อคู่ = 29 วินาที แต่ถ้าใช้เฉพาะจุดเด่นที่แรงที่สุด 1,600 จุดต่อภาพ ใช้ 2 มิลลิวินาทีต่อคู่ = 1.2 วินาที และยังเจอคู่ที่ต่อได้ครบ 100% → ทำสองขั้น: ลองทุกคู่แบบเร็ว แล้วตรวจละเอียดเฉพาะคู่ที่น่าจะซ้อน
2. **มีคู่หลอกไหม** — มี ภาพ `Not use/DJI_0311–0312` และ `0312–0313` จับคู่กันได้ 58 และ 33 จุด (บนสำเนาย่อ · บนต้นฉบับ 58 และ 32 จุด) ด้วยการเลื่อนที่ดูสมเหตุสมผล (ย่อขยาย 0.97 และ 1.03) แต่ผิด: ภาพบอกว่าเลื่อน 0.37 ม. ขณะที่ GPS บอก 2.2 และ 2.5 ม. และเมื่อลองวางรวมกับภาพอื่น (การทดลองแรก ก่อนมีตัวตรวจ) คู่ทั้งสองขัดกับตำแหน่งที่ภาพอื่นกำหนดถึง 1,170 และ 1,298 px ที่ภาพกว้าง 1600 px · น่าจะเกิดจากลายบนผิวที่ซ้ำเป็นช่วงๆ (ยังไม่ได้ยืนยันด้วยตาว่าเป็นลายอะไร)
3. **แยกคู่หลอกจากเนื้อภาพได้ไหม** — ลองแล้วไม่ได้: ค่าความมั่นใจแบบ Brown–Lowe ของคู่หลอกคือ 0.77 และ 0.73 (บนสำเนาย่อ · บนต้นฉบับ 0.77 และ 0.71) ขณะที่คู่จริงที่ผ่านเกณฑ์ 30 จุดต่ำได้ถึง 0.64 บนสำเนา (0.57 บนต้นฉบับ) จึงตั้งเส้นแบ่งไม่ได้โดยไม่ทิ้งคู่จริงไปด้วย (ฉบับร่างเคยเขียนว่า "คู่จริงต่ำได้ถึง 0.21" — ตัวเลขนั้นเป็นคู่จริงที่ซ้อนกันแค่ 14% ได้ 5 จุดลงรอย ซึ่งไม่ผ่านเกณฑ์ 30 จุดอยู่แล้ว จึงไม่ใช่ตัวเทียบที่ยุติธรรม แก้เมื่อ 23 พ.ย. ค่ำ) · เทียบความคล้ายของเนื้อภาพในส่วนซ้อน (NCC) คู่หลอกได้ 0.25 (0.249 และ 0.256) ขณะที่คู่จริง 86 คู่มีตั้งแต่ −0.04 ถึงมัธยฐาน 0.36
4. **GPS แยกได้ไหม** — ได้ ในคู่ที่อยู่รอบบินเดียวกัน คู่จริงต่างจาก GPS ไม่เกิน 0.70 ม. คู่หลอกต่าง 1.85 และ 2.17 ม.
5. **วิธีเดิม (ต่อเป็นลูกโซ่ตามชื่อไฟล์) เทียบวิธีใหม่ บนชุดหลัก 21 ภาพ** — แนวนอนคลาดจาก GPS พอกัน (0.09 กับ 0.10 ม.) แต่แนวตั้งต่างกัน: โดรนไต่ขึ้นจริง 1.00 ม. ตามความสูงในภาพ วิธีเดิมให้ผืนสูงต่างกัน 1.55 ม. วิธีใหม่ 1.24 ม.

## 4. วิธีที่เลือก และผล

ขั้นตอนใน `ต่อภาพ_แกน.py`:

1. หาจุดเด่น (SIFT) ทุกภาพ
2. ลองจับคู่ทุกคู่ด้วยจุดเด่นที่แรงที่สุด 1,600 จุด → คู่ที่ได้ ≥ 8 จุดลงรอย ส่งตรวจ · ถ้าภาพมีเวลา คู่ที่ถ่ายติดกันส่งตรวจด้วยเสมอ
3. ตรวจละเอียด: RANSAC หาการเลื่อน-หมุน-ย่อขยาย รับเมื่อจุดลงรอย ≥ 30, ย่อขยายไม่เกิน 3 เท่า, หมุนไม่เกิน 30°, จุดไม่กระจุก
4. ถ้ามี GPS: ในรอบบินเดียวกัน หาสเกล (เมตรต่อพิกเซล) จากมัธยฐานของทุกคู่ แล้วตัดคู่ที่ระยะจาก GPS ต่างจากระยะบนภาพเกิน 40% ของความกว้างที่ภาพหนึ่งใบเห็น และอัตราส่วนเกินช่วง 0.4–2.5 · ถ้าแต่ละคู่ให้สเกลไม่ไปทางเดียวกัน ถือว่า GPS ไม่น่าเชื่อ ไม่ใช้ตรวจ
5. กลุ่มที่เชื่อมถึงกัน = หนึ่งผืน · วางภาพจากต้นไม้ที่คู่แข็งแรงสุด เริ่มที่ภาพกึ่งกลาง แล้วปรับทุกภาพพร้อมกันแบบถ่วงน้ำหนักให้ทุกคู่ลงรอย (คู่ที่ขัดกับส่วนใหญ่ถูกลดน้ำหนักและติดป้าย)
6. ลำดับภาพ = ตำแหน่งบนผืน · ภาพชุดเดิมได้ผลเดิมเสมอไม่ว่าใส่ลำดับไหน (จัดลำดับภายในด้วยเนื้อภาพ และตรึงการสุ่มของ RANSAC)

เกณฑ์ตัวเลขในข้อ 2–4 (8, 30, 3 เท่า, 30°, 40%, 0.4–2.5) **ผู้จัดทำตั้งเอง** จากภาพชุดนี้ชุดเดียว

| ชุดทดสอบ (สลับลำดับ + ตั้งชื่อมั่ว) | ผล |
|---|---|
| ชุดหลัก 21 ภาพ | ผืนเดียว 16,216×2,078 px ลำดับถูกทั้ง 21 ภาพ · ลอง 210 คู่ → ส่งตรวจ 52 → ใช้ 28 · คลาดบนผืนมัธยฐาน 2.0 px สูงสุด 3.5 px · ตรงกับเวลา 100% · คลาดจาก GPS 0.10 ม. · สเกลประมาณ 0.31 มม. ต่อพิกเซลของภาพต้นฉบับ · คำนวณ 5.9 วินาที |

## 5. ข้อจำกัดที่รู้

- ถ้าไม่มี GPS และรอยต่อพึ่งคู่ภาพคู่เดียว โปรแกรมกันคู่หลอกไม่ได้ ทำได้แค่เตือน
- ตัวตรวจ GPS ทดสอบกับภาพชุดเดียว โดรนรุ่นเดียว (Mini 3 Pro) ที่บินข้างคานในที่โล่ง ยังไม่รู้ว่าใต้สะพานจริงหรือกับ Matrice 4E พิกัดจะนิ่งแบบนี้ไหม
- ใช้แบบจำลองเลื่อน-หมุน-ย่อขยาย ถ้าภาพถ่ายคนละมุมมาก รอยต่อเหลื่อม (เห็นแล้วตอนรวมสองรอบบิน)
- สเกลจาก GPS เป็นค่าประมาณ ใช้แทนเลเซอร์ 4 จุดในหัวข้อ 3.6 ของเล่มไม่ได้
- ลองทุกคู่ใช้เวลาโตตามจำนวนภาพยกกำลังสอง (200 ภาพประมาณ 40 วินาทีเฉพาะขั้นลองคู่ — คำนวณจาก 2 มิลลิวินาทีต่อคู่ ยังไม่ได้วัดจริง)
- ยังไม่ได้ลองกับผิวคอนกรีตเรียบสะอาด และยังไม่ได้ลองกับภาพชุด `rawdata/`

## 6. แก้ข้อความที่เคยบอกผิด

ตอนบ่ายวันเดียวกัน Claude บอกว่าผืนภาพเอียง "เพราะความคลาดสะสม ไม่ใช่คานเอียงจริง" **ข้อนี้พูดโดยไม่ได้ตรวจ และผิดเป็นส่วนใหญ่** ความสูงที่ฝังในภาพบอกว่าโดรนไต่ขึ้นจริง 1.00 ม. ตลอดแนว (รูปแบบขึ้นลงตรงกับผืน สหสัมพันธ์ 0.98) ส่วนที่เป็นความคลาดของวิธีเดิมมีราว 0.5 ม. (ผืน 1.55 ม. เทียบ 1.00 ม.) วิธีใหม่เหลือราว 0.2 ม. (1.24 ม.) · ยังบอกไม่ได้ว่าโดรนไต่ขึ้นเพราะคานลาดจริงหรือเพราะนักบิน
