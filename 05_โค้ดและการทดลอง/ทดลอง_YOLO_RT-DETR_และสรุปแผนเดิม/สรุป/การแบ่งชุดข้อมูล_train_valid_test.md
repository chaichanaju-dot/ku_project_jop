# การแบ่งชุดข้อมูล train / valid / test — ภาพโดรนจริง (private) กัน overfit

> สรุปนี้ generate โดย Claude จากบทสนทนาวางแผนเตรียมข้อมูล ไม่ใช่ไฟล์ต้นฉบับ แก้ไข/อัปเดตได้ตามปกติ
> **ขอบเขต:** ไฟล์นี้พูดถึงเฉพาะภาพรอบบินโดรนจริง (`Bridge/`, private, label ด้วย LabelMe) เท่านั้น — ไม่เกี่ยวกับ dataset จาก Roboflow (ดู `work_diary.md` และ `ขั้นตอนเตรียมข้อมูล_labeling.md` สำหรับ workflow ฝั่ง Roboflow แยกต่างหาก)

## ปัญหาที่เจอ: ภาพจากรอบบินโดรนซ้ำกันเยอะ

เช็คโฟลเดอร์จริงแล้ว (เช่น `Bridge/Land/Under/DJI_202510021143_007`) พบว่า **1 รอบบิน = ภาพหลายร้อยใบ ถ่ายห่างกันแค่ ~2 วินาที** ต่อเนื่องตามเส้นทางบิน (มีไฟล์ PPK นำทาง แสดงว่าบินแบบซ้อนทับภาพ 70-80% ตามมาตรฐาน photogrammetry) — แปลว่าภาพติดกันแทบเป็นจุดเดียวกัน แค่ขยับมุมนิดเดียว

## ทำไมสุ่มแบ่ง train/valid/test แบบธรรมดาไม่ได้

ถ้าสุ่มแบ่งจากภาพทั้งหมดปนกันเลย ภาพที่เกือบเหมือนกัน (ห่างกันแค่ 2 วิ) จะกระจายไปคนละชุด เช่น ภาพที่ 5 ไป train แต่ภาพที่ 6 (แทบเหมือนกันเป๊ะ) ไป test

ผลคือ: พอทดสอบ โมเดล "จำ" ภาพที่ 5 ได้อยู่แล้วเพราะแทบเป็นภาพเดียวกัน → ผลทดสอบ (test) ออกมาดูดีเกินจริง ทั้งที่จริงๆ โมเดลอาจ overfit อยู่ก็ได้ แค่เราตรวจไม่พบเพราะ test set ไม่ได้เป็นตัวแทนข้อมูลใหม่จริง

**ศัพท์ตรงนี้เรียกว่า "data leakage" (ข้อมูลรั่วไหลข้ามชุด)** — เกี่ยวข้องกับ overfitting โดยตรงเพราะทำให้เรา "มองไม่เห็น" ปัญหา overfit เหมือนเฉลยข้อสอบหลุดเข้าไปในข้อสอบจริง

ตัวอย่างที่ยืนยันปัญหานี้จากเปเปอร์ที่อ่านมา (Chen et al. 2023): validation accuracy 98%+ แต่พอทดสอบกับภาพภาคสนามจริงเหลือแค่ 84% — เป็นสัญญาณเตือนแบบเดียวกัน

## วิธีแก้: แบ่งตาม "กลุ่ม" (รอบบิน) ไม่ใช่แบ่งทีละภาพ

**กฎหลัก: 1 โฟลเดอร์รอบบิน = ไปได้แค่ 1 ชุดเท่านั้น** (train หรือ valid หรือ test เลือกอย่างใดอย่างหนึ่ง) ห้ามภาพจากรอบบินเดียวกันกระจายไปมากกว่า 1 ชุด — กฎนี้ใช้กับ**ทั้ง 3 ชุด** ไม่ใช่แค่ train กับ test ต้องแยกกัน (valid ก็ต้องแยกด้วย เพราะ leak เข้า valid ก็ทำให้เลือก setting/จุดหยุดเทรนผิดพลาดได้เหมือนกัน)

ตัวอย่าง:
```
train: DJI_007, DJI_008, DJI_009, DJI_010, DJI_014, DJI_015 ...  (ส่วนใหญ่ ~70%)
valid: DJI_011, DJI_016                                          (~15-20%)
test:  DJI_018, DJI_019                                          (~15-20%, ไม่เคยอยู่ใน train/valid เลย)
```

**ข้อดีเพิ่มเติม:** การแบ่งแบบนี้เท่ากับทดสอบกับสะพาน/ช่วงที่ไม่เคยเห็นมาก่อนจริงๆ ไม่ใช่แค่มุมกล้องต่างนิดหน่อย วัดความสามารถจริงของโมเดลได้แม่นกว่าการสุ่มธรรมดามาก

## Test ก็ต้อง label เหมือนกัน ไม่ใช่แค่ train

ทั้ง 3 ชุด (train, val, test) **ต้อง label หมดทุกชุด** ไม่มีชุดไหนไม่ต้อง label เพราะถ้า test ไม่มี label จะไม่มีทางรู้เลยว่าโมเดลทายถูก/ผิด วัดค่า precision/recall ไม่ได้เลย ความต่างคือ **เอา label ไปใช้ตอนไหน** ไม่ใช่ "มีหรือไม่มี":

| ชุด | label ใช้ทำอะไร |
|---|---|
| Train | ให้โมเดลเรียนรู้ตรงๆ |
| Valid | เช็คระหว่างเทรน (ตัดสินใจว่าจะหยุดตอนไหน ปรับ setting ยังไง) |
| Test | เก็บไว้เฉยๆ ไม่แตะเลยจนจบ เอาไว้เช็คครั้งสุดท้ายว่าใช้ได้จริงแค่ไหน |

## เครื่องมือช่วยแบ่ง (ปิดการสุ่มแบ่งอัตโนมัติของ labelme2yolo แล้วคุมเองตามรอบบิน)

- **labelme2yolo:** ใส่ `--val_size 0 --test_size 0` (ปิดการแบ่งอัตโนมัติ ยัดทุกไฟล์ไป train ให้หมดก่อน) แล้วค่อยย้ายไฟล์เองตามรอบบินทีหลัง

## รอบแรกควรใช้ข้อมูลกี่ภาพ

ไม่มีตัวเลขตายตัว เทียบเคียงจากเปเปอร์ที่อ่านมา: Chen 2023 ใช้ ~6,600 ภาพ (3 คลาส) ได้แม่น 84% จริง, CODEBRIM ~7,700 ภาพ (6 คลาส) F1 85%, Çelik ~2,070 ภาพ (8 คลาส segmentation) กลับได้ IoU แค่ 20.6% (ยังไม่พอ), สคริปต์รุ่นพี่ 1,042+115 ภาพ (7 คลาส OBB) ได้ precision 0.91 — ตัวเลขกระโดดมากเพราะขึ้นกับความยากของงาน ไม่ใช่แค่จำนวน

**เป้าหมายรอบแรกที่แนะนำ:** ~300-600 ภาพรวม (โครงสร้าง+ความเสียหาย) พยายามให้แต่ละ class ความเสียหายมีอย่างน้อย **30-50 ตัวอย่างขึ้นไป** — เป้าหมายคือ "ให้ครบวงจรใช้งานได้ก่อน" ไม่ใช่ "ให้แม่นสุด" เทรนเสร็จดูผลแล้วค่อยเพิ่มข้อมูลตรงจุดที่อ่อน

## การเพิ่มข้อมูลเทรนในรอบต่อๆ ไป

### กฎการแบ่งกลุ่ม (train/valid/test) เป็นข้อผูกมัดถาวร ไม่ใช่แค่รอบแรก

เมื่อกำหนดแล้วว่ารอบบินไหนเป็น train/valid/test **ห้ามเปลี่ยนกลุ่มมันอีกเลยตลอดทั้งโปรเจกต์**:

- ถ้ารอบบินนั้นอยู่ใน **"train"** → ใช้ภาพที่เหลือ (ที่ยังไม่เคย label) จากรอบบินเดียวกันมาเพิ่มในรอบเทรนต่อไปได้เรื่อยๆ ไม่จำกัด เพราะยังอยู่กลุ่มเดิม ไม่มีทางไปปนกับ valid/test
- ถ้ารอบบินนั้นอยู่ใน **"valid" หรือ "test"** → ห้ามเอามาเทรนเด็ดขาด ทั้งตอนนี้และทุกรอบในอนาคต เพราะจะทำให้ evaluation set นั้นใช้วัดผลจริงไม่ได้อีกเลยตลอดไป (โมเดลเคยเห็นมันแล้ว)

ตัวอย่าง: รอบบินที่เป็น train เอาไป label แค่ 1/3 ก่อนในรอบแรกก็ได้ พอรอบหน้าค่อย label อีก 2/3 ที่เหลือเพิ่ม แล้วเอามารวมกับ 1/3 เดิม — ทำได้สบายเพราะทั้งรอบบินนั้นเป็น "train" อยู่แล้วตั้งแต่ต้น

### เทรนต่อ ต้องเอาข้อมูลเก่า+ใหม่รวมกัน ห้ามใช้ใหม่อย่างเดียว

เอา `best.pt` จากรอบก่อนมาเป็นจุดตั้งต้น (ไม่ต้องเริ่มจากศูนย์) แต่ **เทรนด้วยชุดข้อมูลรวม (เก่า+ใหม่)** ไม่ใช่ข้อมูลใหม่อย่างเดียว — ถ้าใช้ใหม่ล้วนๆ โมเดลจะค่อยๆ "ลืม" สิ่งที่เคยเรียนจากข้อมูลเก่า (catastrophic forgetting) โดยเฉพาะถ้าข้อมูลใหม่มีลักษณะต่างจากเก่า

ถ้าข้อมูลเก่ามีเยอะกว่าใหม่มาก ข้อมูลใหม่อาจ "จมหาย" ในกองข้อมูลเก่า — ให้เพิ่ม augmentation/oversample ข้อมูลใหม่เป็นพิเศษเพื่อให้โมเดลเรียนรู้แพทเทิร์นใหม่ได้จริง

(หมายเหตุ: `resume=True` ในสคริปต์รุ่นพี่ใช้สำหรับเทรนต่อจากที่ค้างไว้ตอนไฟดับ/หลุด บนชุดข้อมูล**เดิม**ชุดเดียวกัน คนละกรณีกับการเพิ่มข้อมูลใหม่เข้าไปสอนเพิ่ม)

### วิธีตัดสินใจว่าจะเพิ่มข้อมูลอะไรในรอบหน้า — ดูผลก่อน ไม่ต้องนั่งนับเอง

เทรนรอบแรกเสร็จ → เปิดดูผลสรุปที่โปรแกรมเทรนสร้างให้อัตโนมัติ (confusion matrix, กราฟ precision/recall แยกรายคลาส เหมือนที่เห็นในโฟลเดอร์ `results/` ของรุ่นพี่) → **class ไหนตัวเลขต่ำกว่าเพื่อนชัดเจน รอบหน้าเน้นหาภาพ/label เพิ่มเฉพาะ class นั้น** → เทรนใหม่ด้วยข้อมูลรวม (เก่า+ใหม่) → ดูผลอีกรอบ → วนซ้ำ

ตรงกับที่เจอในเปเปอร์จริง: Chen 2023 เจอ spalling อ่อนสุด (70%), Lateef&Yu เจอ Corrosion Stain อ่อนสุด (74.5%) — ขั้นต่อไปตามธรรมชาติคือไปหาภาพของ class ที่อ่อนเพิ่ม

**ข้อควรรู้:** class คะแนนต่ำไม่ได้แปลว่า "ภาพน้อยไป" เสมอไป บางทีความเสียหายนั้นแยกยากโดยธรรมชาติ (เช่น คราบสนิมจางปนพื้นหลัง) ถ้าเพิ่มภาพแล้วยังไม่ดีขึ้น อาจต้องดูเรื่อง label ให้ชัดเจนขึ้นด้วย ไม่ใช่แค่เพิ่มจำนวนภาพอย่างเดียว

### เก็บ log ผลการเทรนทุกรอบ

ทุกรอบเทรนควรบันทึกไว้ที่ `สรุป/training_log.md` (วันที่, ข้อมูลที่เพิ่ม/เปลี่ยนจากรอบก่อน, ตัวเลขผลรวม+รายคลาส, class ไหนอ่อนสุดรอบนี้, แผนรอบหน้า) จะได้เห็นภาพรวมความคืบหน้าทั้งโปรเจกต์ ไม่ต้องไล่ความจำเอง
