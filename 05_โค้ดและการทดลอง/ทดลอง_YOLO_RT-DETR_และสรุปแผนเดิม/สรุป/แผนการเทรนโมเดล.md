# แผนการเทรนโมเดล — เริ่มใหม่จากศูนย์ (2026-10-09)

> สรุปนี้ generate โดย Claude (session กับมะขาม) ไม่ใช่ไฟล์ต้นฉบับ แก้ไขได้ตามปกติ
>
> **"เริ่มจากศูนย์" ในแผนนี้หมายถึง:**
> - ยังไม่มีภาพที่ label ไว้เลย และไม่ใช้ dataset เดิม
> - ไม่ใช้ผลเทรนรอบก่อนเป็นหลักฐานในการตั้งค่าใดๆ
> - ทุกตัวเลขตั้งจากหลักการ เอกสารอ้างอิง หรือ "รอบนำร่อง" ที่จะวัดใหม่
>
> **แต่ยังเริ่มจากน้ำหนัก pretrained ของ COCO (transfer learning) ไม่ใช่น้ำหนักสุ่ม** — Ultralytics แนะนำให้เทรนจากน้ำหนักสุ่มเฉพาะ dataset ขนาดใหญ่ระดับ COCO/Objects365 ส่วน dataset เล็กถึงกลางให้เริ่มจาก pretrained [Ultralytics tips] งานนี้อยู่ระดับหลักร้อยถึงพันภาพ
>
> **คอลัมน์ "ที่มา":** โค้ด = ตรวจกับซอร์ส Ultralytics จริง (2026-10-09) · docs = เอกสารทางการของเครื่องมือ · เปเปอร์ = งานวิจัยที่อ้าง · กฎโปรเจกต์ = กติกา/เกณฑ์ที่ตกลงไว้ (ไม่ใช่ข้อมูล) · ฉันเลือก = ออกแบบเองพร้อมเหตุผล ต้องยืนยันด้วยผลเทรน

## 1. ข้อเท็จจริงจากโค้ด Ultralytics ที่บังคับการออกแบบ

ตรวจกับซอร์สจริงบน GitHub (`engine/trainer.py`, `models/rtdetr/train.py`, `models/utils/loss.py`, `data/base.py`, `cfg/default.yaml`) และ docs เมื่อ 2026-10-09:

1. **learning rate (LR — ขนาดก้าวที่โมเดลปรับตัว) ลดลงเป็นเส้นตรงตาม epochs ที่ "ตั้งไว้" ไม่ใช่ที่ "เทรนจริง"** — `LR = lr0 × [(1 − epoch/epochs)·(1 − lrf) + lrf]`
2. **การปิด mosaic ช่วงท้าย (close_mosaic) ก็นับจาก epochs ที่ตั้งไว้** — ปิดเมื่อ epoch ≥ epochs − close_mosaic
3. **best.pt = epoch ที่คะแนน val ดีที่สุดเสมอ** ไม่ขึ้นกับ patience — patience มีหน้าที่แค่ "หยุดเร็ว" ประหยัดเวลา
4. **`optimizer='auto'` เลือกตัวปรับน้ำหนักเองตามจำนวนรอบอัปเดตทั้งหมด**
   - สูตร `iterations = ceil(จำนวนภาพ / max(batch, nbs)) × epochs`
   - เกิน 10,000 → MuSGD lr 0.01
   - ไม่เกิน → AdamW lr `0.002×5/(4+จำนวนคลาส)`
   - `warmup_bias_lr` ถูกตั้งเป็น 0 **เฉพาะในโหมด auto**
5. **โมเดลอัปเดตน้ำหนักทุก 64 ภาพ** (`nbs=64`) ไม่ว่า batch เท่าไหร่ — สะสม gradient `round(64/batch)` ครั้งแล้วค่อยอัปเดต 1 ที
6. **RT-DETR ใช้น้ำหนัก loss ตายตัว** (class 1, bbox 5, giou 2) — `box`, `cls`, `dfl`, `cls_pw` ไม่มีผลกับ RT-DETR เลย โค้ดเตือนไว้เองว่า AMP อาจทำให้ loss เป็น NaN และ docs ให้ตั้ง `deterministic=False` เพราะ `grid_sample` ไม่มีโหมดที่ทำซ้ำได้เป๊ะ
7. **`fraction` ไม่ได้สุ่ม** — เลือก "N ไฟล์แรกหลังเรียงชื่อ"

**ผลต่อการออกแบบ:** ถ้าตั้ง epochs สูงๆ แล้วปล่อยให้ patience หยุดเอง best.pt จะมาจากช่วงที่ LR ยังสูง และโมเดลอาจไม่เคยเห็นภาพเต็มแบบไม่ผ่าน mosaic เลย → แผนนี้จึง (ก) วัดหาจุดที่โมเดลอิ่มตัวจากรอบนำร่องก่อน (ข) ตั้ง epochs รอบหลักให้เทรนจบครบตารางจริง

## 2. ก่อนเก็บภาพแรก: ตัดสิน 4 เรื่องให้จบ (Phase 0)

ขั้นนี้คือข้อได้เปรียบของการเริ่มจากศูนย์ — **ออกแบบให้ข้อมูลตอบโจทย์ T-BHI ได้ตั้งแต่วันแรก** แทนที่จะมาตามแก้ทีหลัง

### 2.1 นิยามคลาส + คู่มือ label (เขียนเป็นเอกสารก่อนวาดกรอบแรก)

**ทำไมต้องจบก่อน:** เพิ่มคลาสทีหลัง = ต้องย้อนเปิดทุกภาพที่ label ไปแล้วมาวาดคลาสใหม่ เพราะภาพที่มีของแต่ไม่มี label จะสอนโมเดลว่า "ตรงนี้ไม่ใช่"

**คลาสความเสียหาย** — เลือกจากชนิดที่ BMMS ใช้ให้คะแนน RC และมองเห็นได้จากภาพ 2D (นิยามละเอียดใช้ตาม `drone-image-matching-approaches.md`, เกณฑ์ตาม `สรุปสาระสำคัญ เกณฑ์.pdf`) [กฎโปรเจกต์]

| คลาส | คืออะไร | ใช้ทำอะไรใน T-BHI |
|---|---|---|
| Crack | เส้นแตก เนื้อยังติดเป็นผืนเดียว | ความกว้าง → ระดับ BMMS |
| Spalling | เนื้อหลุดเป็นหลุม/แอ่ง ขอบไม่สม่ำเสมอ | พื้นที่ |
| Exposed_Rebar | เหล็กเสริมโผล่ — **วาดซ้อนอยู่ในกรอบ Spalling** | ภาพ 2D วัดความลึกไม่ได้ แต่ BMMS แยก "ลึกไม่ถึงเหล็ก (ระดับ 4–3)" กับ "ถึงเหล็ก (2–1)" → คลาสนี้คือตัวแทนความลึก |
| Efflorescence | คราบขาว-เทาไหลย้อย | พื้นที่ |
| Rust_Stain | คราบสีน้ำตาลส้ม | พื้นที่ |
| Honeycomb | โพรงใหญ่ เห็นหินแยก ไม่มีปูนหุ้ม | พื้นที่ |

**คลาสโครงสร้าง** — ชิ้นส่วนที่มองเห็นจากโดรนและมีน้ำหนัก We ในสูตร [กฎโปรเจกต์]

| คลาส | รหัส BMMS | We | เหตุผล |
|---|---|---|---|
| Deck | DK | 9 | ภาพใต้สะพานเห็นท้องพื้นเยอะ ไม่มีคลาสนี้ ความเสียหายบนพื้นจะไม่มีชิ้นส่วนให้ผูก แล้วหลุดจาก T-BHI |
| Girder | GD | 10 | ชิ้นส่วนหลัก |
| Pier_Cap | CB | 9 | |
| Pier | PR | 10 | ชิ้นส่วนหลัก |

ถ้าในภาพจริงเจอคานขวาง (DP) หรือยางรองคาน (BR) บ่อย ให้ตัดสินเพิ่ม**ก่อน**เริ่ม label

**กติกา label (ใส่ในคู่มือ):**
- **ทุกจุดที่เห็นต้อง label ครบ** — Ultralytics ระบุว่า label ไม่ครบใช้ไม่ได้ [docs]
- **กรอบชิดขอบ ไม่มีช่องว่าง** [docs]
- **1 กรอบ = 1 จุดที่ต่อเนื่องกัน** ห้ามลากกรอบใหญ่ครอบหลายจุด
- **จุดที่ไม่แน่ใจ:** จดชื่อภาพไว้ทบทวนร่วมกัน ห้ามข้ามเงียบๆ

### 2.2 ความละเอียดภาพที่ต้องได้ (GSD = 1 pixel แทนกี่ mm)

**สูตร:** `GSD = (ความกว้างเซนเซอร์ × ระยะถึงผิว) / (ระยะโฟกัสจริง × ความกว้างภาพเป็น pixel)`

ตัวอย่างกล้องหลัก DJI Mavic 3 (เซนเซอร์กว้าง 17.3 mm — ตรวจสเปกรุ่นที่ใช้จริงอีกครั้ง, โฟกัส 12.3 mm, ภาพกว้าง 5280 px):

| ระยะถึงผิว | 1.5 ม. | 2 ม. | 3 ม. | 5 ม. |
|---|---|---|---|---|
| GSD (mm/px) | 0.40 | 0.53 | 0.80 | 1.33 |

**เทียบกับเกณฑ์ BMMS:**
- รอยร้าว RC แบ่งระดับที่ 1.6 / 3.2 / 4.8 mm [กฎโปรเจกต์]
- ถ้ากำหนดว่ารอยร้าว 1.6 mm ต้องกิน ≥3 pixel → ต้องได้ GSD ≤ 0.53 mm/px = บินห่างไม่เกิน ~2 ม. ด้วยกล้องหลัก ซึ่งเสี่ยงใต้สะพาน
- ทางออกคือใช้เลนส์ซูมจากระยะปลอดภัย (ดูเอกสาร `rawdata/02 Methodology & Work/01_UAV_platform_and_ranging_study/`)

**ข้อจำกัดที่ต้องเขียนลงรายงาน:**
- เลข "≥3 pixel" เป็นค่าที่ฉันตั้ง — เอกสาร UAV study พบว่าแหล่งอ้างอิงให้ค่าต่างกันถึง 6 เท่า ต้องวัดเองด้วยแผ่นรอยร้าวอ้างอิง
- **เกณฑ์ PC (0.10 mm) เป็นไปไม่ได้จากภาพโดรน** — เขียนเป็นขอบเขตงาน

### 2.3 ของอ้างอิงขนาดในภาพ + ค่าจริงหน้างาน

- **ทุกภาพที่ถ่ายความเสียหายให้มี ArUco marker หรือจุดเลเซอร์ขนานติดอยู่ในภาพ** — มีวิธีและโค้ดรองรับใน `crack_scale.py` / `laser_scale.py` (โฟลเดอร์เดียวกับ UAV study)
- **วัดรอยร้าวจริงหน้างานบางจุด** (crack gauge หรือคาลิเปอร์) แล้วจดตำแหน่งไว้ — ใช้พิสูจน์ว่าระบบวัดความกว้างได้ถูก
- เก็บตั้งแต่บินครั้งแรก เพราะย้อนกลับไปเก็บทีหลังไม่ได้

### 2.4 กติกาแบ่งชุด (ล็อกก่อน label)

- **หน่วยแบ่ง = รอบบิน** — ถ้ามีมากกว่า 1 สะพาน การแยก**ทั้งสะพาน**ไว้เป็น test ดีที่สุด เพราะพิสูจน์ได้ว่าใช้กับสะพานใหม่ได้
- **เลือกรอบบินของ test และ val ก่อน label อะไรเลย** แล้วจดลงไฟล์ (เช่น `splits.yaml`)
- **ภาพสาธารณะเข้า train เท่านั้น**
- **tile ทุกแผ่นตามรอบบินของภาพแม่**
- **ภาพที่เข้า test/val แล้วห้ามออกตลอดกาล** — ถ้าเจอ label ผิดใน test ให้แก้ จดไว้ แล้ววัดทุกโมเดลใหม่บน test ฉบับแก้

## 3. แหล่งข้อมูล

### 3.1 ภาพโดรนของเราเอง (บังคับ)

- **เป็น test และ val ทั้งหมด** + เป็นส่วนหนึ่งของ train — เพราะคือภาพแบบที่ระบบต้องเจอตอนใช้งานจริง
- **label แบบออฟไลน์เท่านั้น ห้ามอัปโหลดขึ้นคลาวด์บุคคลที่สาม** [กฎโปรเจกต์]
- **เครื่องมือ:** LabelMe มี AI polygon (SAM2/SAM3/EfficientSAM) ที่รันในเครื่องได้หลังโหลดโมเดลครั้งแรก ช่วยให้วาด polygon เร็วขึ้นมาก [docs] — ตรวจก่อนว่าฟีเจอร์ไหนฟรี ไหนเป็นรุ่น Pro
- **เลือกภาพทุก ~10 เฟรม** — ภาพติดกันที่ห่าง 2 วินาทีแทบไม่ได้สอนอะไรใหม่

## 4. จำนวนข้อมูล

### 4.1 ที่มาของตัวเลข: ชุดวัดต้องมีตัวอย่างพอให้คะแนนนิ่ง

ค่าคลาดเคลื่อนของ recall รายคลาส ประมาณด้วย `SE = √(p(1−p)/n)` (กรณีแย่สุด p = 0.5):

| กรอบในชุดวัด (n) | 10 | 15 | 20 | 30 | 50 | 100 |
|---|---|---|---|---|---|---|
| ± (1 SE) | 0.16 | 0.13 | 0.11 | 0.09 | 0.07 | 0.05 |

- **อ่านว่า:** test 50 กรอบต่อคลาส → คะแนนแกว่ง ~±0.07 ความต่างที่เล็กกว่า ~0.14 (2 SE) ระหว่างสองโมเดลยังสรุปไม่ได้
- **เป็นค่าประมาณ** เพราะ mAP ไม่ใช่สัดส่วนตรงๆ และกรอบในภาพเดียวกันไม่อิสระต่อกัน ของจริงจะแกว่งมากกว่านี้
- **val:** val ชุดเล็กทำให้การเลือกโมเดลเพี้ยน และทางแก้ที่ง่ายที่สุดคือขยาย val (Cawley & Talbot 2010)

| ชุด | ความเสียหาย | โครงสร้าง | ที่มาของตัวเลข |
|---|---|---|---|
| test (ภาพเรา) | ≥50 กรอบต่อคลาส, ≥2 รอบบิน | ≥30 ชิ้นต่อคลาส, ≥2 รอบบิน | ตารางข้อ 4.1 (±0.07) — ฝั่งโครงสร้างแต่ละภาพมีหลายชิ้นและวัตถุชัดกว่า ใช้น้อยกว่าได้ [ฉันเลือก] |
| val (ภาพเรา) | ≥30 กรอบต่อคลาส | ≥20 ชิ้นต่อคลาส | ใช้เลือก best.pt ต้องนิ่งพอ [ฉันเลือก] |
| train (ภาพเรา) | ขั้น M1 / M2 / M3 = 50 / 150 / 300 กรอบต่อคลาส | เริ่ม 100–150 ภาพ, ≥100 ชิ้นต่อคลาส | เพิ่มทีละขั้นแล้วดูกราฟ (ข้อ 9) ว่าคุ้มจะไปต่อไหม |
| ภาพว่าง (background) | ≤10% ของ train | — | ลดการทายผิด [docs] |

**ข้อควรรู้:**
- **ตัวเลข "ผลดีที่สุด" ของ Ultralytics** (≥1,500 ภาพ และ ≥10,000 กรอบต่อคลาส) ไกลเกินกำลังโปรเจกต์นี้ ใช้เป็นเพดานอ้างอิงเท่านั้น [docs]
- **คลาสที่หายากบนสะพานเรา** (เช่น Honeycomb, Exposed_Rebar) อาจไปไม่ถึง 50 ใน test → รายงานพร้อมค่าคลาดเคลื่อนตรงๆ ห้ามรวมกับคลาสอื่นเพื่อให้ตัวเลขดูดี (dataset สาธารณะช่วยฝั่ง train ได้ แต่ช่วย test ไม่ได้)
- **label train ตามคิวที่สุ่มลำดับไว้ล่วงหน้า** → M1 ⊂ M2 ⊂ M3 จะเป็นชุดย่อยสุ่มที่ซ้อนกันเองโดยอัตโนมัติ เอาไปทำ learning curve ได้ทันที และไม่ลำเอียงไปทางภาพง่ายๆ ที่มักถูกหยิบมา label ก่อน

### 4.3 ภาพโดรนต้องตัดเป็น tile (ฝั่งความเสียหาย)

- **ปัญหา:** ภาพ 5280×3956 ถ้าบีบลง 960 จะเล็กลง ~5.5 เท่า รอยร้าวกว้าง 3 pixel เหลือ ~0.5 pixel = หายไปเลย
- **Ultralytics แนะนำ:** ถ้ามีวัตถุเล็กเยอะ ให้เทรนที่ความละเอียดเดิมหรือสูงกว่า [docs]
- **ทางแก้:** label บนภาพเต็ม แล้ว**ตัดเป็น tile 960×960 ซ้อนกัน 20%** (~35 แผ่นต่อภาพ) ใช้วิธีเดียวกันทั้งตอนเทรนและตอนใช้งานจริง
- **หลักฐาน:** งานวิจัย SAHI (Akyon et al. 2022) พบว่าตัดภาพตอนใช้งานอย่างเดียวเพิ่ม AP 5.1–6.8% และตัดตอนเทรนด้วยรวมกันเพิ่ม 12.7–14.5% บน VisDrone/xView (ทดสอบกับ detector ตัวอื่น ใช้เป็นทิศทาง ไม่ใช่ตัวเลขที่จะได้แน่)
- **เก็บแค่ tile ที่มีความเสียหาย** + tile ว่างไม่เกิน 10%
- **กรอบที่โดนขอบ tile ตัด:** เก็บเฉพาะที่เหลือในแผ่น ≥50% ของพื้นที่ [ฉันเลือก]
- **ตอนใช้งาน:** รวมผลของ tile ที่ซ้อนกันแล้วตัดกรอบซ้ำ ก่อนส่งให้ SAM ทำ mask ที่ความละเอียดเต็ม

ฝั่งโครงสร้างไม่ต้องตัด tile เพราะชิ้นส่วนตัวใหญ่ บีบลง 640 ยังเห็นชัด

### 4.4 ชุดวัด SAM (ไม่ได้ใช้เทรน)

- **ทำอะไร:** วาด polygon ให้ความเสียหายใน test ~30 ชิ้นต่อคลาส (อย่างน้อย Crack กับ Spalling) แล้ววัด IoU และ % พื้นที่คลาดของ mask จาก SAM เทียบกับของคน
- **⚠️ polygon ชุดนี้ต้องวาดหรือแก้ด้วยมือ ห้ามใช้ AI polygon แล้วกดผ่าน** — AI polygon ของ LabelMe ก็คือ SAM ถ้าใช้คำตอบของ SAM เป็นเฉลยไว้ตรวจ SAM เอง ผลจะดีเกินจริงแบบไม่มีความหมาย
- **ความกว้างรอยร้าว:** พิสูจน์ด้วยค่าที่วัดหน้างาน (ข้อ 2.3)

### 4.5 คุณภาพ label

- **ให้ 2 คน label test ส่วนหนึ่ง (~10%) แยกกันโดยไม่เห็นงานกัน** แล้ววัดว่าตรงกันแค่ไหนรายคลาส (กรอบที่ IoU ≥ 0.5 และคลาสตรงกัน)
- ได้ 2 อย่าง: (ก) เพดานที่สมเหตุสมผล — ถ้าคนยังเห็นตรงกันแค่ 70% อย่าคาดหวังให้โมเดลได้ 95% (ข) เจอนิยามคลาสที่กำกวมตั้งแต่ต้น ก่อนลามไปทั้ง dataset
- ทุกครั้งที่ export dataset ให้ตั้งชื่อเวอร์ชัน (เช่น `v1-M1`) และจดจำนวนภาพ/กรอบต่อคลาสต่อชุด แหล่งที่มา license และรอบบินไว้ในไฟล์เดียว

### 4.6 Checklist กันข้อมูลรั่ว

- [ ] ภาพจากรอบบินเดียวกันอยู่ชุดเดียวกัน (รวมทุก tile)
- [ ] ภาพสาธารณะอยู่ใน train เท่านั้น และตัดภาพซ้ำข้ามแหล่งแล้ว
- [ ] ภาพ augment (ถ้ามีการทำล่วงหน้า) อยู่ใน train เท่านั้น
- [ ] ไม่ใช้ `fraction` แบ่งชุดย่อย (ข้อ 1.7)

## 5. เลือกโมเดล

### 5.1 ความเสียหาย: RT-DETR-L + SAM

- **ตรงกับสถาปัตยกรรมของโปรเจกต์** (RT-DETR หากรอบ → SAM ทำ mask)
- **ถ้าเริ่มจากศูนย์ก็ยังคุ้ม:** label เป็นกรอบเร็วกว่า polygon มาก ใช้ polygon แค่ชุดวัด SAM (ข้อ 4.4)
- **อยู่ใน Ultralytics** ใช้ format และสคริปต์ชุดเดียวกับ YOLO
- **เลือก L ไม่เลือก X:** บน COCO ตัว X แม่นกว่าแค่ 53.0 → 54.8 AP แต่ช้ากว่าชัด (114 → 74 FPS บน T4) [docs]
  - Sun et al. (2017) พบว่าโมเดลใหญ่ได้เปรียบชัดก็ต่อเมื่อข้อมูลเยอะมาก
  - ที่ 960 px บนการ์ด 16 GB ตัว X จะได้ batch เล็กมาก

### 5.2 โมเดลเทียบ: YOLO26m

- **ทดสอบข้อสันนิษฐาน "transformer ต้องการข้อมูลมากกว่า CNN"** บนข้อมูลชุดเดียวกัน — เป็นผลการทดลองที่มีค่าต่อรายงาน
- **ขนาด m ความแม่นบน COCO ใกล้ RT-DETR-L** (~53 AP) เทียบกันได้ยุติธรรม [README Ultralytics, docs]
- **เป็นรุ่นล่าสุดที่ปล่อยใช้ได้จริง** (ม.ค. 2026) — YOLO27 ประกาศ ก.ย. 2026 แต่ยังไม่ปล่อยน้ำหนัก และ FAQ แนะนำให้ใช้ YOLO26 ไปก่อน
- มีเทคนิค STAL ที่ผู้พัฒนาบอกว่าช่วยวัตถุเล็ก (หลักฐานส่วนใหญ่มาจาก Ultralytics เอง)
- **ถ้า YOLO26m ชนะชัด** ต้องให้มะขามกับอาจารย์ตัดสินว่าจะเปลี่ยนสถาปัตยกรรมไหม

### 5.3 สำรอง (ยังไม่ทำ): RF-DETR

- ICLR 2026, backbone DINOv2 ออกแบบมาเพื่อ fine-tune กับข้อมูลเฉพาะทาง
- บน RF100-VL สูงกว่า RT-DETR ราว 0.3–1.6 AP — **ตัวเลขส่วนใหญ่มาจาก Roboflow เอง**
- ต้องใช้ไลบรารีคนละตัว ใช้เมื่อทั้งสองตัวแรกยังอ่อนจริงเท่านั้น

### 5.4 โครงสร้าง: YOLO26m-seg

- ~23.6M พารามิเตอร์, COCO mask mAP50-95 44.1 [README Ultralytics — ยืนยันในหน้า docs อีกครั้งก่อนอ้างในรายงาน]
- **ไม่เล็กกว่านี้:** พื้นที่ mask ของชิ้นส่วนคือตัวหารของ ye_i — mask หยาบ EHI ก็เพี้ยน
- **ไม่ใหญ่กว่านี้:** 4 คลาส วัตถุตัวใหญ่ ข้อมูลหลักร้อย ใหญ่กว่านี้ไม่คุ้ม
- ถ้าเวอร์ชัน Ultralytics ที่ลงไว้ไม่มี YOLO26-seg ใช้ `yolo11m-seg.pt` แทน

### 5.5 SAM — ไม่ต้องเทรน

ใช้ตอนใช้งานอย่างเดียว เลือกรุ่นจากความเร็วกับผลบนชุดวัด (ข้อ 4.4)

## 9. ลำดับงานทั้งหมด

| Phase | ทำอะไร | ได้อะไร |
|---|---|---|
| 0 | เขียนคู่มือ label + นิยามคลาส, กำหนด GSD, เตรียม marker/เลเซอร์, เลือกรอบบินของ test/val ลง `splits.yaml` | กติกาที่ไม่ต้องแก้ทีหลัง |
| 1 | บิน/ถ่าย (มีของอ้างอิงขนาด + วัดรอยร้าวจริงบางจุด) → **label test ก่อน** → label val → วาด polygon ชุดวัด SAM ด้วยมือ → 2 คน label test ซ้ำ ~10% | ชุดวัดที่ล็อกแล้ว ก่อนเทรนครั้งแรก |
| 2 | label train ถึง M1 (50 กรอบต่อคลาส) ตามคิวสุ่ม → **รอบนำร่อง** RT-DETR + YOLO26m-seg → ลองรันทั้งสายกับภาพจริงไม่กี่ภาพ (ตัด tile → ตรวจจับ → SAM → คำนวณ T-BHI) | E* ของแต่ละโมเดล, เวลาต่อรอบ, รู้ว่าทั้งสายต่อกันได้ |
| 3 | label ถึง M2 (150) → RT-DETR lr0 {0.0001, 0.0003, 0.001} เลือกด้วย val → YOLO26m เทียบ → (ถ้าใช้ข้อมูลสาธารณะ) ทดลองเรื่องแหล่งข้อมูล | lr0 ที่ใช้ต่อ, ผลเทียบสถาปัตยกรรม |
| 4 | label ถึง M3 (300) หรือหยุดก่อนถ้ากราฟแบน → รอบสุดท้าย 3 seed → **learning curve** → test → เขียนรายงาน | ตัวเลขสำหรับรายงาน |

**การทดลองเรื่องแหล่งข้อมูล (ถ้าใช้ dataset สาธารณะ — Phase 3):**
- A = train ด้วยข้อมูลสาธารณะล้วน
- B = สาธารณะ + ภาพเรา
- C = ภาพเราล้วน

วัดบน test ภาพเราทั้งหมด → ตอบได้ว่า "label ภาพตัวเองคุ้มไหม และข้อมูลสาธารณะช่วยจริงหรือแค่ทำให้ช้า"

**learning curve (Phase 4):**
- เทรนคอนฟิกที่ชนะใหม่บนชุด M1, M2, M3 (ซ้อนกันอยู่แล้วจากข้อ 4.2)
- **คุมจำนวนรอบอัปเดตให้ใกล้กัน** — ชุดที่เล็กกว่า k เท่าใช้ epochs มากขึ้น k เท่า (สูงสุด 1,000) ไม่งั้นชุดเล็กจะได้ฝึกน้อยกว่าแค่เพราะรอบน้อย ไม่ใช่เพราะข้อมูลน้อย
- **อ่านกราฟ:** ยังชัน = label ต่อคุ้ม / แบน = ไปแก้อย่างอื่น (label, ขนาด tile, โมเดล)

**ปรับ epochs หลังทุกรอบหลัก:**
- epoch ที่ดีที่สุดตกใน 10% สุดท้าย → รอบหน้าเพิ่ม 50%
- ดีที่สุดก่อนครึ่งทาง และ val loss พุ่ง → ลดลง

**เวลา:** ยังไม่มีตัวเลข — วัดจากรอบนำร่องใน Phase 2 แล้วค่อยวางตารางการใช้การ์ด

## 10. วัดผลและรายงาน

- **การตัดสินใจทุกอย่างใช้ val เท่านั้น** (เลือก lr0, เลือกโมเดล, เลือก epochs)
- **test ใช้รายงานผลแต่ละ Phase ห้ามใช้ตัดสินใจ** — `model.val(data=..., split="test")`
- **รายงานรายคลาส:** P, R, AP50, AP50-95 **คู่กับจำนวนกรอบใน test เสมอ** พร้อมช่วงแกว่งจากหลาย seed
- **แยกรายงาน 2 ชุด:** test ภาพเรา (ตัวเลขหลัก) กับ test สาธารณะ (ถ้ามี) — ห้ามรวมเป็นตัวเลขเดียว
- **เปิด confusion matrix ดูคู่ที่สับสนกัน:** Crack↔Spalling, Efflorescence↔Rust_Stain, Spalling↔Honeycomb
- **รายงานผลชุดวัด SAM** (IoU, % พื้นที่คลาด) และผลวัดความกว้างรอยร้าวเทียบค่าหน้างาน — สองตัวนี้คือหลักฐานว่าตัวเลขที่ป้อนเข้า T-BHI เชื่อได้
- **บันทึกทุกรันลง `training_log.md`:** วันที่, เวอร์ชัน dataset, ค่าที่เปลี่ยนจากรันก่อน, ผลรายคลาส, epoch ที่ดีที่สุด
