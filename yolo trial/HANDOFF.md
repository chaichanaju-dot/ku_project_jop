## 1. โปรเจกต์นี้ทำอะไร (เป้าหมายเดียวประโยคเดียว)

คำนวณ **T-BHI (Thai Bridge Health Index)** — คะแนนสุขภาพสะพาน — จากภาพถ่ายสะพานที่เก็บด้วยโดรน
โดยใช้ AI ตรวจจับ (ก) ชนิดชิ้นส่วนโครงสร้าง และ (ข) ความเสียหาย แล้วคำนวณคะแนนตามคู่มือ
"ประเมินสะพานจากภาพโดรน" (section 4.4–4.8)

**โซ่การคำนวณ (chain) ที่เป็นหัวใจ:**

```
ภาพโดรน
  → ตรวจจับชิ้นส่วน + ความเสียหาย (ได้ mask ระดับพิกเซล)
  → วัดขนาด/พื้นที่ความเสียหาย
  → C_hi  (ระดับความรุนแรงของแต่ละจุด 0–5 ตามเกณฑ์คู่มือ)
  → EHI   (Element Health Index — คะแนนสุขภาพของชิ้นส่วนแต่ละชิ้น)
  → T-BHI (คะแนนรวมของทั้งสะพาน — บอกว่าสะพานยังดีไหม ต้องเข้าซ่อมไหม)
```

**Concept การใช้งานจริง:** บินโดรนถ่ายทุกชิ้นส่วนของสะพาน (เสา/คาน/ตอม่อ/pier cap)
คานยาว ๆ ถ่ายหลายภาพ → เอาภาพมาตรวจจับ → หาพื้นที่พิกเซลของชิ้นส่วนและความเสียหาย
→ ถ้าหา scale (มม./พิกเซล) ได้ ก็แปลงเป็นขนาดจริงเพื่อเข้าเกณฑ์คู่มือ → คำนวณคะแนน

## 2. สถาปัตยกรรมโค้ดปัจจุบัน (ที่มีอยู่แล้ว)

ใช้ **2 โมเดล YOLO ทำงานแยกอิสระบนภาพเดียวกัน แล้วจับคู่ผลด้วย IoU** (ไม่ใช่โมเดลเดียวทำทุกอย่าง):

1. **โมเดลโครงสร้าง (ของเราเอง, YOLO26-OBB)** — หา pier/beam/pier cap เป็นกรอบ OBB
   **ไม่เชื่อ class ที่มันทายเรื่องความเสียหาย** เพราะเทรนจากข้อมูลน้อย

2. **โมเดลความเสียหาย (ของรุ่นพี่, YOLO-OBB)** — หาความเสียหาย + ประเภท
   แม่นมาก (precision 0.91, mAP50-95 0.80, เทรน 942 epoch บน 1042+115 ภาพ)
   class: Crack, Efflorescence, Porous_Defect, Rust_Stained_Exposure, Spalling,
   Steel_Exposure, strain (ยังไม่รู้ความหมาย "strain" — ถูกข้ามอยู่)

**วิธีเชื่อม:** ทั้งคู่แปลงกรอบ OBB เป็น pixel mask แล้วจับคู่ด้วย IoU ≥ 0.3
- จับคู่ได้ → ใช้กรอบของเรา (ตำแหน่งแม่น) + class ของรุ่นพี่ (ประเภทแม่น)
- จับคู่ไม่ได้ → ใช้กรอบรุ่นพี่ (พื้นที่เกินจริงเพราะกรอบสี่เหลี่ยมกว้างกว่ารูปทรงจริง)

ไฟล์หลัก: main.py, vision.py (pipeline), damage_rules.py (mask→ระดับ 0–5),
bridge_health.py (สูตร EHI/T-BHI), element_lookup.py (น้ำหนัก W), train.py

## 3. ปัญหาที่ติดอยู่ตอนนี้ (สำคัญที่สุด)

### 3.1 ปัญหาเฉพาะหน้า — โมเดลโครงสร้างรันไม่ได้
เพิ่งเปลี่ยนโมเดลโครงสร้างจาก YOLO-seg เป็น YOLO26-OBB (2026-09-04)
**แต่ยังไม่มี weight OBB ที่เทรนแล้ว** เพราะยังไม่ได้ re-label dataset เป็น OBB ใน Roboflow
→ ตอนนี้ `python main.py` จะ error ที่ `YOLO(MODEL_PATH)` ทันที (ตั้งใจให้ error ชัด)
→ **งานทุกอย่างถูก block จนกว่าจะ re-label + เทรนเสร็จ** (หรือเปลี่ยนไปใช้ SAM — ดูข้อ 5)

### 3.2 ปัญหาใหญ่เชิงหลักการ — หา scale (มม./พิกเซล) ไม่ได้
เกณฑ์คู่มือกำหนดความรุนแรงเป็น **หน่วยจริง** (มม. / ตร.ซม.) แต่ pipeline มีแค่ **พิกเซล**
→ ถ้าไม่มี mm/px จะ map เข้าเกณฑ์เพื่อหา C_hi ตามคู่มือไม่ได้

**ข้อเท็จจริงเชิงคณิตศาสตร์:** ภาพเดียวจากกล้องเดี่ยวหา scale เองไม่ได้ (scale ambiguity)
ต้องมีข้อมูลเมตริกเข้ามาจากภายนอกเสมอ

**สรุปการหา scale ที่คุยกันแล้ว:**
- EXIF `RelativeAltitude` (DJI) = ความสูงแนวดิ่งเหนือจุด take-off **ไม่ใช่ระยะถึงผิว**
  ใช้ได้เฉพาะถ่ายก้มตรง 90° ถ่ายพื้นราบ — ภาพถ่ายข้างเสา (gimbal pitch ~0°) ใช้ไม่ได้เลย
- เคสจริงที่ตรวจสอบ: gimbal pitch = +3.7° (มองตรงเข้าผิวเสา) → RelativeAltitude ใช้ไม่ได้
  แต่มุมนี้ดีสำหรับการวัด (เกือบตั้งฉาก ไม่มี foreshortening)
- **ทางที่เลือก: ชุดเลเซอร์ขนาน 4 จุด (สีเขียว)** ฉายจุดที่รู้ระยะห่างจริงลงผิว
  → mm_per_px = ระยะห่างจริง / ระยะห่างพิกเซลในภาพ (ราคา ~1,000 บาท ไม่ต้องแตะผิว)
- มี paper รองรับ (Applsci 2023 laser beam, Metrology 2024) — ให้สูตรพร้อมใช้

### 3.3 ปัญหา element identity ข้ามภาพ (ยังไม่ได้แก้)
**BHI เป็นสูตรระดับ element ไม่ใช่ระดับภาพ** — เสาต้นเดียวถ่าย 30 ภาพ ถ้ารวมแบบ per-image
จะได้ 30 element ทันที ทางแก้ที่เสนอ (ไม่ต้องทำ 3D): จัดโฟลเดอร์ "1 ชิ้นส่วน = 1 โฟลเดอร์"
แล้วรวมพื้นที่เสียหายทุกภาพในโฟลเดอร์ก่อนหาร โดยใช้พื้นที่ผิวจริงจากแบบก่อสร้างเป็นตัวหาร

## 5. กำลังตัดสินใจ/ลังเล — เรื่องโมเดล (ประเด็นร้อนตอนนี้)

**อาจารย์อยากให้เอา YOLO ไว้ท้ายสุด** และมองว่า YOLO "จับ pattern ไม่ค่อย academic"
กำลังสำรวจว่าจะใช้ LLM / VLM / SAM แทนได้ไหม

### ความเข้าใจที่ต้องมีก่อน (สำคัญ — เคยเข้าใจผิดมาแล้ว)

**YOLO คือ CNN อยู่แล้ว** ไม่ใช่คนละตระกูล
- **CNN:** YOLO, U-Net, DeepLabv3+, Mask R-CNN
- **Foundation model:** SAM (ViT), VLM เช่น Gemini (ViT + ภาษา)
- **LLM:** ข้อความล้วน — **มองภาพไม่เห็น**

### แต่ละตัวคืนค่าอะไร

| ตระกูล | คืนค่า | คำนวณพื้นที่ได้ไหม | ต้องเทรนไหม |
|---|---|---|---|
| YOLO-seg/OBB | polygon + mask | ได้ | ต้อง (label เยอะ) |
| SAM | mask พิกเซล | ได้ (แม่น) | **ไม่ต้อง (zero-shot)** |
| VLM (Gemini) | JSON + bbox หยาบ | หยาบมาก | ไม่ต้อง |
| LLM | ข้อความ | ไม่ได้ (ไม่เห็นภาพ) | ไม่ต้อง |

### จุดสำคัญ: SAM กับ VLM ตรงข้ามกัน ต้องใช้คู่กัน
- **SAM รู้ "ตรงไหน" (mask แม่น) แต่ไม่รู้ "อะไร"** (บอกไม่ได้ว่า crack หรือ spalling)
- **VLM รู้ "อะไร" (ประเภท) แต่ไม่รู้ "ตรงไหน" ละเอียด** (ได้แค่กล่องหยาบ)
- ใช้เดี่ยว ๆ ไม่ได้ทั้งคู่ → ต้องต่อกัน

### สถาปัตยกรรมที่เสนอ (ไม่ต้องใช้ YOLO เลย → ข้ามปัญหา re-label ข้อ 3.1)

```
VLM (Gemini)  → บอกว่ามีอะไร + bbox หยาบ + ประเภท
      ↓ ส่ง bbox เป็น prompt
SAM           → แปลง bbox เป็น mask ระดับพิกเซล
      ↓ mask
Python        → พื้นที่ → C_hi → EHI → T-BHI    ← ตัวเลขทั้งหมดจบที่นี่
      ↓
LLM           → เขียนรายงานภาษาคน (ไม่แตะตัวเลข)
```

### กฎเหล็ก
**ห้าม LLM คำนวณ C_hi/EHI/T-BHI เด็ดขาด** — สูตรต้องอยู่ใน Python (bridge_health.py)
เพราะ LLM คำนวณอาจผิดและรันซ้ำได้ค่าไม่เท่าเดิม → เสีย reproducibility → งานถูกตีตก
LLM ใช้ได้แค่ขั้นสุดท้าย: แปลงตัวเลขที่ Python คำนวณเสร็จแล้วเป็นรายงานภาษาคน

### คำถามวิจัยที่ตั้งไว้ (สำหรับรายงาน)
"Foundation model ที่ไม่ต้อง label (SAM+VLM) ทดแทนโมเดลที่ต้อง label (YOLO) ได้ไหม
และแลกความแม่นไปเท่าไหร่" → เปรียบเทียบ 2 เส้นทาง ป้อน mask เข้า Python ตัวเดียวกัน
วัด IoU, ความถูกต้องประเภท, และค่า T-BHI สุดท้ายที่ต่างกัน

### ข้อควรระวังของ VLM
- Reproducibility: ต้องตั้ง temperature = 0 และรายงานค่าเบี่ยงเบนจากการรันหลายครั้ง
- ต้นทุน: Gemini Flash ~1 บาท/ภาพ (YOLO inference ฟรีหลังเทรน)
- ต้องมี YOLO เป็น baseline เทียบเสมอ ไม่งั้นพิสูจน์ไม่ได้ว่าวิธีใหม่ดีกว่า

### ⚠️ ยังไม่ได้ตอบ — ควรถามก่อนตัดสินใจ
- **"YOLO จับ pattern ไม่ academic" คืออาการอะไร** (ตรวจไม่เจอ / จำแนกผิด / mask เบี้ยว)
  สามอาการนี้แก้คนละทาง มีแค่อาการเดียวที่ VLM ช่วยได้จริง
- โมเดลรุ่นพี่แม่นมาก (0.91) → ปัญหาน่าจะอยู่ที่โมเดลโครงสร้างที่ยังไม่เทรน (ปัญหา**ข้อมูล**)
  ไม่ใช่ปัญหาสถาปัตยกรรม → เปลี่ยนไป VLM อาจไม่ได้แก้ที่ต้นเหตุ

## 6. จุดที่รู้ว่าต้องแก้ (ยังไม่ได้แก้)

1. **`crack` ใน damage_rules.py ใช้เกณฑ์ "ทับ 1 pixel ก็นับ"** ต่างจาก spalling ที่ใช้ % พื้นที่
   ยิ่งอันตรายเมื่อมี GSD เพราะ 1 pixel อาจ = หลาย มม. → ควรเปลี่ยนเป็น threshold เชิงพื้นที่จริง
2. `honeycomb` และ `rust_efflorescence` ให้คะแนนคงที่ ไม่สนขนาด → ควรเช็คกับคู่มือ
3. เกณฑ์ "ดีมาก" ต้องการ T-BHI == 100.00 เป๊ะ → floating point แทบเป็นไปไม่ได้ ควรเผื่อ tolerance
4. MIN_MATCH_IOU = 0.3 ยังไม่ผ่านการปรับจูนจริง
5. 2D วัดความลึก spalling ไม่ได้ → ประเมิน spalling ต่ำกว่าจริงเสมอ (ต้องเขียนเป็นข้อจำกัด)
6. crack width < 1 พิกเซล → นับ mask ตรง ๆ ได้ค่าเกินจริง ต้องใช้ skeleton + distance transform
   หรือเลื่อน crack width เป็น future work ถ้า GSD ไม่พอ (ทำพื้นที่ให้ครบก่อน วัดง่ายกว่า)
