# T-BHI Bridge Health Index - Project Summary

ให้ Claude Code อ่านไฟล์นี้ก่อน **แล้วเปิดอ่านไฟล์ .py ทุกไฟล์ในโปรเจกต์ประกอบด้วย**
(โปรเจกต์เล็ก อ่านหมดไม่เปลือง) เพราะสรุปนี้ตั้งใจให้เป็นแค่ดัชนี+เหตุผลเบื้องหลัง
ไม่ใช่เนื้อหาเต็มของแต่ละไฟล์ - รายละเอียดจริงต้องไปอ่านจาก docstring ในไฟล์นั้นๆ

## โปรเจกต์คืออะไร

คำนวณ **T-BHI (Thai Bridge Health Index)** จากภาพถ่ายสะพาน โดยใช้ YOLO ตรวจจับ
ชิ้นส่วนโครงสร้าง + ความเสียหาย แล้วคำนวณคะแนนสุขภาพตามคู่มือ
"คู่มือเริ่มต้นโปรเจกต์ประเมินสะพานจากภาพโดรน" (section 4.4-4.8)

## ไฟล์หลักและหน้าที่

| ไฟล์ | หน้าที่ |
|---|---|
| [main.py](main.py) | entry point - เรียก vision.py คำนวณ T-BHI ผ่าน bridge_health.py, พิมพ์รายงานละเอียด, เซฟภาพ overlay |
| [vision.py](vision.py) | pipeline หลัก - รวม 2 โมเดล (ดูสถาปัตยกรรมด้านล่าง) |
| [damage_rules.py](damage_rules.py) | pixel mask overlap → ระดับความเสียหาย 0-5 |
| [bridge_health.py](bridge_health.py) | สูตร EHI/T-BHI + กฎบังคับสถานะจากชิ้นส่วนหลัก (section 4.8) |
| [element_lookup.py](element_lookup.py) | ตารางน้ำหนัก W และ primary/secondary ของแต่ละชิ้นส่วน |
| [train.py](train.py) | สคริปต์เทรนโมเดลโครงสร้าง (YOLO26-OBB) |

รันคำสั่ง: `python main.py [path_ภาพ] [conf]` (ไม่ใส่ argument = ใช้ภาพ/conf default)

ทุกครั้งที่รัน จะได้ 2 อย่าง:
1. **รายงานละเอียดพิมพ์ใน terminal** (`print_detailed_report()` ใน main.py) - ทุก
   damage instance ที่เจอ (ชื่อ, pixel, ระดับ, ค่า C_hi), proportions ต่อระดับ,
   สูตร EHI และ T-BHI คำนวณจริงพร้อมตัวเลขแทนค่าให้เห็นทุกขั้น ไม่ใช่แค่ผลสรุป
2. **ภาพ overlay เซฟอัตโนมัติ** เป็น `<ชื่อภาพ>_overlay.png` ในโฟลเดอร์ที่รันคำสั่ง
   (`save_overlay()` ใน vision.py) - เส้นขอบ+label สีต่างกันตาม damage_type
   พร้อม legend เฉพาะ class ที่เจอจริงในภาพนั้น

## สถาปัตยกรรมปัจจุบัน (สำคัญที่สุด - อ่านให้เข้าใจก่อนแก้โค้ด)

ใช้ **2 โมเดลแยกกัน ทำงานอิสระต่อกัน (parallel)** บนภาพเดียวกัน แล้วจับคู่ผลด้วย
**IoU** ไม่ใช่โมเดลเดียวทำทุกอย่าง:

1. **`MODEL_PATH`** (`runs/obb/train/weights/best.pt`, ของเราเอง, **YOLO26-OBB**
   ตั้งแต่ 2026-09-04 - เดิมเป็น YOLO-seg, เปลี่ยนสถาปัตยกรรมแล้วเพราะ label ง่ายกว่า
   และกรอบเฉียงจับชิ้นส่วนที่ถ่ายเอียงได้แม่นกว่ากรอบตรง)
   → หาโครงสร้าง (pier/beam/pier cap) เป็นกรอบ OBB rasterize เป็น mask + ให้กรอบ
   รูปทรงความเสียหายจากภาพเดียวกัน (**ไม่เชื่อ class ที่มันทาย** เพราะเทรนจากข้อมูล
   เล็ก) **ยังไม่ได้เทรนโมเดลนี้ใหม่หลังเปลี่ยนสถาปัตยกรรม** - ต้อง re-label dataset
   เป็น OBB ใน Roboflow แล้ว export ใหม่ก่อน ถึงจะรัน `python src/train.py` ได้จริง
   (ดู [train.py](train.py) - มันเช็ค label format ให้เองแล้วถ้ายังเป็น seg format
   จะ error ทันทีพร้อมบอกวิธีแก้)

2. **`SENIOR_MODEL_PATH`** (`C:\ku_project_jop\rawdata\งานของรุ่นพี่\weights\best.pt`,
   ของรุ่นพี่, **YOLO-OBB**) → หาความเสียหาย**และประเภท**เองอิสระ
   (แม่นมาก: precision=0.91, mAP50-95=0.80, เทรน 942 epoch บน 1042+115 ภาพ)
   class ที่รู้จัก: Crack, Efflorescence, Porous_Defect, Rust_Stained_Exposure,
   Spalling, Steel_Exposure, strain (**"strain" ยังไม่รู้ความหมาย ถูกข้ามอยู่**)
   ไฟล์นี้**ไม่แตะ**ตอนเปลี่ยนสถาปัตยกรรม - ใช้ต่อได้เลย

**วิธีเชื่อม:** ทั้ง 2 โมเดลเป็น OBB เหมือนกันแล้ว ทั้งคู่แปลงกรอบ (4 มุม) เป็น pixel
mask ด้วยฟังก์ชันเดียวกัน (`_obb_to_mask`) แล้วจับคู่กันด้วย **IoU ≥ 0.3**
(`_best_matching_mask`, ค่าคงที่ `MIN_MATCH_IOU`)
- จับคู่ได้ → ใช้กรอบของเรา (ตรงตำแหน่งที่ครอบชิ้นส่วนจริง) + ใช้ class ของรุ่นพี่ (ประเภทแม่นยำ)
- จับคู่ไม่ได้ → fallback ใช้กรอบ OBB ของรุ่นพี่ rasterize เป็น mask เอง (พื้นที่ประเมินเกินจริง
  เพราะกรอบสี่เหลี่ยมกว้างกว่ารูปทรงจริงเสมอ แต่ยังดีกว่าไม่นับเลย)

**ทำไมต้องซับซ้อนขนาดนี้:** ลองมาแล้วหลายแบบ (โมเดลเดียวทำทุกอย่าง / ต่อกันแบบ
sequential crop-then-classify) ล้วนมีปัญหา - สรุปคือ "ใครถนัดอะไรให้ทำเต็มที่
อย่างนั้น ไม่แบ่งครึ่งๆ กลาง ๆ" ดูรายละเอียดเหตุผลเพิ่มเติมได้ใน docstring ของ
[vision.py](vision.py) บรรทัดบนสุด (เขียนไว้ละเอียดแล้ว)

## บั๊กที่เจอและแก้ไปแล้ว

1. `_best_matching_mask` เดิมใช้ raw overlap count (ไม่ใช่ IoU) → mask ขยะขนาดใหญ่
   จากโมเดลเราเอง (ครั้งหนึ่งเจอ mask "crack" ที่มีพื้นที่เท่ากับทั้ง pier พอดี - ชัดว่า
   เป็น false positive) ไปชนะการจับคู่กับความเสียหายจริงแทบทุกจุดเพราะ mask ใหญ่
   ทับกับทุกอย่างในบริเวณนั้น แก้แล้วโดยเปลี่ยนเป็น IoU (ดู `MIN_MATCH_IOU = 0.3`
   ใน vision.py)

2. **นับชิ้นส่วนโครงสร้างซ้ำ (double-counting)** - ที่ conf ต่ำมาก (0.01) YOLO's NMS
   ไม่ได้ suppress detection ซ้อนกันของวัตถุชิ้นเดียวกันเสมอไป (เจอ "pier bridge"
   2 กล่องที่ confidence เกือบเท่ากันเป๊ะ 0.014887 vs 0.014886 ตำแหน่งซ้อนทับกัน
   เกือบสนิท) ผลคือชิ้นส่วนจริงชิ้นเดียวถูกนับเป็น 2 element (คนละ EHI เล็กน้อยเพราะ
   ขอบ mask ต่างกันนิดหน่อย) แล้วทั้งคู่ไปรวมใน `sum(q*W*EHI)` ทำให้ชิ้นนั้นมีน้ำหนัก
   เป็น 2 เท่าใน T-BHI โดยไม่ตั้งใจ - แก้แล้วด้วย `_dedupe_structural()` (vision.py,
   ค่าคงที่ `DEDUPE_IOU = 0.7`) รวม mask ของ detection ที่ class เดียวกันและ IoU
   สูงเข้าด้วยกันก่อนสร้างรายงาน (เช็คจากภาพ image_0001431: เดิมรายงาน 4 element
   (pier×2, pier_cap×2) หลังแก้เหลือ 2 element (pier×1, pier_cap×1) ตรงกับที่เห็น
   ในภาพจริง, T-BHI เปลี่ยนจาก 89.48 → 88.59)

## จุดที่รีวิวแล้วอาจต้องแก้ (สูตร/เกณฑ์ - ยังไม่ได้แก้จริง)

1. **`crack` ใน damage_rules.py ใช้เกณฑ์ "ทับ 1 pixel ก็นับ"** ต่างจาก
   spalling/exposed_rebar ที่ใช้ % พื้นที่ทับ (≥30%) — เสี่ยงมากขึ้นตอนนี้เพราะ
   fallback OBB มักให้กรอบกว้างเกินจริง อาจทำให้ crack โดนตัดสินว่า "ทับสนิม"
   ทั้งที่ไม่ได้ทับจริง ควรใส่ threshold % ให้ crack เหมือนตัวอื่น
2. **`honeycomb` และ `rust_efflorescence` ให้คะแนนคงที่** (4 กับ 3 ตามลำดับ)
   ไม่สนขนาดพื้นที่เสียหายเลย ต่างจาก crack/spalling ที่ granular กว่า - ควรเช็ค
   กับคู่มือต้นฉบับว่าตั้งใจแบบนี้จริงไหม
3. **เกณฑ์ "ดีมาก" ต้องการ T-BHI == 100.00 เป๊ะ** (bridge_health.py) ในทาง
   ปฏิบัติแทบเป็นไปไม่ได้จาก floating point - ควรเผื่อ tolerance เล็กน้อย
4. **`MIN_MATCH_IOU = 0.3`** (vision.py, ที่เพิ่งเพิ่มตอนแก้บั๊ก) ยังไม่ผ่านการ
   ทดสอบ/ปรับจูนจริง เลือกมาแค่ให้ตรงกับค่าคงที่อื่นในไฟล์เดิม
