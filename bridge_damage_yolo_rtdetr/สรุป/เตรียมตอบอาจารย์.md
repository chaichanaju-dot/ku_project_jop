## 2. ทำไมใช้สถาปัตยกรรม AI แบบนี้ (2 โมเดลอิสระ)

**คำตอบ:** ใช้ **YOLO-segmentation** หาโครงสร้าง + **RT-DETR หากรอบความเสียหาย ส่งต่อให้ SAM refine เป็น pixel mask** — ทำงานอิสระต่อกันบนภาพเดียวกัน ไม่ใช่โมเดลเดียวทำทุกอย่าง

**ทำไมแยก 2 โมเดล ไม่รวมเป็นตัวเดียว:** "ใครถนัดอะไรให้ทำเต็มที่อย่างนั้น ไม่แบ่งครึ่งๆ กลางๆ" — เคยลองแบบอื่นมาก่อน (โมเดลเดียวทำทุกอย่าง / ต่อกันแบบ crop-then-classify) แล้วมีปัญหา สรุปว่าแยกแล้วรวมผลด้วยพื้นที่ทับซ้อนดีที่สุด

**ทำไมต้องมี SAM ด้วย (ไม่ใช้ RT-DETR เปล่าๆ):** RT-DETR เป็น object detector แบบกล่องล้วนๆ ไม่มี segmentation head — ถ้าใช้พื้นที่กล่องเป็นพื้นที่ความเสียหายจะ**ประเมินเกินจริงเสมอ** เพราะความเสียหายจริงมักมีรูปทรงไม่สม่ำเสมอ/คดโค้ง กล่อง (ไม่ว่าตรงหรือเฉียง) ครอบพื้นที่เกินจริงอยู่ดี ต้องมี SAM มา refine เป็น mask จริงถึงจะวัดพื้นที่แม่นยำ — **ข้อแลกเปลี่ยนที่ยอมรับแล้ว:** ระบบช้าลง/ซับซ้อนขึ้นเพราะมี 2 โมเดล inference ต่อภาพ

**ทำไมไม่ใช้แผนเดิม (OBB+OBB จากรุ่นพี่):** แผนเก่าใช้ YOLO26-OBB (กรอบเฉียง) ทั้งฝั่งโครงสร้างและความเสียหาย จับคู่ด้วย IoU — เปลี่ยนเพราะกรอบเฉียงก็ยังเป็นกรอบสี่เหลี่ยม ไม่แก้ปัญหาพื้นที่เกินจริงของความเสียหายรูปทรงไม่สม่ำเสมอ (ดู `PROJECT_SUMMARY.md` หัวข้อ "สถาปัตยกรรมเดิม" สำหรับบั๊กที่เคยเจอ เช่น double-counting ชิ้นส่วนซ้ำ, mask ขยะจาก IoU ต่ำ)

## 3. สูตรคำนวณ T-BHI มาจากไหน น่าเชื่อถือแค่ไหน

**คำตอบสั้น:** ผสม 3 แหล่ง — **BMMS** (มาตรฐานราชการไทย ให้เกณฑ์ตัวเลข), **AASHTO/AASHTOWare BrM** (ให้โครงสร้างสูตรรวมคะแนนแบบ weighted-average ที่พิสูจน์แล้ว), **Pellegrino et al. 2011** (ตีพิมพ์วารสาร Q1 ให้น้ำหนักชิ้นส่วน+สูตรจัดลำดับเครือข่าย)

**จุดที่ต้องยอมรับตรงๆ ว่าเป็นของสังเคราะห์ใหม่ ไม่ใช่ยืมมาทั้งดุ้น:**
1. ค่าสัมประสิทธิ์ Chi ระดับ 4 และ 1 (0.83, 0.17) มาจาก linear interpolation ขยาย AASHTO 4 ระดับเป็น BMMS 6 ระดับ — ไม่มีในต้นฉบับ AASHTO ตรงๆ
2. Override Rule — ไม่ระบุแหล่งอ้างอิงชัดเจนในเอกสาร ดูเหมือนออกแบบเสริมเอง (มีฐานจากกฎ MIN ของ BMMS)
3. การผสม 3 มาตรฐานเป็นกรอบเดียว — ไม่เคยมีใครทำมาก่อน แต่ Pellegrino (2011) เองก็ใช้แนวทาง "ท้องถิ่นเป็นแกน + เชื่อมมาตรฐานสากล" แบบเดียวกันและผ่าน Q1 ได้ เป็นบรรทัดฐานรองรับ

**ถ้าถูกกดดันว่า "พิสูจน์ได้ไหมว่าผสมถูก":** ตอบตรงๆ ว่ายังพิสูจน์ทฤษฎีล้วนๆ ไม่ได้ 100% — พิสูจน์ได้แค่ความเทียบเท่าทางคณิตศาสตร์กับสูตรที่ใช้จริงอยู่แล้ว (AASHTOWare BrM) ส่วนการพิสูจน์ว่าใช้ได้ผลจริงต้องทดสอบกับสะพานจริงเทียบกับวิศวกรผู้เชี่ยวชาญ ซึ่งเป็นงานขั้นถัดไปที่ยังไม่ได้ทำ

รายละเอียดเต็ม + เลขหน้าอ้างอิงในไฟล์ต้นฉบับ: `ที่มาความน่าเชื่อถือของสูตร T-BHI.md`

## 4. เกณฑ์ตัวเลขความเสียหาย (รอยร้าวกว้างเท่าไหร่ = ระดับไหน) มาจากไหน

**คำตอบ:** จากคู่มือ **BMMS** ของกรมทางหลวง (DOH) — ตรวจสอบแล้วว่าตัวเลขจริง ไม่ได้แต่งขึ้น (เช็คกับไฟล์ต้นฉบับ 382 หน้า พบตรงกันที่หน้า 109-111 และอีกหลายจุด)

ตัวอย่าง: รอยร้าว RC — ดีพอใช้ <1.6mm, พอใช้ 1.6-3.2mm, ชำรุด 3.2-4.8mm, วิกฤต >4.8mm

**ทำไมใช้ BMMS ไม่ใช้ AASHTO ตรงๆ:** AASHTO เข้มกว่ามาก (รอยร้าว <0.3mm ถึงเรียก "ดี") ถ้าใช้ตัดสินสะพานไทยตรงๆ จะได้ผล "แย่เกินจริง" เทียบกับที่วิศวกร DOH คุ้นเคย

**ช่องว่างที่ยังต้องออกแบบเอง (ยังไม่มีคำตอบสำเร็จรูปจากเอกสารไหนเลย):**
- แปลง pixel/mask → หน่วยจริง (mm/cm) — ต้องใช้ GSD จากความสูงบิน+สเปกกล้อง หรือวัตถุอ้างอิงในภาพ
- น้ำหนักถ่วงระหว่างประเภทความเสียหาย — ไม่มี ใช้กฎ Multi-Path Distress (เอาที่แย่สุด) แทน
- บาง Condition State ไม่มีนิยามครบ (เช่น Honeycomb ไม่มีเกณฑ์ระดับ 2/1)

รายละเอียดเต็ม: `สรุปสาระสำคัญ เกณฑ์.pdf` (หัวข้อ 5, 7)

## 5. ทำไมเทรนโมเดลใหม่จากศูนย์ทุกรอบ ไม่ต่อยอดจาก checkpoint เดิม

**คำตอบสั้น:** "สิ่งที่โมเดลเรียนรู้อยู่ในข้อมูล ไม่ใช่ในไฟล์น้ำหนัก — ข้อมูลเดิมยังอยู่ครบ พอเทรนใหม่โมเดลก็เรียนของเดิมทั้งหมดซ้ำบวกข้อมูลใหม่ด้วย ไม่ได้เสียอะไรนอกจากเวลาเทรน 1-2 ชั่วโมง แต่แลกมาด้วยผลที่ทำซ้ำได้ ตรวจสอบได้ และเปรียบเทียบได้ทั้งด้านข้อมูล สถาปัตยกรรม และพารามิเตอร์"

**เหตุผลหลัก 5 ข้อ:** ทำซ้ำได้ / รู้ว่าอะไรทำให้ดีขึ้น (ตัวแปรเดียวคือข้อมูล) / เทียบสถาปัตยกรรมข้ามโมเดลได้ (RT-DETR vs YOLO) / ขยายชุดทดสอบได้ (ย้ายภาพ train→test ได้เพราะโมเดลใหม่ไม่เคยเห็น) / ไม่สะสมความผิดพลาดเก่า (label ที่เคยกำกวมไม่ฝังอยู่ในน้ำหนัก)

**ต้องตอบได้ด้วยว่าเมื่อไหร่ที่เทรนต่อจาก checkpoint ถึงถูก:** ข้อมูลใหญ่ระดับแสน-ล้านภาพจนเทรนใหม่ไม่ไหว / เข้าถึงข้อมูลเดิมไม่ได้แล้ว / เทรนค้างกลางทาง (ใช้ `resume=True`) / งานวิจัย continual learning โดยเฉพาะ — **ไม่มีข้อไหนตรงกับโปรเจกต์นี้** (ข้อมูลหลักร้อยถึงพันภาพ เทรนใหม่ชั่วโมงเดียว)

รายละเอียดเต็ม: `ทำไมเทรนจากตัวเปล่า.md`

## 6. วิธีจัดการ dataset (train/valid/test) เป็นยังไง

**กฎหลัก:** ภาพที่เคยอยู่ test/valid **ห้ามย้ายออกตลอดกาล** — ภาพใหม่ทั้งหมดไปลง train เท่านั้น จนกว่าจะ "reset" (=เติมภาพเข้า test/valid เพิ่ม ไม่ใช่สลับใหม่ทั้งหมด)

**ทำไมต้องล็อกแบบนี้:** ถ้าสลับ valid/test ใหม่ทุกรอบ (ก) เทียบ mAP/precision/recall ข้ามรอบไม่ได้เลยเพราะคนละข้อสอบ (ข) เสี่ยงภาพที่เคยเทรนไปแล้วหลุดเข้า test ทำให้คะแนนสูงเกินจริงแบบไม่รู้ตัว

**เงื่อนไขที่ต้อง "เติม test" (ไม่ใช่แค่เพิ่ม train เฉยๆ):**
- คลาสไหนมีตัวอย่างใน test ต่ำกว่า ~10 → วัดผลไม่น่าเชื่อถือ (รอบ 1 เจอจริง: Honeycomb 3, Spalling 4, Rust_Stain 5 ตัวอย่าง)
- คลาสที่เคยบางสะสมภาพเพิ่มมามากแล้ว
- มีภาพลักษณะใหม่เข้ามา (ภาพโดรนสะพานจริง ต่างจาก close-up ที่ใช้อยู่ตอนนี้)

**แยกให้ถูก 2 ปัญหาที่มักสับสนกัน:** "คลาสทำได้แย่" (mAP ต่ำ) → ต้องเติม**ภาพเข้า train** / "คลาสบางใน test" (ตัวอย่างน้อย) → ต้อง**ย้ายภาพจาก train เข้า test** เป็นคนละปัญหา คนละวิธีแก้

**ทำไมย้ายภาพ train→test ได้อย่างปลอดภัย:** เพราะเทรนจากตัวเปล่าทุกรอบ (ข้อ 5) โมเดลใหม่ไม่เคยเห็นภาพที่เพิ่งย้ายมา — ถ้าวันไหนกลับไปเทรนต่อจาก checkpoint ต้องหยุดวิธีนี้ทันที

รายละเอียดเต็ม: `work_diary.md`, memory `test_set_grows_never_shuffles.md`

## 7. ผลการเทรนตอนนี้เป็นยังไง มีจุดอ่อนตรงไหน

**สถานะ:** เทรนไปแล้ว 1 รอบเต็ม (RT-DETR, 385 ภาพจาก Roboflow/public dataset) mAP@0.5 รวม = 0.195 — **กำลังเปลี่ยนแผนใหม่** (เทรนจากศูนย์, แยก label ทีละโมเดล, export YOLO ตรงๆ) ยังไม่มีผลรอบใหม่ ดูสถานะสดที่ `work_diary.md`

**การวิเคราะห์จุดอ่อนที่ทำไปแล้ว (สำคัญ ใช้ตอบคำถาม "ทำไมบางคลาสแย่"):**
- Crack (mAP 0.028) และ Efflorescence (0.074) แย่สุด — **ไม่ใช่เพราะข้อมูลน้อย** (Crack มี 134 ตัวอย่าง มากกว่า Rust_Stain ที่ดีที่สุด (มี 56 ตัวอย่าง) ถึง 2 เท่า) เป็นเพราะ (ก) Crack บางเกินกว่าจะเห็นชัดที่ความละเอียด 640px (ข) เคย label กำกวมระหว่าง Spalling/Efflorescence (แก้แล้วในรอบ 2)
- **ข้อจำกัดสำคัญที่ต้องพูดตรงๆ:** ชุดข้อมูลปัจจุบันมาจาก public dataset ต่างประเทศ (close-up) **ยังไม่มีภาพสะพานจริงของโปรเจกต์เลย** — mAP ที่วัดได้บอกแค่ว่าโมเดลเก่งกับภาพแบบ public dataset แค่ไหน ยังไม่พิสูจน์ว่าใช้งานจริงกับภาพโดรนสะพานไทยได้ดีแค่ไหน — ต้องเอาภาพสะพานจริงเข้า test ก่อนสรุปผลลงรายงาน
- แบ่ง train/valid/test รอบแรกใช้ค่า default ของ Roboflow ได้ 82/11/7 (ไม่ใช่ 60/25/15 ตามที่ตั้งใจ) ทำให้ test เล็กเกินไปตั้งแต่ต้น — บทเรียนคือต้องตั้งสัดส่วนเองเสมอ

**เครื่องมือที่มีให้วิเคราะห์อัตโนมัติ:** `analyze_results.py` — รันแล้วได้ mAP รายคลาส + จำนวนตัวอย่างทุก split + คำเตือนว่าคลาสไหนต้องเติม train/test

รายละเอียดเต็ม: `training_log.md`

## 8. ทำไมยังไม่มีโค้ด pipeline จริง (main.py ฯลฯ)

**คำตอบ:** จงใจเว้นไว้ก่อน เพราะต้องอ่านมาตรฐาน/เกณฑ์ขนาดความเสียหายให้ครบก่อน (ใช้ตัดสิน threshold ในการแปลง pixel mask → ระดับความเสียหาย 0-5) ถ้าเขียนตอนนี้เสี่ยงต้องรื้อทิ้งทำใหม่หลังอ่านมาตรฐานเสร็จ — ตอนนี้อ่านมาตรฐานเสร็จแล้ว (ข้อ 3-4) แต่ยังติดขั้นเตรียม dataset/เทรนโมเดลให้เสร็จก่อน

**สิ่งที่ยังไม่มีคำตอบสำเร็จรูป ต้องออกแบบเองตอนเขียนโค้ดจริง:**
- สูตรแปลง pixel → หน่วยจริง (mm/cm)
- วิธี match ผลจาก RT-DETR (กรอบ) กับ mask โครงสร้างจาก YOLO-seg ด้วยพื้นที่ทับซ้อน (ต้องออกแบบใหม่ เพราะ RT-DETR output คนละแบบกับ OBB เดิม)
- หน่วยของ qe (ปริมาณชิ้นส่วน) ในสูตร T-BHI — นับเป็นจำนวนชิ้นหรือความยาว/พื้นที่ ยังไม่ระบุ

## 9. Roadmap ที่เหลือ (ถ้าถูกถามว่า "ต่อไปจะทำอะไร")

1. label ความเสียหายเพิ่ม (Crack/Efflorescence) ในโปรเจกต์ Object Detection แยกต่างหาก → export YOLO
2. เทรน RT-DETR รอบใหม่จากศูนย์ ด้วย dataset ที่จัดระเบียบใหม่
3. เริ่ม label โครงสร้าง (Girder/Pier/Pier Cap) ผ่าน LabelMe/Roboflow สำหรับภาพโดรนจริง (`Bridge/`) — ยังไม่ได้เริ่มเลย
4. เทรน YOLO-seg สำหรับโครงสร้าง
5. เอาภาพสะพานจริงเข้า test (ไม่ใช่แค่ train) เพื่อให้ผลวัดได้น่าเชื่อถือสำหรับรายงาน
6. ทดลองเปรียบเทียบสถาปัตยกรรม (RT-DETR vs YOLO) บนข้อมูลชุดเดียวกัน — การทดลองที่มีค่าสำหรับรายงาน
7. เขียน `damage_rules.py`, `bridge_health.py`, `element_lookup.py`, `main.py`, `vision.py` จริง
8. ทดสอบ pipeline เต็มกับภาพจริงจาก `Bridge/`
