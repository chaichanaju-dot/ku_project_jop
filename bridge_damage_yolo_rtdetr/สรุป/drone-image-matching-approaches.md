# แนวทางการรวมภาพโดรน + ระบุตำแหน่ง Defect (Overlapping Images)

## บริบทงาน
- ถ่ายภาพโครงสร้าง (คาน/เสาคอนกรีต) ด้วยโดรน แบบเรียงต่อกันมี overlap
- มี 2 โมเดล detection: (1) ตรวจจับโครงสร้าง (structure) (2) ตรวจจับความเสียหาย (damage: crack, spalling, honeycomb, porous defect)
- ปัญหา: ภาพเดียวกัน/defect เดียวกัน อาจถูกตรวจจับซ้ำในหลายเฟรมที่ overlap กัน ต้องหาวิธี dedup
- ปัญหาที่เจอจริง: ลอง stitch ด้วย feature matching (OpenCV Stitcher) แล้วภาพเพี้ยน/ตัดบางส่วนออก (เช่นเสาหาย) เพราะพื้นผิวคอนกรีตเรียบ ไม่มี texture ให้จับจุดเด่นได้ดีพอ

---

## ทำไมต้อง "รวมภาพ" หลังตรวจจับ (สรุปเข้าใจง่ายก่อนอ่านรายละเอียด)

**เหตุผลข้อเดียว: กันนับความเสียหายจุดเดียวกันซ้ำ**

ภาพ overlap กัน แปลว่ารอยร้าวเดียวกันอาจติดอยู่ในหลายภาพพร้อมกัน (เช่นภาพ 5, 6, 7) ถ้าไม่ทำอะไรเลย รันตรวจจับทีละภาพแล้วรวมผลตรงๆ จะได้ **รอยร้าวจริง 1 จุด ถูกนับเป็น 3 จุด** → เอาไปคิดสูตร T-BHI จะทำให้สะพานดูเสียหายเกินจริง (คะแนนสุขภาพต่ำกว่าความจริง)

**"รวมภาพ" มี 2 ความหมายที่ต้องแยกให้ออก:**

| | ทำอะไร | จำเป็นไหม |
|---|---|---|
| รวม **"พิกัด"** ให้อยู่ระบบเดียวกัน (เส้นทาง A) | แปลงตำแหน่งที่เจอในแต่ละภาพให้เทียบกันได้ ไม่ต้องเอาพิกเซลมาต่อกันจริง | จำเป็น เพื่อเช็คว่าซ้ำหรือไม่ |
| รวม **"พิกเซล"** เป็นภาพเดียวจริงๆ (เส้นทาง B) | เอาภาพมาต่อกันจริงเป็นภาพ mosaic ใหญ่ | แค่ทางเลือก (ได้ภาพสวยไว้ทำรายงานด้วย) |

**Dedup (de-duplication) คืออะไร:** ขั้นตอนเช็คว่า detection ที่เจอในภาพต่างกันอันไหนจริงๆ เป็นความเสียหายจุดเดียวกัน (แค่ถูกถ่ายติดซ้ำหลายเฟรม) แล้วรวมให้เหลือรายการเดียว — เช่น เจอ crack 3 รายการจากภาพ 5,6,7 → หลัง dedup เหลือ 1 รายการ (รู้ว่าเป็นจุดเดียวกัน เจอซ้ำ 3 เฟรม)

**เรื่องที่ต้องแยกให้ชัด:** การคำนวณ Chi/EHI/T-BHI **ไม่สนใจว่าภาพถูกรวมหรือไม่** สนใจแค่ "ลิสต์ความเสียหายที่ dedup แล้ว พร้อมขนาดจริง" — จะได้ลิสต์นี้มาจากภาพเดียวที่ต่อกันแล้ว (เส้นทาง B) หรือจากภาพแยกที่เช็คไม่ให้ซ้ำแล้ว (เส้นทาง A) ผลลัพธ์ที่ป้อนเข้าสูตรเหมือนกันเป๊ะ

## Walkthrough เต็ม ตั้งแต่ถ่ายภาพจนได้ T-BHI (เทียบ 2 เส้นทางคู่กัน)

ตัวอย่าง: ถ่ายภาพเสาต้นเดียว 19 ภาพเรียงต่อกัน (overlap กัน)

### เส้นทาง A (ไม่ต่อภาพ — ตรวจจับแยกแต่ละภาพก่อน)

```
1. ถ่ายภาพ 19 ภาพ — แต่ละภาพมี GPS + มุมกล้อง (yaw/pitch/roll) ติดมา
2. ตรวจจับทีละภาพ (ทั้ง 19 ภาพแยกกัน) → ได้ตำแหน่งความเสียหายเป็น pixel ของแต่ละภาพ
3. แปลง pixel → พิกัดจริงบนเสา (ใช้ GPS+มุมกล้อง, ฟังก์ชัน pixel_to_world) → ทุกจุดพูด "ภาษาเดียวกัน" แล้ว
4. Dedup: เทียบพิกัดจริง จุดไหนใกล้กันมาก = จุดเดียวกัน → เหลือรายการไม่ซ้ำ
5. วัดขนาดจริง (mm/cm²) ของแต่ละจุดที่ไม่ซ้ำ (ได้มาพร้อมขั้น 3 เลย ไม่ต้องคำนวณ GSD แยก)
6. เทียบขนาดกับตาราง BMMS → ได้ระดับ 0-5 → ได้ค่า Chi
7. จับคู่แต่ละจุดกับชิ้นส่วนโครงสร้าง (คาน/เสาต้นไหน) จากโมเดลโครงสร้าง
8. คำนวณ EHI ต่อชิ้นส่วน: EHI_e = Σ(Chi × ye_i) × 100
9. รวมทุกชิ้นส่วน: T-BHI = Σ(qe·We·EHIe) / Σ(qe·We)   → ได้คะแนน T-BHI ✅
```

### เส้นทาง B (ต่อภาพก่อนด้วย Pix4D/ODM แล้วตรวจจับทีเดียว)

```
1. ถ่ายภาพ 19 ภาพ — เหมือนกัน
2. เอาเข้า Pix4D/ODM ต่อภาพทั้งหมดเป็นภาพเดียว (orthomosaic) — ได้ GSD (สเกลจริง) มาด้วยในตัว
3. ตรวจจับบนภาพ mosaic ภาพเดียว (ครั้งเดียวจบ ไม่ต้องรัน 19 ครั้ง)
4. ไม่ต้อง dedup เลย — เป็นภาพเดียว จุดไหนก็เจอแค่ครั้งเดียวอยู่แล้ว
5. วัดขนาดจริง (mm/cm²) โดยใช้ GSD ที่ซอฟต์แวร์ให้มา
6. เทียบขนาดกับตาราง BMMS → ได้ระดับ 0-5 → ได้ค่า Chi
7. จับคู่แต่ละจุดกับชิ้นส่วนโครงสร้าง (คาน/เสาต้นไหน)
8. คำนวณ EHI ต่อชิ้นส่วน: EHI_e = Σ(Chi × ye_i) × 100
9. รวมทุกชิ้นส่วน: T-BHI = Σ(qe·We·EHIe) / Σ(qe·We)   → ได้คะแนน T-BHI ✅
```

**ต่างกันแค่ขั้น 2-4 เท่านั้น ขั้น 5-9 เหมือนกันเป๊ะทั้งคู่ — ปลายทางเดียวกันคือตัวเลข T-BHI**

| | เส้นทาง A | เส้นทาง B |
|---|---|---|
| ตรวจจับกี่ครั้ง | 19 ครั้ง (ทีละภาพ) | 1 ครั้ง (ภาพ mosaic) |
| ต้อง dedup เอง | ต้อง (เขียนโค้ดเพิ่ม) | ไม่ต้อง (ภาพเดียวอยู่แล้ว) |
| เสี่ยงอะไร | เขียนโค้ดเพิ่มเอง | ต่อภาพเพี้ยน (ปัญหาที่เจอจริงกับ Pix4D พื้นผิวเรียบ) |

## แบบที่ 1: Feature Matching (SIFT/ORB + Homography)

**หลักการ:** หาจุดเด่น (keypoints) ในแต่ละภาพ จับคู่จุดที่เหมือนกันระหว่างภาพที่ overlap กัน คำนวณ homography matrix (H) เพื่อรู้ว่าต้องบิด/เลื่อนภาพยังไงให้ซ้อนกันพอดี

**เครื่องมือ:** `cv2.Stitcher_create()` (สำเร็จรูป) หรือเขียนเอง (`cv2.SIFT_create()` / `cv2.ORB_create()` + `cv2.findHomography()`)

**ข้อดี:**
- ไม่ต้องมี GPS/IMU
- ใช้ OpenCV ได้เลย ไม่ต้องพึ่งซอฟต์แวร์ภายนอก

**ข้อเสีย:**
- ถ้าพื้นผิวเรียบ ไม่มี texture ชัดเจน (คอนกรีตเนื้อเดียวกันยาวๆ) → จับจุดเด่นไม่พอ หรือจับคู่ผิด → stitch เพี้ยน/ภาพหาย (ปัญหาที่เจอจริง)
- `cv2.Stitcher_create()` จะตัดภาพที่ต่อไม่ติดทิ้งไปเงียบๆ (เช็คได้จาก `status` ที่ return)
- ถ้าต่อภาพแบบสะสม (pairwise ต่อเนื่อง) error จะสะสมมากขึ้นเรื่อยๆ ยิ่งภาพเยอะยิ่งเพี้ยน (ต้องใช้ bundle adjustment ช่วย)

**เหมาะกับ:** พื้นผิวที่มี texture ชัดเจน (รอยแตกเยอะ คราบเยอะ ไม่เรียบ)

```python
stitcher = cv2.Stitcher_create(cv2.Stitcher_PANORAMA)
status, result = stitcher.stitch(images)
# status != 0 คือ error, ภาพบางส่วนจะถูก drop ไปเงียบๆ
```

## แบบที่ 2: Photogrammetry Software สำเร็จรูป (Pix4D / Agisoft / ODM)

**หลักการ:** ใช้หลัก feature matching เดียวกับแบบที่ 1 แต่มี bundle adjustment ช่วยลด error สะสม ออกผลเป็น 3D model + orthomosaic

**เครื่องมือ:** Pix4Dmapper, Agisoft Metashape, OpenDroneMap (ฟรี)

**ปัญหาที่เจอจริง (Pix4D):**
- Template เริ่มต้น "3D Maps" ออกแบบมาสำหรับถ่ายภาพแบบ nadir (มองลงพื้นตรงๆ) เช่นงานแผนที่/เกษตร
- งานถ่ายเสา/คาน (พื้นผิวแนวตั้ง, มุมกล้องเอียงเข้าหาโครงสร้าง) ไม่เหมาะกับ 3D Maps → ทำให้ภาพเพี้ยน/ตัดเสาออก

**วิธีแก้:**
1. เปลี่ยน Processing Template จาก **3D Maps → 3D Models** (Process > Processing Options > Templates) — ออกแบบมาสำหรับภาพแบบ oblique/terrestrial โดยเฉพาะ เหมาะกับโมเดล 3 มิติของอาคาร/งานตรวจสอบ (inspection)
2. ใช้เครื่องมือ **Orthoplane** เพิ่มเติม เพื่อสร้าง orthomosaic ของพื้นผิวแนวตั้ง (ปกติ Pix4D สร้าง ortho ขนานกับพื้นราบ X,Y เท่านั้น ถ้าไม่ใช้ Orthoplane ผิวแนวตั้งจะไม่ถูกจัดการถูกต้อง)
3. ถ่ายภาพแบบ oblique/terrestrial (เอียงกล้องเข้าหาเสา) ไม่ใช่ nadir, แนะนำถ่ายทุก 5-10 องศา ให้ overlap เพียงพอ

**ข้อดี:**
- ไม่ต้องเขียนโค้ด stitching เอง
- แม่นยำกว่าแบบ 1 เพราะมี bundle adjustment แก้ error สะสม
- ได้ orthomosaic/3D model ไว้ทำรายงานด้วย

**ข้อเสีย:**
- พึ่งซอฟต์แวร์ภายนอก (มีค่าใช้จ่าย ยกเว้น ODM)
- ยังพึ่ง texture ของภาพอยู่ดี (แม้จะทนทานกว่าแบบ 1)
- ต้องเลือก template/setting ให้ตรงกับลักษณะงาน (nadir vs oblique/vertical) ไม่งั้นผลลัพธ์เพี้ยน

**เหมาะกับ:** ต้องการภาพ mosaic/3D model ไว้ทำรายงานหรือ presentation ด้วย ไม่ใช่แค่ตำแหน่ง defect

## แบบที่ 3: GPS + Gimbal Angle Projection (ไม่ต้อง stitch ภาพ)

**หลักการ:** ไม่ต่อภาพให้เป็นภาพเดียวก่อน — ตรวจจับ defect บนแต่ละภาพดิบแยกกัน แล้วใช้ตำแหน่ง GPS ของกล้อง + มุมกิมบอล (yaw/pitch/roll) คำนวณว่าแต่ละ pixel/bbox ตกอยู่ที่พิกัดจริงตรงไหนบนพื้นผิวโครงสร้าง จากนั้น dedup ด้วยระยะห่างจริง (เมตร) แทนที่จะเทียบ pixel

**ข้อมูลที่ต้องมี:**
- GPS log (lat, lon, altitude) ของกล้อง ณ ตอนถ่ายแต่ละภาพ
- Gimbal angle (yaw, pitch, roll) — บางรุ่นอยู่ใน EXIF, บางรุ่นต้องดูไฟล์ log แยก (เช่น DJI `.SRT`)
- ระยะห่างจากกล้องถึงพื้นผิว (ถ้าบินระยะคงที่ ใช้ค่าคงที่ได้; แม่นกว่าถ้ามี LiDAR/depth sensor)

**ข้อดี:**
- ไม่ต้องพึ่ง texture ของภาพเลย → แก้ปัญหาพื้นผิวเรียบ/เพี้ยนได้ตรงจุด
- ไม่มี error สะสมแบบ pairwise stitching (ทุกภาพคำนวณอิสระจาก GPS ตรงๆ)
- Scale ได้ดีกับจำนวนภาพเยอะๆ

**ข้อเสีย:**
- ต้องมี GPS/gimbal log ที่แม่นยำ (ยิ่งดีถ้าเป็น RTK GPS)
- ถ้าไม่มีระยะห่างจากพื้นผิวที่แม่นยำ ความแม่นยำของพิกัดจะลดลง
- ไม่ได้ภาพ mosaic รวมไว้ดูภาพรวม (ต้องทำแยกถ้าต้องการ)

**เหมาะกับ:** พื้นผิวเรียบ/ไม่มี texture (คอนกรีตเนื้อเดียวกัน) ที่ feature matching มีปัญหา, ต้องการแค่ตำแหน่งความเสียหายแม่นๆ ไม่สนใจภาพรวม

```python
def pixel_to_world(px, py, img_w, img_h, camera_pos, yaw, pitch, roll,
                     fov_h, fov_w, distance_to_surface):
    # แปลง pixel -> มุมเบี่ยงจากกึ่งกลางภาพ -> ray direction -> หมุนตาม yaw/pitch/roll
    # -> ยิง ray จากตำแหน่งกล้องไปจนถึงระยะที่กำหนด (ชนพื้นผิว)
    ...
    return world_point  # พิกัดจริงบนโครงสร้าง (x, y, z)
```

# เส้นทาง A: แบบ 1 หรือ 3 — ตรวจจับก่อน แล้วรวมทีหลัง

ใช้เมื่อ**ไม่**ผ่านซอฟต์แวร์สำเร็จรูปที่ต่อภาพให้เสร็จ (ตรวจจับบนภาพดิบทีละใบ)

1. **ตรวจจับแยกทีละภาพ** — รันโมเดลโครงสร้าง + โมเดลความเสียหาย บนภาพดิบทั้ง 19 ภาพแยกกัน ได้ list ของ detection (bbox, class, confidence) ต่อภาพ ยังไม่สนใจเรื่องซ้ำ
2. **แปลงพิกัดของแต่ละ detection ให้อยู่ในระบบเดียวกัน** — ใช้ homography (แบบ 1) หรือ GPS+gimbal projection (แบบ 3) แปลง bbox pixel เป็นพิกัดโลกจริง/canvas กลาง เพื่อให้เทียบตำแหน่งข้ามภาพได้
3. **Deduplication** — เทียบพิกัดโลกจริงของทุก detection ถ้าใกล้กันเกิน threshold (IoU หรือระยะทาง) ถือว่าเป็น defect เดียวกันที่ถูกถ่ายซ้ำหลายเฟรม รวมเป็นรายการเดียว เลือก confidence สูงสุดเป็นตัวแทน บันทึกจำนวนเฟรมที่เจอไว้ด้วย (ยิ่งเจอหลายเฟรมยิ่งมั่นใจว่าไม่ใช่ false positive)
4. **คำนวณขนาดจริงและระดับความเสียหาย** — ทำหลัง dedup เสร็จ (คำนวณครั้งเดียวต่อ defect ไม่ใช่ต่อเฟรม)
   - หา **GSD (Ground Sampling Distance)** เอง = ระยะจริงที่ 1 pixel แทน (cm/pixel): `GSD = (sensor_width × ระยะห่างกล้องถึงผิว) / (focal_length × ความกว้างภาพเป็น pixel)`
     - แบบ 3: มีพิกัดโลกจริงอยู่แล้ว ใช้ขนาด bbox ในพิกัดโลกได้เลย ไม่ต้องคำนวณ GSD แยก
     - แบบ 1: ต้องรู้ระยะห่างกล้องถึงผิวจริง มาคำนวณ GSD เอง เพราะ homography อย่างเดียวไม่มี scale จริง
   - แปลงขนาด defect เป็นหน่วยจริง: **Spalling/Honeycomb** คำนวณพื้นที่จาก mask/bbox × GSD², **Crack** วัดความยาวตาม contour ของรอยร้าว + ความกว้างเฉลี่ย/สูงสุด (ไม่ใช้ bbox ตรงๆ เพราะเส้นเฉียงจะให้ค่าบิดเบือน)
   - เทียบขนาดที่วัดได้กับเกณฑ์ระดับความรุนแรง (severity threshold) ตามมาตรฐานที่ใช้งานจริง (เช่น ACI หรือมาตรฐานภายในองค์กร) — ยังไม่ได้ใส่ตัวเลขตายตัวในเอกสารนี้
5. **จับคู่ defect กับชิ้นส่วนโครงสร้าง** — เทียบตำแหน่ง defect (หลัง dedup+วัดขนาดแล้ว) กับผลของโมเดลโครงสร้าง เพื่อระบุว่าอยู่บนคาน/เสาตัวไหน ตำแหน่งไหน (เช่น "รอยร้าวกว้าง 2.3 มม. ระดับปานกลาง ที่คาน B-12 กึ่งกลางช่วง")
6. **(ถ้าต้องการ) ทำภาพรวมไว้แสดงผล** — stitch ภาพแยกต่างหากเป็นขั้นตอนคนละงานจากการตรวจจับ (ไม่กระทบความแม่นยำ) แล้ววาด marker ตำแหน่ง defect ที่ dedup+วัดขนาดแล้วทับลงไป

# เส้นทาง B: แบบ 2 — ต่อภาพก่อนด้วยซอฟต์แวร์สำเร็จรูป แล้วตรวจจับทีเดียว

ใช้ Pix4D/Agisoft/ODM ต่อภาพเป็น orthomosaic ก่อน แล้วค่อยตรวจจับบนภาพเดียวนั้น (ต้องตั้ง Template เป็น **3D Models** + ใช้ **Orthoplane** สำหรับพื้นผิวแนวตั้งอย่างคาน/เสา ตามที่เจอปัญหาจริงมาแล้ว)

1. **ต่อภาพด้วยซอฟต์แวร์** — อัปโหลดภาพดิบทั้งหมดเข้า Pix4D/ODM ให้ทำ feature matching + bundle adjustment ให้อัตโนมัติ ผลลัพธ์คือ **orthomosaic ภาพเดียว** ที่ทุก pixel มีพิกัดจริงกำกับแล้ว พร้อม **GSD ให้มาในตัว** (ไม่ต้องคำนวณเอง)
2. **ตรวจจับบนภาพ mosaic ภาพเดียว** — รันโมเดลโครงสร้าง + โมเดลความเสียหาย บนภาพ mosaic ทีเดียว ไม่ต้องรันทีละภาพย่อย
3. **ไม่ต้องทำ Deduplication** — เพราะเป็นภาพเดียวแล้ว defect แต่ละจุดปรากฏแค่ครั้งเดียว (ขั้นตอนนี้ถูกข้ามไปโดยอัตโนมัติ)
4. **คำนวณขนาดจริงและระดับความเสียหาย** — ใช้ GSD ที่ซอฟต์แวร์ให้มาแล้ว (ไม่ต้องคำนวณ GSD เอง) แปลงขนาด defect เป็นหน่วยจริงแบบเดียวกับเส้นทาง A ขั้นที่ 4 แล้วเทียบกับเกณฑ์ severity เหมือนกัน
5. **จับคู่ defect กับชิ้นส่วนโครงสร้าง** — เหมือนเส้นทาง A ขั้นที่ 5 ทุกประการ ยังต้องทำเองเสมอไม่ว่าจะเลือกเส้นทางไหน
6. **ภาพรวมสำหรับแสดงผล** — ได้อยู่แล้วจากขั้นตอนที่ 1 (ตัว orthomosaic เอง) ไม่ต้องทำเพิ่ม

## นิยามประเภทความเสียหายคอนกรีต (สำหรับ label โมเดล damage detection)

### Crack (รอยร้าว)
- เนื้อคอนกรีตยังคงเป็นผืนเดียวกัน มีแค่เส้นแตกผ่าน ไม่มีชิ้นส่วนหลุดหายไป
- ชนิดย่อย:
  - **Map/Pattern cracking** — รอยแตกบางสานกันเป็นร่างแห มักเกิดจากการหดตัวขณะบ่ม/บ่มไม่ดี
  - **Linear/wide crack** — รอยร้าวเปิดกว้าง ต่อเนื่องเป็นเส้นตรงหรือเฉียง มักเกิดจากสนิมเหล็กเสริมขยายตัวดันจากด้านใน (มีคราบสนิมไหลตามแนวรอยร้าวร่วมด้วย)
  - **Arc/ring cracking** — รอยร้าวโค้งเป็นวง มักเป็นสัญญาณเริ่มต้นก่อนเกิด spalling เป็นแผ่นวงกลม (จุดกำเนิดความเค้นอยู่กลางวง เช่นเหล็กเสริมที่เริ่มเป็นสนิม)

### Spalling (การกระเทาะ)
- เนื้อคอนกรีตผิวหน้าหลุดล่อนออกมาเป็นชิ้น/แผ่น/ก้อน ทิ้งรอยเป็นแอ่งหรือหลุม ขอบไม่เรียบ
- มักเผยให้เห็นมวลรวม (หิน/กรวด) หรือเหล็กเสริมด้านใน
- สาเหตุหลัก: สนิมเหล็กเสริมขยายตัว (ปริมาตรมากกว่าเหล็กเดิม 2-6 เท่า) ดันคอนกรีตจนแตกและหลุด, หรือ freeze-thaw, แรงกระแทก, ไฟไหม้
- **ระยะก่อนกระเทาะ (Delamination/Incipient spalling)** — ผิวคอนกรีตนูนขึ้นมาจากผิวปกติ (คลำ/มองเห็นได้) เพราะคอนกรีตกับเนื้อด้านในเริ่มแยกชั้นแต่ยังไม่หลุดขาด เช็คได้ด้วยการเคาะเบาๆ ถ้าเสียงกลวง (hollow) แปลว่าแยกชั้นแล้ว พร้อมหลุดเมื่อไหร่ก็ได้
- เกณฑ์แยกจาก crack: ต้อง**เห็นเนื้อคอนกรีตหลุดออกจริง** (เป็นหลุม/แอ่ง/ขอบปิดล้อมไม่สม่ำเสมอ) ไม่ใช่แค่เส้นแตก

### Efflorescence / Rust staining (คราบตกตะกอน/คราบสนิม)
- คราบขาว-เทาที่ไหลย้อย เกิดจากน้ำชะแคลเซียมไฮดรอกไซด์ในคอนกรีตออกมาตกผลึกเมื่อสัมผัสอากาศ — ไม่ทำให้โครงสร้างอ่อนแอโดยตรง แต่เป็นสัญญาณว่ามีน้ำซึมผ่านต่อเนื่อง
- คราบสีน้ำตาลส้ม = สนิมเหล็กเสริมที่ละลายไหลออกมาตามรอยแตก/รอยรั่ว เป็นสัญญาณว่าน้ำซึมถึงเหล็กเสริมแล้ว

### Porous defect (ผิวพรุน / bug holes)
- รูพรุนเล็กๆ (เท่าหัวเข็มหมุดถึงเมล็ดถั่ว) กระจายที่ผิวหน้าเท่านั้น
- สาเหตุ: ฟองอากาศติดค้างตอนเท ไม่ได้เขย่า/จี้ให้อากาศออกพอ
- ความรุนแรง: เบา ส่วนใหญ่เป็นปัญหาความสวยงามของผิว ไม่กระทบกำลังโครงสร้างมาก (มวลรวมยังประสานกันแน่นด้านใน)

### Honeycomb (รังผึ้ง)
- ช่องว่างขนาดใหญ่เป็นโพรง เห็นมวลรวม (หิน/กรวด) แยกออกจากกันชัดเจน ไม่มีปูนซีเมนต์เพสต์ห่อหุ้ม
- สาเหตุ: ปูนไหลเข้าแบบหล่อไม่ทั่วถึง (มุมอับ/เหล็กเสริมหนาแน่น), ส่วนผสมผิดสัดส่วน, เขย่าไม่พอ, เทสูงเกินจนมวลรวมแยกตัว
- ความรุนแรง: หนัก กำลังรับแรงอัดลดลงมาก เป็นช่องทางให้น้ำ/อากาศเข้าถึงเหล็กเสริมโดยตรง ต้องซ่อมด้วย patch repair/grouting ไม่ใช่แค่ฉาบผิว

### ตารางเทียบเกณฑ์แยก Crack vs Spalling

| เกณฑ์ | Crack | Spalling |
|---|---|---|
| เนื้อคอนกรีตหลุดออกจริงหรือไม่ | ไม่ (ยังติดกันเป็นผืนเดียว) | ใช่ (หลุดเป็นชิ้น/แผ่น/ก้อน) |
| ขอบเขตของรอยเสียหาย | เส้นบาง/เส้นตรง | รูปร่างปิดล้อมไม่สม่ำเสมอ (คล้ายหลุม/แอ่ง) |
| เห็นมวลรวม/เหล็กเสริมโผล่ | ไม่ | มักเห็น |
| ผิวนูนขึ้นจากระดับปกติ | ไม่ | อาจนูน (สัญญาณ delamination ก่อนหลุด) |

## สถานะปัญหาปัจจุบัน
- ลองแบบ 1 (OpenCV Stitcher) แล้วภาพเพี้ยน/ไม่ครบ (พื้นผิวคอนกรีตเรียบเกินไป)
- ลองแบบ 2 (Pix4D) แล้วเสาถูกตัดออก — สาเหตุคือ template ผิด (3D Maps แทนที่จะเป็น 3D Models) + ไม่ได้ใช้ Orthoplane
- ยังไม่ได้ทดลองแบบ 3 (GPS-based) — ต้องเช็คก่อนว่าโดรนที่ใช้มี GPS/gimbal log ให้ดึงข้อมูลหรือไม่
