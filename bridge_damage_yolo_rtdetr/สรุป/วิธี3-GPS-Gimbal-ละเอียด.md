# วิธีที่ 3 (GPS + Gimbal Projection) แบบละเอียดเต็ม — ตั้งแต่ถ่ายภาพจนถึง T-BHI

> ไฟล์นี้แยกจาก `drone-image-matching-approaches.md` เพราะเจาะจงเฉพาะวิธีที่ 3 แบบละเอียดมาก — ใช้ตอนต้องอธิบาย/พิสูจน์ให้อาจารย์ฟัง หรือตอนเริ่มเขียนโค้ดจริง
> **สถานะล่าสุด (2026-09-25): ทดสอบกับข้อมูลจริงแล้ว 3 ครั้ง — พบว่าใช้งานไม่ได้กับ GPS ที่มีอยู่ตอนนี้ (ดูสาเหตุด้านล่าง)** ดู `work_diary.md` สำหรับสถานะโปรเจกต์โดยรวม

## สรุปสั้นที่สุด (อ่านส่วนนี้ก่อน)

**หลักการ:** เอา pixel **ตำแหน่งไหนก็ได้ในภาพ** (จะเป็นความเสียหาย จุดสังเกต หรืออะไรก็ตาม — สูตรไม่สนใจว่าคือจุดอะไร) → แปลงเป็นมุมเบี่ยงจากกึ่งกลางภาพ (ใช้ FOV กล้อง) → รวมกับมุมกิมบอลจริงและระยะห่างกล้อง↔ผิว → คำนวณตำแหน่งจริง 3 มิติบนโครงสร้าง → วัดระยะห่างระหว่าง 2 ตำแหน่งได้ขนาดจริง (mm)

ตอนพิสูจน์สูตร (หัวข้อ "สรุปผลการทดลอง" ด้านล่าง) ใช้จุดสังเกตทั่วไป (ไม่ใช่ความเสียหาย) เพราะแค่ต้องการทดสอบว่าสูตรแม่นไหม — ไม่ต้องรอโมเดล AI ตรวจจับความเสียหายให้เสร็จก่อน พอสูตรพิสูจน์แล้วว่าแม่น ค่อยเอาไปใช้กับ pixel ของความเสียหายจริงตอนใช้งานจริง (ฟังก์ชันเดียวกันเป๊ะ)

**ตัวแปรสำคัญที่สุด 3 ตัว:**
1. **FOV กล้อง** (จาก Focal Length 35mm equivalent) — บอกว่ากล้องมองเห็นมุมกว้างแค่ไหน
2. **มุมกิมบอล (Gimbal Pitch/Yaw/Roll)** — บอกทิศทางที่กล้องเล็งจริง ณ ขณะถ่าย
3. **ระยะห่างจากกล้องถึงผิวโครงสร้าง** — ตัวแปรที่**ไม่มีใน EXIF ให้เลย** ต้องหาเพิ่มเอง (นี่คือจุดที่ทำให้การทดลองพลาด — อ่านด้านล่าง)

**ทำไมการทดลองพลาด:** ทดสอบกับข้อมูลจริง 3 ครั้ง (เทียบกับโมเดล 3D) คลาดเคลื่อน **38% / 545% / 318%** — สาเหตุคือใช้ **GPS ของกล้องมาคำนวณระยะห่าง** (แทนที่จะรู้ระยะห่างจริง) แล้วพบว่า **ภาพทั้งหมดที่ทดสอบมี `RtkFlag = 16` ซึ่งแปลว่าเป็นแค่ GPS ธรรมดา (Single Point Positioning) ไม่ใช่ RTK เลย** แม้โดรนจะมีความสามารถ RTK ติดมาก็ตาม — GPS ธรรมดาคลาดเคลื่อนได้หลายเมตร พอเอามาคำนวณระยะห่าง ผลจึงเพี้ยนไปมาก **สูตรคำนวณเองพิสูจน์แล้วว่าถูกต้อง (ตรีโกณมิติมาตรฐาน) ปัญหาอยู่ที่ตัวเลขระยะห่างที่ป้อนเข้าสูตรเท่านั้น** — รายละเอียดเต็มในหัวข้อ "สรุปผลการทดลอง" ด้านล่าง

## สิ่งที่ต้องรู้ก่อนเริ่ม (ทำครั้งเดียว ก่อนออกไปบินจริง)

### 1. สเปกกล้องโดรน (หาจากคู่มือ/เว็บผู้ผลิต ครั้งเดียวต่อรุ่นกล้อง)

| ต้องรู้ | ใช้ทำอะไร |
|---|---|
| มุมรับภาพแนวนอน (Horizontal FOV) | คำนวณว่า 1 pixel แทนความกว้างจริงเท่าไหร่ |
| ความละเอียดภาพ (image width × height เป็น pixel) | ตัวหารในสูตร mm/pixel |
| Focal length (ระยะโฟกัส) — ถ้าไม่มี FOV ตรงๆ ใช้แปลงกันได้ | ทางเลือกถ้าไม่มี FOV ระบุตรงๆ |

### 2. แผนการบิน

- **บินขนานกับผิวโครงสร้าง** (ไม่ใช่บินสูงมองลงพื้น) — เพราะถ่ายคาน/เสาที่เป็นผิวแนวตั้ง/แนวราบ ไม่ใช่พื้นราบ
- **รักษาระยะห่างด้านข้างจากผิวให้คงที่ตลอดแนวบิน** (เช่น 3 เมตร) — ระยะนี้คือ "ระยะห่างจากกล้องถึงพื้นผิว" ที่ต้องใช้คำนวณ **ไม่ใช่ความสูงบินเทียบพื้นดิน** (จุดที่เคยสับสนกันมาก่อน — ถ่ายแนวราบ ระยะสำคัญคือระยะด้านข้าง ไม่ใช่ความสูง)
- ถ้าไม่มีเซนเซอร์วัดระยะ (LiDAR/depth) ต้องกำหนดระยะนี้ไว้ล่วงหน้าตอนวางแผนบิน แล้วพยายามบินให้คงที่ตามนั้นจริง

## ตัวแปรที่ต้องดึงจากแต่ละภาพ (ชื่อจริงใน EXIF/XMP วงเล็บความหมาย)

ภาพจากโดรน DJI ฝังข้อมูลไว้ใน EXIF มาตรฐาน + XMP เฉพาะของ DJI — อ่านได้ด้วยไลบรารีอย่าง `exiftool` หรือ `pymupdf`/`PIL` (ที่เคยใช้ในโปรเจกต์นี้แล้ว)

### พิกัดตำแหน่งกล้อง (GPS)

| ชื่อฟิลด์จริง | ความหมาย |
|---|---|
| `GPSLatitude` | ละติจูด (ตำแหน่งแนวเหนือ-ใต้) |
| `GPSLongitude` | ลองจิจูด (ตำแหน่งแนวตะวันออก-ตะวันตก) |
| `GPSAltitude` | ความสูงจาก GPS (ระดับน้ำทะเล — **ไม่ใช่ระยะห่างจากผิวโครงสร้าง**) |
| `drone-dji:RelativeAltitude` | ความสูงเทียบจุดขึ้นบิน (ยังไม่ใช่ระยะห่างจากผิวโครงสร้างเช่นกัน ถ้าถ่ายแนวราบ) |

### มุมกล้อง (Gimbal — สำคัญที่สุด เพราะบอกทิศทางที่กล้อง "มอง" จริงๆ)

| ชื่อฟิลด์จริง | ความหมาย |
|---|---|
| `drone-dji:GimbalYawDegree` | กล้องหันซ้าย-ขวา กี่องศา (ทิศทางแนวราบ) |
| `drone-dji:GimbalPitchDegree` | กล้องเงย/ก้ม กี่องศา (0° = แนวนอนพอดี, -90° = มองตรงลงพื้น) — **ฟิลด์นี้โปรเจกต์เคยใช้แล้วสำหรับทำ confidence flag** |
| `drone-dji:GimbalRollDegree` | กล้องเอียงซ้าย-ขวา (ปกติใกล้ 0 เสมอเพราะกิมบอลกันสั่น) |

**หมายเหตุ:** อย่าใช้ `drone-dji:FlightYawDegree`/`FlightPitchDegree`/`FlightRollDegree` แทน — นั่นคือมุมของตัวโดรน ไม่ใช่มุมกล้อง (กิมบอลปรับแยกอิสระจากตัวโดรนได้)

### สเปกกล้อง (ต่อภาพ เผื่อบางรุ่นซูมได้ ค่าจะเปลี่ยนทุกภาพ)

| ชื่อฟิลด์จริง | ความหมาย |
|---|---|
| `FocalLength` | ระยะโฟกัสจริงของเลนส์ (mm) |
| `FocalLengthIn35mmFilm` | ระยะโฟกัสเทียบเท่ากล้องฟิล์ม 35mm (ใช้คำนวณ FOV ได้ตรงๆ ถ้าไม่รู้ขนาดเซนเซอร์จริง) |
| `ExifImageWidth` / `ExifImageHeight` (หรือ `PixelXDimension`/`PixelYDimension`) | ความละเอียดภาพเป็น pixel |

### ค่าที่ EXIF ไม่มีให้ ต้องกำหนดเอง

| ต้องรู้ | มาจากไหน |
|---|---|
| **ระยะห่างจากกล้องถึงผิวโครงสร้างจริง** | ไม่มีใน EXIF (ยกเว้นมี LiDAR/depth sensor) — ต้องกำหนดจากแผนการบิน (ระยะที่ตั้งใจบินให้คงที่) หรือวัดจริงหน้างาน |

## ⚠️ ข้อจำกัดสำคัญที่พบจริง (2026-09-25): GPS Altitude พังหนักเวลาถ่ายใต้สะพาน

**พบจากการเช็คภาพจริง 2 ใบ:**

| ภาพ | ตำแหน่งถ่าย | GPS Altitude | สมเหตุสมผลไหม |
|---|---|---|---|
| ภาพเหนือสะพาน (เหนือ deck) | ท้องฟ้าโล่ง มองเห็นดาวเทียมเต็มที่ | **+4.5 m** (เหนือระดับ deck) | ✅ สมเหตุสมผล |
| ภาพใต้สะพาน (ใต้ท้องคาน) | ท้องฟ้าโดนบังจากพื้นสะพาน | **-14.5 m** ("Below Sea Level") | ❌ ผิดปกติมาก — ผลต่างกับพิกัดจุดบนโมเดล 3D ถึง ~20 เมตร |

**สาเหตุ:** GPS หาความสูงได้แม่นยำ โดยต้องพึ่งสัญญาณจากดาวเทียมที่อยู่**มุมสูงตรงหัว**เป็นหลัก — พอบินอยู่ใต้พื้นสะพาน โครงสร้างบังสัญญาณดาวเทียมมุมสูงหมด เหลือแค่ดาวเทียมมุมเฉียงต่ำ ทำให้คำนวณความสูงผิดเพี้ยนได้มาก (สิบกว่าเมตร) แม้ตำแหน่งแนวราบ (lat/lon) จะยังพอใช้ได้อยู่

**ผลกระทบต่อโปรเจกต์:** งานตรวจสะพานส่วนใหญ่ต้องถ่าย**ใต้ท้องสะพาน/คาน** (จุดที่ความเสียหายมักอยู่) ซึ่งเป็นจุดที่ GPS Altitude จะแย่เป็นพิเศษเสมอ ไม่ใช่แค่เคสนี้เคสเดียว — **วิธีที่ 3 (GPS+Gimbal) ต้องหลีกเลี่ยงการใช้ GPS Altitude ตรงๆ สำหรับคำนวณระยะห่าง** ควรใช้ระยะแนวราบ (lat/lon เท่านั้น) ร่วมกับมุม Gimbal Pitch แทน หรือหาระยะห่างด้วยวิธีอื่น (วัดหน้างาน/เซนเซอร์ระยะเสริม) สำหรับภาพที่ถ่ายใต้สะพานโดยเฉพาะ

|---|---|---|
| Gimbal Yaw Degree | ✅ เจอ | +151.50 |
| Gimbal Pitch Degree | ✅ เจอ | +3.70 |
| Gimbal Roll Degree | ✅ เจอ (เช็คซ้ำแล้ว 2026-09-25) | +0.00 (ใกล้ 0 ตามคาด เพราะกิมบอลกันสั่น) |
| Focal Length (35mm equivalent) | ✅ เจอ | 24.0 mm (จริง 12.3mm) |
| Exif Image Width/Height | ✅ เจอ | 5280 × 3956 |
| GPS Latitude/Longitude | ยังไม่ได้เช็คในรอบนี้ (ปกติมีเสมอ) | — |

**สรุป: มีข้อมูลครบทุกตัวที่ EXIF ให้ได้ (GPS, Gimbal Yaw/Pitch/Roll, Focal Length, ความละเอียดภาพ) เหลือแค่ "ระยะห่างจากกล้องถึงผิวโครงสร้าง" ที่ต้องกำหนดเอง** ตามที่คาดไว้ตั้งแต่แรก (ค่านี้ไม่มีในภาพถ่ายของกล้องไหนอยู่แล้ว ต้องมาจากแผนบิน/วัดหน้างานเสมอ) — ภาพนี้น่าจะมาจาก DJI Mavic 3 (ความละเอียด 5280×3956 ตรงกับสเปกกล้อง Hasselblad ของรุ่นนี้)

**อัปเดต:** ลองแก้ปัญหา "ไม่รู้ระยะห่าง" ด้วยการคำนวณจาก GPS กล้อง↔GPS จุดบนโมเดล 3D แทน — **ผลออกมาไม่สำเร็จ** ดูหัวข้อ "สรุปผลการทดลอง" ด้านล่างสำหรับรายละเอียดเต็มและสาเหตุที่แท้จริง

## การคำนวณที่ใช้พิสูจน์ (เตรียมไว้ตอบอาจารย์ — ยังไม่มีผลทดลองจริง แต่พิสูจน์ทฤษฎีได้เต็มที่)

### สูตรพื้นฐาน (ตรีโกณมิติ ไม่มีอะไรซับซ้อน)

```
ความกว้างจริงที่กล้องเห็นทั้งภาพ ณ ระยะ D = 2 × D × tan(FOV_h / 2)
mm ต่อ pixel (เฉลี่ยทั้งภาพ) = ความกว้างจริงที่เห็น ÷ จำนวน pixel แนวนอน
```

**ตัวอย่างคำนวณด้วยสเปกกล้องจริง** (จากภาพตัวอย่างที่เช็คแล้วข้างบน — Focal Length 35mm equiv = 24.0mm, ภาพกว้าง 5280px, ระยะห่างยังไม่มีค่าจริง สมมติ 3 เมตรไปก่อน):

```
ขั้น 1: หา FOV จากค่า 35mm equivalent (สูตร: เซนเซอร์ 35mm มาตรฐานกว้าง 36mm)
  FOV_h = 2 × arctan(36 / (2 × 24.0)) = 2 × arctan(0.75) = 73.74°

ขั้น 2: หาความกว้างจริงที่กล้องเห็น ณ ระยะ 3 เมตร (สมมติ ยังไม่มีค่าจริง)
  ความกว้างจริงที่เห็น = 2 × 3000mm × tan(73.74°/2) = 2 × 3000 × 0.75 = 4500.0 mm

ขั้น 3: mm ต่อ pixel = 4500.0 ÷ 5280 = 0.852 mm/pixel

ตรวจสอบ: รอยร้าวกิน 3 pixel ในภาพ → ความกว้างจริง = 3 × 0.852 = 2.56 mm
```

**หมายเหตุ:** ระยะ 3 เมตรในตัวอย่างนี้เป็นค่าสมมติ (ยังไม่มีระยะจริงจากแผนบิน) พอมีระยะจริงแล้ว แทนค่าใหม่ในขั้น 2 ได้ทันที ตัวเลขที่เหลือคำนวณจากสเปกกล้องจริงทั้งหมดแล้ว ไม่ใช่ค่าสมมติอีกต่อไป

### สูตรแม่นยำกว่า (สำหรับ pixel ที่ไม่ได้อยู่กึ่งกลางภาพ — ถ่ายมุมเอียงจะต่างจากค่าเฉลี่ยทั้งภาพ)

สูตรด้านบนใช้ค่าเฉลี่ยทั้งภาพ ซึ่งคลาดเคลื่อนมากขึ้นถ้า pixel อยู่ห่างจากกึ่งกลางภาพ (เพราะมุมที่กว้างขึ้นทำให้ระยะจริงต่อ pixel ไม่เท่ากันทุกจุด) สูตรที่แม่นกว่าคือคำนวณทีละ pixel:

```
มุมเบี่ยงของ pixel จากกึ่งกลางภาพ = arctan( (px_offset / (ความกว้างภาพ/2)) × tan(FOV_h/2) )
ตำแหน่งจริงของ pixel นั้น (เทียบจุดกึ่งกลางที่กล้องมองตรง) = D × tan(มุมเบี่ยงนั้น)
```

ส่วนนี้คือแก่นของฟังก์ชัน `pixel_to_world()` เต็มรูปแบบ (รวมการหมุนตาม yaw/pitch/roll ต่ออีกชั้นเพื่อได้พิกัด 3 มิติจริงบนโครงสร้าง ไม่ใช่แค่ 1 มิติแนวนอน)

### ทำไมเชื่อสูตรนี้ได้ (หลักฐานเชิงทฤษฎี)

หลักการนี้**ไม่ใช่สิ่งที่คิดขึ้นใหม่สำหรับโปรเจกต์นี้** — เป็นตรีโกณมิติพื้นฐานที่ใช้ในกล้อง/งานสำรวจ/remote sensing มานานหลายสิบปี และเป็นสูตรเดียวกับที่ซอฟต์แวร์ photogrammetry เชิงพาณิชย์ (Pix4D/Agisoft) ใช้คำนวณค่า GSD ภายในตัวเองอยู่แล้ว (ตามที่คุยกันไว้ตอนเทียบแบบ 2 กับแบบ 3)

### สรุปผลการทดลอง (2026-09-25) — ทดสอบจริงกับโมเดล 3D แล้ว 3 ครั้ง

**วิธีทดสอบ:** เลือกจุด 2 จุดบนโครงสร้างที่เห็นชัดทั้งในภาพถ่ายและในโมเดล 3D (NP Survey) → วัดระยะจริงจากโมเดล 3D (ground truth) → คำนวณระยะจาก pixel ด้วยสูตร (ใช้ระยะห่างที่คำนวณจาก GPS กล้อง↔GPS จุด แทนการรู้ค่าจริง) → เทียบผล

| ครั้งที่ | Gimbal Pitch | GPS Altitude ของภาพ | ระยะคำนวณได้ | ระยะจริง (โมเดล 3D) | คลาดเคลื่อน % | คลาดเคลื่อนจริง |
|---|---|---|---|---|---|---|
| 1 | +3.70° | **-14.5 m** (below sea level) | 2.04 m | 1.47 m | 38.2% | 0.57 m |
| 2 | +13.40° | **+14.5 m** (above sea level) | 2.50 m | 0.39 m | 545.2% | 2.11 m |
| 3 | +12.60° | **+63.4 m** (above sea level) | 5.12 m | 1.22 m | 318.4% | 3.90 m |

**ผลสรุป: คลาดเคลื่อนสูงเกินใช้งานได้ทุกครั้ง และไม่คงที่ (38-545%) — ไม่ใช่ error แบบ bias คงที่ที่แก้ด้วยตัวคูณได้**

**ข้อสังเกตสำคัญ 2 อย่างจากตารางนี้:**

1. **ทั้ง 3 ภาพถ่ายคานใต้สะพานบริเวณเดียวกัน แต่ GPS Altitude กระโดดไปมาถึง 78 เมตร** (-14.5 ถึง +63.4) — พิสูจน์ว่า GPS ที่จุดนี้ไม่เสถียรเลย ไม่ใช่แค่ "แย่คงที่" แต่ **แย่แบบสุ่มไม่มีรูปแบบ** เปลี่ยนไปทุกครั้งที่ถ่าย เพราะดาวเทียมที่มองเห็นได้เปลี่ยนไปตามตำแหน่ง/มุมกล้องที่ต่างกันแม้เพียงเล็กน้อย GPS คำนวณทั้งแนวราบและแนวดิ่งจากดาวเทียมชุดเดียวกัน — พอแนวดิ่งเพี้ยนมากขนาดนี้ แนวราบก็น่าจะเพี้ยนตามไปด้วย (แค่น้อยกว่า) อธิบายได้ว่าทำไม error แต่ละครั้งไม่คงที่และคาดเดาไม่ได้

2. **ครั้งที่ 2 มีความคลาดเคลื่อนจริง (2.11m) ใกล้เคียงครั้งอื่น แต่ % สูงลิ่ว (545%)** เพราะระยะจริงที่วัดเล็กมาก (0.39m) — ยิ่งวัดจุดที่อยู่ใกล้กันมาก ยิ่งเจอ % คลาดเคลื่อนสูงจากความผิดพลาด GPS ขนาดเท่าเดิม (ข้อจำกัดตามธรรมชาติของการวัดระยะสั้นด้วยเครื่องมือที่มี error สัมบูรณ์คงที่)

### สาเหตุที่แท้จริง (ยืนยันแล้ว): ภาพทั้งหมดไม่ได้ใช้ RTK

เช็ค EXIF พบฟิลด์ `RtkFlag = 16` ในภาพที่ทดสอบทั้งหมด — ค้นเอกสารทางการแล้วพบว่า:

| RtkFlag | ความหมาย | ความแม่นยำ |
|---|---|---|
| 0 | ไม่มีการหาตำแหน่งเลย | คลาดเคลื่อนหลายสิบเมตร |
| **16** | **Single Point Positioning (GPS ธรรมดา)** | **ระดับเมตร — นี่คือค่าที่เจอในทุกภาพที่ทดสอบ** |
| 34 | RTK Float | ระดับเดซิเมตร |
| 50 | RTK Fixed | ระดับเซนติเมตร |

**ตรวจไขว้ 2 แหล่งอิสระแล้ว (2026-09-25) ยืนยันตัวเลขเดียวกันคำต่อคำ:**
- [Sitemark - How to read DJI RTK/NTRIP metadata](https://support.sitemark.com/en/articles/9610492-how-to-read-dji-rtk-ntrip-metadata) (บริษัท third-party ทำซอฟต์แวร์แผนที่โดรน)
- [DJI Enterprise Geospatial Solutions Advanced FAQ](https://enterprise-insights.dji.com/blog/geospatial-solutions-faq) (**จาก DJI เอง โดยตรง** — โดเมน enterprise-insights.dji.com) ระบุตรงๆ ว่า "Column 13: RTK status, 0-no positioning, 16-single point positioning mode, 34-RTK float solution, 50-RTK fixed solution" และ "When the flag of a photo is not 50, it is not recommended to use this photo directly for mapping"

ทั้งสองแหล่งให้ตัวเลขและคำแนะนำตรงกันเป๊ะ — มั่นใจได้ว่าไม่ใช่ข้อมูลที่ผิดหรือแต่งขึ้น

**สรุป: แม้โดรนจะมีความสามารถ RTK ติดมา แต่ตอนถ่ายภาพเหล่านี้ไม่ได้เชื่อมสัญญาณแก้ไข (correction) จากสถานีฐาน จึงตกมาใช้ GPS ธรรมดาแทน — ความแม่นยำระดับเมตรของ GPS ธรรมดา คือสาเหตุโดยตรงของความคลาดเคลื่อน 38-545% ที่เจอ**

### แยกให้ชัด: อะไรพัง อะไรไม่พัง

| ส่วน | สถานะ |
|---|---|
| สูตรตรีโกณมิติ (pixel → ตำแหน่งจริง) | **ถูกต้อง** — พิสูจน์ทางคณิตศาสตร์แล้ว เป็นหลักการเดียวกับ photogrammetry เชิงพาณิชย์ |
| วิธีหาระยะห่างจาก GPS ธรรมดา | **ผิดพลาดสูง ใช้ไม่ได้จริง** — ยืนยันจาก RtkFlag=16 |

**คำตอบ:**
> "หลักการคำนวณเป็นตรีโกณมิติที่พิสูจน์แล้วสมบูรณ์ทางคณิตศาสตร์ ทดสอบกับข้อมูลจริง 3 ครั้งเทียบกับโมเดล 3D พบว่าคลาดเคลื่อน 38-545% วิเคราะห์สาเหตุแล้วพบว่าภาพที่ใช้ทดสอบมี RtkFlag=16 คือใช้ GPS ธรรมดาไม่ใช่ RTK ทั้งที่โดรนมีความสามารถ RTK ติดมา ทางแก้คือต้องเชื่อมสถานีฐาน RTK (D-RTK 2 หรือ NTRIP) ให้ flag ขึ้น 50 ก่อนถ่ายภาพจริง หรือควบคุมระยะห่างจากการวางแผนบินแทนการพึ่ง GPS คำนวณ"

## ลำดับ pipeline เต็ม (สรุปซ้ำจากที่คุยกัน เพื่อให้ไฟล์นี้อ่านจบในตัวเอง)

```
1. บินถ่ายภาพ (overlap กัน) — ระยะห่างจากผิวคงที่ตามที่วางแผนไว้
2. ตรวจจับทีละภาพ (โครงสร้าง + ความเสียหาย) → ได้ตำแหน่ง pixel
3. แปลง pixel → พิกัดจริง 3 มิติ (สูตรข้างบน + หมุนตาม yaw/pitch/roll)
4. Dedup: เทียบพิกัดจริงข้ามภาพ ใกล้กัน = จุดเดียวกัน
5. วัดขนาดจริง: ระยะห่างระหว่างพิกัดจริงของขอบความเสียหาย (ได้มาจากขั้น 3 เลย)
6. เทียบขนาดกับตาราง BMMS → ได้ระดับ 0-5 → ได้ Chi
7. จับคู่ความเสียหายกับชิ้นส่วนโครงสร้างจากพิกัดจริง
8. EHI_e = Σ(Chi × ye_i) × 100
9. T-BHI = Σ(qe·We·EHIe) / Σ(qe·We)  ← ได้คะแนนสุดท้าย
```

รายละเอียดเปรียบเทียบกับวิธีที่ 1, 2 และนิยามประเภทความเสียหาย ดูที่ `drone-image-matching-approaches.md`
