## ปัญหา: ภาพโดรน overlap กัน นับความเสียหายซ้ำข้ามเฟรม

ถ่ายภาพคาน/เสาด้วยโดรนแบบเรียงต่อกันมี overlap — ความเสียหายจุดเดียวกันอาจถูกตรวจจับซ้ำในหลายเฟรม ต้องหาวิธี dedup ข้ามเฟรม (คนละเรื่องกับ dedup ภายในภาพเดียวที่มีอยู่แล้วใน `PROJECT_SUMMARY.md` เรื่อง `_dedupe_structural()`)

**3 วิธีที่พิจารณา:**
1. Feature matching (`cv2.Stitcher_create()`) — **ลองแล้ว ล้มเหลว** พื้นผิวคอนกรีตเรียบเกินไป ไม่มี texture ให้จับจุดเด่น ภาพเพี้ยน/เสาหาย
2. Pix4D — **ลองแล้ว ล้มเหลว** ใช้ template ผิด ("3D Maps" แทนที่จะเป็น "3D Models") ยังไม่ได้ลองใหม่ด้วย template ที่ถูกต้อง + Orthoplane
3. GPS + มุมกิมบอล projection — **ลองแล้ว ล้มเหลว เช่นกัน** (รายละเอียดด้านล่าง)

รายละเอียดเต็ม 3 วิธี + 2 เส้นทางประมวลผล (ตรวจจับก่อนรวม vs ต่อภาพก่อนตรวจจับ) + นิยามประเภทความเสียหายคอนกรีตแบบละเอียด + โค้ดตัวอย่าง: `drone-image-matching-approaches.md`

### สรุปผลวิธีที่ 3 (GPS+Gimbal Projection) — ทดสอบจริงแล้ว ใช้งานไม่ได้กับ GPS ที่มีตอนนี้

**หลักการ:** pixel → มุมเบี่ยงจากกึ่งกลางภาพ (ใช้ FOV กล้อง) → รวมมุมกิมบอลจริง+ระยะห่างกล้อง↔ผิว → ตำแหน่งจริง 3 มิติ → วัดระยะห่างระหว่าง 2 ตำแหน่งได้ขนาดจริง **สูตรตรีโกณมิติพิสูจน์แล้วว่าถูกต้อง** (หลักการเดียวกับ photogrammetry เชิงพาณิชย์)

**เช็ค EXIF จริงแล้ว มีข้อมูลครบทุกตัวที่ต้องใช้** (GPS, Gimbal Yaw/Pitch/Roll, Focal Length, ความละเอียดภาพ — น่าจะเป็น DJI Mavic 3, 5280×3956) เหลือแค่ "ระยะห่างกล้อง↔ผิวโครงสร้าง" ที่ EXIF ให้ไม่ได้ ต้องหาเพิ่มเอง

**ทดสอบจริง 3 ครั้งเทียบกับโมเดล 3D (NP Survey) — คลาดเคลื่อน 38.2% / 545.2% / 318.4% ใช้งานไม่ได้ทุกครั้ง**

**สาเหตุยืนยันแล้ว (เช็ค EXIF + ค้นเอกสาร DJI อย่างเป็นทางการ 2 แหล่ง):** ภาพทั้งหมดที่ทดสอบมี `RtkFlag = 16` = Single Point Positioning (GPS ธรรมดา ระดับเมตร) **ไม่ใช่ RTK เลย** แม้โดรนจะมีความสามารถ RTK ติดมา (ต้อง flag=50 ถึงจะแม่นระดับ cm) — พบเพิ่มว่า GPS Altitude ของภาพทั้ง 3 ที่ทดสอบกระโดดไปมาถึง 78 เมตร (-14.5 ถึง +63.4) ทั้งที่ถ่ายบริเวณเดียวกัน ยืนยันว่า GPS ไม่เสถียรแบบสุ่ม (ดาวเทียมที่มองเห็นได้เปลี่ยนไปตามตำแหน่ง/มุมกล้องที่ต่างกันแม้เพียงเล็กน้อย โดยเฉพาะถ่ายใต้สะพานที่โครงสร้างบังสัญญาณดาวเทียมมุมสูง)

**สรุป: สูตรคำนวณถูกต้อง ปัญหาอยู่ที่ "วิธีหาระยะห่าง" ที่พึ่ง GPS ธรรมดาแทนที่จะรู้ค่าจริง** ทางแก้ที่เสนอ: (1) เชื่อมสถานีฐาน RTK ให้ flag ขึ้น 50 ก่อนบินจริง หรือ (2) ควบคุม/วัดระยะห่างจากแผนการบินแทนการคำนวณจาก GPS — รายละเอียดเต็ม ตารางผลทดสอบ สูตรคำนวณ ตัวแปร EXIF ที่ต้องใช้ และแหล่งอ้างอิง (2 แหล่งอิสระ ยืนยันตรงกัน): `วิธี3-GPS-Gimbal-ละเอียด.md`

## วิธีจัดการ train/valid/test (ตกลงกันแล้ว)

**บริบท:** ผู้ใช้ทยอย label ภาพเพิ่มเรื่อยๆ ตามเวลา (ไม่ได้มีภาพครบทั้งหมดในมือตั้งแต่แรก)

```
ตอนนี้     : label เสร็จเท่าไหร่ → แบ่ง train/valid/test ทีเดียวจากภาพทั้งหมดที่มี
              ตั้งสัดส่วนเองใน Roboflow (60/25/15 หรือ 70/15/15) ห้ามใช้ค่า default
              เพราะรอบแรกใช้ default แล้วได้ 82/11/7 → test เล็กเกินไป (บางคลาสเหลือ 3 ภาพ)
              ↓
ทยอยเพิ่ม  : ภาพที่ label เสร็จทีหลัง → เอาลง train อย่างเดียวเท่านั้น
              Roboflow จะแบ่ง export ใหม่เป็น train/valid/test ของมันเอง — ไม่ต้องสนใจ
              เอาทั้ง 3 โฟลเดอร์ที่ export มาใหม่ ไปรวมใน train เดิมให้หมด
              valid/test เดิม ห้ามแตะเด็ดขาด
              ↓
เติม test  : เมื่อเข้าเงื่อนไขข้างล่าง → เพิ่มภาพเข้า test/valid (ไม่ใช่สลับใหม่หมด)
```

**กฎเหล็ก: ภาพที่เคยอยู่ใน test/valid ห้ามย้ายออกไปไหนตลอดกาล** — "reset" ของโปรเจกต์นี้ = เพิ่มภาพเข้า test ไม่ใช่สุ่มแบ่งใหม่ทั้งก้อน:

```
ก่อน : train 800 / valid 60 / test 60
หลัง : train 900 / valid 90 / test 100   ← test เดิม 60 ภาพยังอยู่ครบทุกภาพ
```

**เหตุผล:** ถ้าสลับใหม่หมด (ก) เทียบ mAP/precision/recall กับรอบก่อนไม่ได้เลย เพราะคนละชุดข้อสอบ (ข) แย่กว่านั้น — ภาพที่เคยอยู่ใน train อาจหลุดไปอยู่ test รอบใหม่ โมเดลเก่าเคยเห็นมาแล้ว คะแนนจะสูงเกินจริงแบบไม่รู้ตัว พอทำแบบ "เพิ่มอย่างเดียว" จะได้ทั้ง 2 อย่าง: วัดบน test เดิมเทียบกับทุกรอบที่ผ่านมาได้ตรงๆ / วัดบน test ใหม่น่าเชื่อถือกว่าเพราะตัวอย่างเยอะขึ้น

**เงื่อนไขที่ต้องเติมภาพเข้า test (Claude ต้องเช็คให้ทุกครั้งที่วิเคราะห์ผลเทรน แล้วบอกผู้ใช้เอง ผู้ใช้ไม่ต้องจำเอง):**
1. คลาสที่บางที่สุดใน test มีต่ำกว่า ~10 ตัวอย่าง — ตัวเลข mAP รายคลาสจะแกว่งจนเชื่อถือไม่ได้ (รอบ 1 เจอจริง: Honeycomb 3, Spalling 4, Rust_Stain 5)
2. คลาสที่เคยบางใน test มีภาพสะสมเพิ่มมาเยอะแล้ว — การเติม train อย่างเดียวไม่มีวันแก้ปัญหา test บางได้ ต้องเติมเข้า test เท่านั้น
3. มีภาพลักษณะใหม่เข้ามาที่ test เดิมไม่ครอบคลุม — สำหรับโปรเจกต์นี้คือตอนเอาภาพโดรนสะพานจริง (`Bridge/`) เข้ามา ซึ่งคนละลักษณะกับภาพ close-up จาก public dataset ที่ใช้อยู่ตอนนี้ จุดนี้ต้องเติมเข้า test แน่นอน
4. ก่อนสรุปผลจริงลงรายงาน/thesis

ทุกครั้งที่เติมภาพเข้า test ต้องเขียนกำกับใน `training_log.md` ว่ารอบนี้ test ขยายจากกี่ภาพเป็นกี่ภาพ และถ้าจะเทียบกับรอบก่อนแบบตรงๆ ให้ดูคะแนนบน test ชุดเดิมเท่านั้น

**ข้อจำกัดที่ต้องรู้และเขียนลงรายงาน:** test ปัจจุบันเป็นภาพ close-up จาก public dataset ต่างประเทศทั้งหมด **ยังไม่มีภาพสะพานจริงของโปรเจกต์เลย** — mAP ที่วัดได้ตอนนี้บอกได้แค่ว่าโมเดลเก่งกับภาพแบบ public dataset ยังไม่ได้พิสูจน์ว่าใช้งานจริงกับภาพโดรนได้ดีแค่ไหน ต้องเอาภาพสะพานจริงเข้า test ให้ได้ก่อนสรุปผลลงรายงาน (ถ้าภาพจริงมีน้อย ให้ความสำคัญ test > train > valid)
