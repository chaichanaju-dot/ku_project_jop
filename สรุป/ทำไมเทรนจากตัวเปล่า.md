# ทำไมเทรนจาก `rtdetr-l.pt` (ตัวเปล่า) ทุกรอบ แทนการเทรนต่อจาก `best.pt`

> เอกสารนี้รวมเหตุผลทั้งหมดไว้ที่เดียว สำหรับใช้เขียนรายงาน / ตอบคำถามอาจารย์
> ข้อสรุปสั้นที่สุด: **ตัวเปล่าไม่ได้ให้คะแนนสูงกว่า แต่ทำให้ "เปรียบเทียบ" ได้ ซึ่งเป็นหัวใจของงานวิจัย**

---

## แก่นของเรื่อง: การทดลองต้องเปลี่ยนทีละตัวแปร

งานวิจัยที่สรุปผลได้ ต้องคุมทุกอย่างให้คงที่ แล้วเปลี่ยนสิ่งที่อยากศึกษาทีละอย่าง

การเทรนจากตัวเปล่าทุกรอบ ทำให้ "จุดตั้งต้นของโมเดล" เป็นค่าคงที่เสมอ — เหลือตัวแปรเดียวคือสิ่งที่เราตั้งใจเปลี่ยน

ส่วนการเทรนต่อจาก `best.pt` ทำให้จุดตั้งต้นเปลี่ยนไปทุกรอบ (ขึ้นกับทุกอย่างที่เคยเทรนมาก่อนหน้า) จึงไม่มีค่าคงที่ให้ยึด

---

## 1. เปรียบเทียบด้าน "ข้อมูล"

**คำถามที่อยากตอบ:** เพิ่มภาพแล้วดีขึ้นแค่ไหน คุ้มกับแรงที่ลง label ไหม

| | เทรนจากตัวเปล่า | เทรนต่อจาก `best.pt` |
|---|---|---|
| ตัวแปรที่เปลี่ยน | ข้อมูลอย่างเดียว | ข้อมูล **+ จำนวน epoch สะสม + การรีเซ็ต learning rate** |
| สรุปได้ว่า | "เพิ่ม 300 ภาพ → mAP +0.14" | ได้แค่ "รอบ 2 แม่นกว่ารอบ 1" แต่บอกสาเหตุไม่ได้ |
| พล็อตกราฟ จำนวนภาพ vs mAP | ได้ | ไม่ได้ (แกนนอนไม่ใช่ตัวแปรเดียวที่เปลี่ยน) |
| ย้อนเติมจุดที่ขาด (เช่น อยากรู้ผลที่ 550 ภาพ) | เทรนใหม่ด้วย 550 ภาพได้เลย | ต้องไล่เทรนใหม่ทั้งสายตั้งแต่ต้น |

**ผลที่ได้จากการเทียบนี้:** รู้ว่าถึงจุดที่เพิ่มข้อมูลแล้วไม่ช่วยแล้วหรือยัง (diminishing returns) → ประหยัดเวลาไม่ต้อง label เพิ่มโดยเปล่าประโยชน์ และรู้ว่าถึงเวลาเปลี่ยนไปปรับอย่างอื่นแทน

---

## 2. เปรียบเทียบด้าน "โมเดล"

**คำถามที่อยากตอบ:** สถาปัตยกรรมไหนเหมาะกับงานตรวจความเสียหายสะพานที่ข้อมูลระดับนี้

**เทรนต่อจาก `best.pt` ทำไม่ได้เลย** — `best.pt` ของ RT-DETR เอาไปต่อยอดกับ YOLO ไม่ได้ (โครงสร้างภายในคนละแบบ) แต่ละสถาปัตยกรรมต้องมีสายการเทรนของตัวเอง ซึ่งไม่มีทางเทียบกันได้อย่างยุติธรรม

**เทรนจากตัวเปล่าทำได้ทันที** — เปลี่ยนบรรทัดเดียวในสคริปต์:

```python
PRETRAINED = "rtdetr-l.pt"    # การทดลองที่ 1
PRETRAINED = "yolo11l.pt"     # การทดลองที่ 2 — เปลี่ยนแค่บรรทัดนี้
```

ข้อมูลเดียวกัน, config เดียวกัน, test ชุดเดียวกัน → ต่างกันแค่สถาปัตยกรรม

**ข้อสังเกตที่น่าสนใจสำหรับงานนี้:** RT-DETR เป็นสถาปัตยกรรมแบบ transformer ซึ่งโดยทั่วไปต้องการข้อมูลมากกว่า CNN มากกว่าจะแสดงศักยภาพเต็มที่ (งานที่ใช้ได้ผลดีมักมีข้อมูลหลักหมื่นภาพขึ้นไป) ขณะที่โปรเจกต์นี้มีหลักร้อย — จึงมีความเป็นไปได้ที่ YOLO จะให้ผลดีกว่าที่ขนาดข้อมูลระดับนี้ **ซึ่งเป็นสมมติฐานที่ทดสอบได้จริงและเป็นผลการทดลองที่มีค่าสำหรับรายงาน**

---

## 3. เปรียบเทียบด้าน "ตัวแปร/พารามิเตอร์"

**คำถามที่อยากตอบ:** ปรับ `IMGSZ` จาก 640 เป็น 960 ช่วยเรื่องรอยร้าวจริงไหม / augmentation แบบไหนเหมาะกว่า

**เทรนจากตัวเปล่า:** ทั้งสองการทดลองเริ่มจากน้ำหนักตั้งต้นเดียวกันเป๊ะ ต่างกันแค่ค่าที่ตั้ง → เทียบได้ตรงๆ

**เทรนต่อจาก `best.pt`:** โมเดลที่ fine-tune มาที่ 640 แล้วเอามาเทรนต่อที่ 960 ไม่ใช่การทดสอบ IMGSZ ที่สะอาด เพราะน้ำหนักตั้งต้นของสองฝั่งไม่เหมือนกันตั้งแต่แรก — และถ้าเปลี่ยนจำนวนคลาส (เพิ่มชนิดความเสียหายใหม่) จะต่อยอดไม่ได้เลยเพราะขนาดหัวโมเดลไม่ตรงกัน ต้องเทรนใหม่อยู่ดี

---

## 4. เหตุผลอื่นที่ไม่เกี่ยวกับการเปรียบเทียบโดยตรง

**ทำซ้ำได้ (เหตุผลทางวิชาการที่หนักที่สุด)**
เทรนจากตัวเปล่า → ระบุ methodology ในรายงานได้ครบใน 3 บรรทัด (dataset + config + โมเดลตั้งต้น) ใครก็รันซ้ำได้ผลเดิม
เทรนต่อจาก checkpoint → ต้องระบุประวัติการเทรนทุกรอบย้อนหลังตามลำดับ พร้อมสถานะ dataset ณ ตอนนั้นของแต่ละรอบ ซึ่งเขียนเป็น methodology ไม่ได้จริง

**ขยายชุดทดสอบได้**
เทรนจากตัวเปล่า → ย้ายภาพจาก train เข้า test ได้ (โมเดลรอบใหม่ไม่เคยเห็นภาพนั้น) ทำให้แก้ปัญหา test เล็กเกินไปได้
เทรนต่อจาก checkpoint → ทุกภาพที่เคยเข้า train ปนเปื้อนถาวร ขยาย test จากภาพที่มีอยู่ไม่ได้เลย **ติดอยู่กับ test ชุดแรกตลอดชีวิตโปรเจกต์** (ของเรารอบแรกได้ test แค่ 7% บางคลาสเหลือ 3 ภาพ ถ้าไปทางนั้นจะแก้ไม่ได้)

**ไม่สะสมความผิดพลาดเก่า**
label ที่เคยกำกวมระหว่าง Spalling กับ Efflorescence ฝังเป็น decision boundary ในน้ำหนักไปแล้ว การแก้ label แล้ว fine-tune ต่อไม่ได้ลบของเดิมทิ้ง แค่ดันไปอีกทาง ร่องรอยยังเหลือ

**ไม่ต้องจดบัญชี ไม่เสี่ยง data leakage**
เทรนต่อจาก checkpoint ต้องจดตลอดว่าภาพไหนเคยเข้า train รอบไหน พลาดครั้งเดียว = ภาพที่โมเดลเคยเห็นหลุดเข้า test → คะแนนสูงเกินจริงโดยไม่มีสัญญาณเตือน
เทรนจากตัวเปล่า → สถานะโฟลเดอร์ปัจจุบันคือความจริงทั้งหมด ตรวจสอบด้วยตาได้ทันที

**`best.pt` ไม่ใช่จุดตั้งต้นการเทรนตั้งแต่แรก**
`best.pt` คือ checkpoint ที่ทำคะแนน valid ได้ดีที่สุด — มีไว้เพื่อ**เอาไปใช้ตรวจจับ** (โหลดเข้า `main.py`) ไม่ใช่เพื่อเทรนต่อ การเทรนต่อที่ถูกต้องจริงๆ คือ `resume=True` ด้วย `last.pt` ซึ่งใช้เฉพาะตอนเทรนค้างกลางทาง (ไฟดับ/เน็ตหลุด)

**การโหลด `best.pt` มาเทรนใหม่ ไม่ใช่การต่อยอดจริง**
Ultralytics จะเริ่ม learning rate schedule ใหม่ทั้งหมด (มี warmup แล้วดัน LR ขึ้นสูงอีกครั้ง) ซึ่งไปกระแทกน้ำหนักที่ convergence แล้วให้กระจาย — จึงได้ทั้งสองอย่างแบบครึ่งๆ ไม่ใช่การต่อยอดจริง และไม่ใช่การเริ่มใหม่ที่สะอาด

---

## 5. ข้อเสียของการเทรนจากตัวเปล่า (พูดให้ครบทั้งสองด้าน)

**เสียเวลาเทรนใหม่ทุกรอบ** — ประมาณ 1-2 ชั่วโมงต่อรอบที่ขนาดข้อมูลหลักร้อยถึงพันภาพ

เป็นข้อเสียเดียวที่มี และไม่ใช่ปัญหาที่สเกลนี้ — จะเริ่มเป็นปัญหาก็ต่อเมื่อข้อมูลใหญ่ระดับแสนภาพจนเทรนเป็นวัน

**คะแนนไม่ได้สูงกว่าเสมอไป** — ผลของสองวิธีมักใกล้เคียงกัน เพราะทั้งคู่เห็นข้อมูลชุดเดียวกัน (เรารวมภาพเก่า+ใหม่เทรนอยู่แล้ว ไม่ได้เทรนแต่ภาพใหม่) ข้อดีของตัวเปล่าคือเรื่องการอธิบายและความยืดหยุ่น ไม่ใช่ความแม่นยำดิบ

---

## 6. เมื่อไหร่ที่การเทรนต่อจาก checkpoint ถึงเป็นทางเลือกที่ถูก

(ตอบข้อนี้ได้ด้วยจะทำให้เหตุผลน่าเชื่อถือขึ้น เพราะแสดงว่าเข้าใจทั้งสองฝั่ง ไม่ได้ยึดติดด้านเดียว)

- ข้อมูลใหญ่มากจนเทรนใหม่ไม่ไหว (ระดับแสน-ล้านภาพ เทรนเป็นวันหรือสัปดาห์)
- เข้าถึงข้อมูลเดิมไม่ได้แล้ว (ถูกลบตามข้อกำหนดความเป็นส่วนตัว หรือเป็นข้อมูลที่ยืมมาชั่วคราว)
- เทรนค้างกลางทางเพราะไฟดับ/เครื่องหลุด → ใช้ `resume=True` กับ `last.pt` ซึ่งเป็นการต่อยอดจริง
- งานวิจัยสาย continual learning ที่ศึกษาการเรียนรู้ต่อเนื่องเป็นหัวข้อหลักโดยตรง

**ไม่มีข้อใดตรงกับเงื่อนไขของโปรเจกต์นี้** — ข้อมูลหลักร้อยถึงพันภาพ เทรนใหม่ชั่วโมงเดียว และข้อมูลทั้งหมดยังเก็บไว้ครบ
