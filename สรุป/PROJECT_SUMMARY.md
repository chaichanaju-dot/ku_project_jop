"คู่มือเริ่มต้นโปรเจกต์ประเมินสะพานจากภาพโดรน" (section 4.4-4.8)

## สถาปัตยกรรมที่ตัดสินใจแล้ว (2026-09-17) — ยังไม่ implement

แนวคิด "2 โมเดลแยกกัน ทำงานอิสระต่อกัน (parallel) บนภาพเดียวกัน" ยังใช้อยู่
("ใครถนัดอะไรให้ทำเต็มที่อย่างนั้น ไม่แบ่งครึ่งๆ กลางๆ") แต่**เปลี่ยนตัวโมเดลใหม่ทั้งคู่**
จากแผน OBB+OBB เดิม (ดูหัวข้อ "สถาปัตยกรรมเดิม" ด้านล่าง — ถูกแทนที่แล้ว):

1. **YOLO (segmentation)** → ตรวจจับ**ชิ้นส่วนโครงสร้าง** (pier/beam/pier cap ฯลฯ)
   ให้ mask ระดับ pixel ตรงจาก segmentation head โดยตรง (ไม่ต้อง rasterize จาก OBB
   เหมือนแผนเดิม)
2. **RT-DETR (transformer) + SAM (hybrid)** → ตรวจจับ**ความเสียหาย + พื้นที่ความเสียหาย**
   — **สร้าง/เทรนเอง** ไม่ใช้โมเดลรุ่นพี่แล้ว RT-DETR หากรอบ+จำแนกประเภทความเสียหาย
   ก่อน (จุดแข็งจริงของมัน) แล้วส่งกรอบนั้นเข้า **SAM** เพื่อ refine เป็น pixel mask
   จริงอีกที (แก้ปัญหาความเสียหายรูปทรงเฉียง/ไม่สม่ำเสมอที่กรอบ box เดียวครอบไม่พอ
   — ดูเหตุผลในหัวข้อ "คำถามเปิด" ที่ถูกแก้แล้วด้านล่าง)

**วิธีเชื่อมข้อมูล:** สองโมเดลไม่คุยกัน ต่างคนต่างตรวจจับบนภาพเดียวกันอิสระต่อกัน
ข้อมูล "รวมกัน" เพราะมาจากภาพเดียวกัน ไม่ใช่โมเดลหนึ่งป้อนอีกโมเดล — ผลจากโครงสร้าง
(mask) จับคู่กับผลความเสียหาย (จาก RT-DETR) ด้วยพื้นที่ทับซ้อน (รายละเอียดวิธี
match/IoU ต้องออกแบบใหม่ตอนเขียนโค้ดจริง เพราะ output ของ RT-DETR คนละแบบกับ OBB
เดิม — ดูคำถามเปิดด้านล่าง)

### คำถามเปิด — RT-DETR ให้พื้นที่ pixel จริงได้ไหม (แก้แล้ว 2026-09-17)

**RT-DETR แบบมาตรฐาน (ทั้งต้นฉบับ Baidu และ Ultralytics RT-DETR) เป็น object
detector แบบกล่อง (bounding box) ล้วนๆ ไม่มี segmentation head ในตัว** — ไม่ให้
pixel mask หรือพื้นที่ pixel จริงเหมือนที่ YOLO-seg ให้ และปัญหาไม่ใช่แค่ "กล่องตรง
vs กล่องเฉียง (OBB)" — ความเสียหายจริงมักมีรูปทรงไม่สม่ำเสมอ/คดโค้ง กล่องแบบไหนก็
ครอบพื้นที่เกินจริงอยู่ดี ต้องใช้ mask ถึงจะแก้ปัญหาได้จริง

**ตัดสินใจแล้ว: (c) RT-DETR + SAM (hybrid)** — RT-DETR หากรอบ+จำแนกประเภทความเสียหาย
ก่อน (จุดแข็งจริงของมัน) แล้วส่งกรอบนั้นเข้า SAM เพื่อ refine เป็น pixel mask จริง
อีกที ได้พื้นที่แม่นยำโดยไม่ต้องแคร์เรื่องมุม/รูปทรง และยังคงใช้ transformer
(RT-DETR) ตามที่ตั้งใจไว้แต่แรก — ข้อแลกเปลี่ยนที่รับไว้แล้ว: เพิ่มโมเดล inference
อีกตัว (SAM) ในระบบ ทำให้ pipeline ช้าลง/ซับซ้อนขึ้นกว่าใช้ RT-DETR เปล่าๆ

ทางเลือกอื่นที่พิจารณาแล้วไม่เลือก: (a) ยอมรับพื้นที่กล่องเป็นค่าประมาณ (คลาดเคลื่อน
เยอะเกินไป), (b) ต่อ mask head เข้า RT-DETR เอง (ไม่ใช่ของมาตรฐาน เสี่ยงสูง),
(d) เปลี่ยนไป YOLO-seg ล้วน (เสีย transformer ตามที่ตั้งใจไว้)

## บั๊กที่เจอและแก้ไปแล้ว

1. `_best_matching_mask` เดิมใช้ raw overlap count (ไม่ใช่ IoU) → mask ขยะขนาดใหญ่
   จากโมเดลเราเอง (ครั้งหนึ่งเจอ mask "crack" ที่มีพื้นที่เท่ากับทั้ง pier พอดี - ชัดว่า
   เป็น false positive) ไปชนะการจับคู่กับความเสียหายจริงแทบทุกจุดเพราะ mask ใหญ่
   ทับกับทุกอย่างในบริเวณนั้น แก้แล้วโดยเปลี่ยนเป็น IoU (ดู `MIN_MATCH_IOU = 0.3`
   ใน vision.py)

2. **นับชิ้นส่วนโครงสร้างซ้ำ (double-counting)** - ที่ conf ต่ำมาก (0.01) YOLO's NMS
   ไม่ได้ suppress detection ซ้อนกันของวัตถุชิ้นเดียวกันเสมอไป (เจอ "pier bridge"
   2 กล่องที่ confidence เกือบเท่ากันเป๊ะ 0.014887 vs 0.014886 ตำแหน่งซ้อนทับกัน
   เกือบสนิท) ผลคือชิ้นส่วนจริงชิ้นเดียวถูกนับเป็น 2 element (คนละ EHI เล็กน้อยเพราะ
   ขอบ mask ต่างกันนิดหน่อย) แล้วทั้งคู่ไปรวมใน `sum(q*W*EHI)` ทำให้ชิ้นนั้นมีน้ำหนัก
   เป็น 2 เท่าใน T-BHI โดยไม่ตั้งใจ - แก้แล้วด้วย `_dedupe_structural()` (vision.py,
   ค่าคงที่ `DEDUPE_IOU = 0.7`) รวม mask ของ detection ที่ class เดียวกันและ IoU
   สูงเข้าด้วยกันก่อนสร้างรายงาน (เช็คจากภาพ image_0001431: เดิมรายงาน 4 element
   (pier×2, pier_cap×2) หลังแก้เหลือ 2 element (pier×1, pier_cap×1) ตรงกับที่เห็น
   ในภาพจริง, T-BHI เปลี่ยนจาก 89.48 → 88.59)

  โอกาสแก้พร้อมกับตอน re-label เป็น OBB ไปเลย

## จุดที่รีวิวแล้วอาจต้องแก้ (จากแผนเดิม OBB+OBB — ต้องทบทวนใหม่กับสถาปัตยกรรมใหม่)

1. **`crack` ใน damage_rules.py ใช้เกณฑ์ "ทับ 1 pixel ก็นับ"** ต่างจาก
   spalling/exposed_rebar ที่ใช้ % พื้นที่ทับ (≥30%) — เสี่ยงมากขึ้นตอนนี้เพราะ
   fallback OBB มักให้กรอบกว้างเกินจริง อาจทำให้ crack โดนตัดสินว่า "ทับสนิม"
   ทั้งที่ไม่ได้ทับจริง ควรใส่ threshold % ให้ crack เหมือนตัวอื่น
2. **`honeycomb` และ `rust_efflorescence` ให้คะแนนคงที่** (4 กับ 3 ตามลำดับ)
   ไม่สนขนาดพื้นที่เสียหายเลย ต่างจาก crack/spalling ที่ granular กว่า - ควรเช็ค
   กับคู่มือต้นฉบับว่าตั้งใจแบบนี้จริงไหม
3. **เกณฑ์ "ดีมาก" ต้องการ T-BHI == 100.00 เป๊ะ** (bridge_health.py) ในทาง
   ปฏิบัติแทบเป็นไปไม่ได้จาก floating point - ควรเผื่อ tolerance เล็กน้อย
4. **`MIN_MATCH_IOU = 0.3`** (vision.py, ที่เพิ่งเพิ่มตอนแก้บั๊ก) ยังไม่ผ่านการ
   ทดสอบ/ปรับจูนจริง เลือกมาแค่ให้ตรงกับค่าคงที่อื่นในไฟล์เดิม

## ทำต่อได้ที่ (อัปเดต 2026-09-17 ตามสถาปัตยกรรมใหม่)

1. **อ่านมาตรฐาน/เกณฑ์ขนาดความเสียหายที่จะให้มาก่อน** แล้วค่อยออกแบบ
   `damage_rules.py` จริง (threshold พื้นที่ทับซ้อน, ระดับความเสียหาย 0-5) —
   บล็อกทุกอย่างด้านล่างอยู่ ยังไม่ควรเริ่มเขียนโค้ดจนกว่าจะอ่านเสร็จ
2. **ทดสอบ pipeline RT-DETR + SAM** ว่า latency รวมรับได้ไหม (2 โมเดล inference
   ต่อภาพสำหรับความเสียหายอย่างเดียว ยังไม่รวม YOLO-seg โครงสร้าง) และตัดสินใจ
   ว่าจะใช้ SAM ตัวเต็มหรือรุ่นเบา (เช่น MobileSAM/FastSAM) เพื่อความเร็ว
3. เตรียม dataset สำหรับเทรนใหม่: YOLO-seg (โครงสร้าง, ต้องเป็น segmentation
   mask format) และ RT-DETR (ความเสียหาย, แค่ label เป็น box+class พอ เพราะ mask
   จริงมาจาก SAM ตอน inference ไม่ต้อง label mask เอง) — dataset ของรุ่นพี่เป็น
   OBB format ใช้ต่อกับโมเดลใหม่ไม่ได้ตรงๆ ต้องแปลง/รวบรวมใหม่
4. เขียน `main.py` ตามสเปกที่ตกลงแล้ว (รับ path โฟลเดอร์หรือภาพเดี่ยว, เซฟ
   overlay ลงโฟลเดอร์แยกตามรอบที่รัน)
5. ทดสอบ pipeline กับภาพจริงจาก `Bridge/` หลายภาพ ก่อนสรุปผลกับอาจารย์ว่าใช้งานได้จริง
