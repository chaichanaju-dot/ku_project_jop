บทสรุปสำหรับผู้อ่านที่มีเวลา 5 นาที

ห้าคำตอบหลัก

1. "ลง software แยกลงโดรน DJI ได้ไหม" — ได้ แต่ไม่ใช่ในความหมายที่มักเข้าใจ DJI เปิดให้เขียนโปรแกรมได้ 2 ที่เท่านั้น คือ (ก) แอป Android ที่คุยกับรีโมต ผ่าน Mobile SDK V5 และ (ข) คอมพิวเตอร์ที่แขวนไว้กับตัวโดรนในฐานะ payload ผ่าน Payload SDK V3
ตัว flight controller เป็นกล่องดำปิดสนิท — แก้ firmware เอง เขียนโค้ดรันบน flight controller เอง หรือปิด geofence ทำไม่ได้เลย
2. "บินใกล้วัตถุมากขึ้นเพื่อให้เห็นชัดขึ้น" — เป็นทางที่ผิด ที่ความละเอียดเป้าหมายเท่ากัน (0.2 mm/pixel) เลนส์ wide ต้องบินห่างเพียง 1.12 m ซึ่งอยู่ในเขต braking distance ต่ำสุดที่ DJI ยอมให้ตั้งได้ (1.0 m) พอดี แปลว่าต้องปิดระบบกันชน
เลนส์ tele 168 mm ให้ความละเอียดเท่ากันที่ระยะ 7.95 m — ห่างกว่า 7 เท่า ปลอดภัยกว่ามาก และ laser rangefinder ก็แม่นขึ้นด้วย (ที่ 2 m คลาดเคลื่อนถึง 15% แต่ที่ 8 m เหลือ 2.7%)
3. "อยากรู้ว่าโดรนห่างวัตถุเท่าไหร่" — เซนเซอร์ของ DJI ไม่มีตัวไหนแม่นพอที่ระยะใกล้ laser rangefinder ทุกรุ่นของ DJI มีพจน์คงที่ ±0.2 m ในสูตรความแม่น ซึ่งไม่ลดลงตามระยะ → ที่ระยะ 3 m คลาดเคลื่อน ±6.8%, ที่ 2 m คลาดเคลื่อนถึง 15%
ยิ่งไปกว่านั้น H20/H30/M30 มี minimum range 3 m ตายตัว วัดใกล้กว่านั้นไม่ได้เลย ส่วน obstacle sensing แม้จะคืนค่าเป็นมิลลิเมตรผ่าน API แต่ DJI ไม่เคยประกาศความแม่นยำเลยแม้แต่รุ่นเดียว — มันเป็นเซนเซอร์กันชน ไม่ใช่เครื่องมือวัด
4. ทางออกที่ทั้งถูกที่สุดและแม่นที่สุด — ไม่ต้องวัดระยะเลย ติด fiducial marker (ArUco) ที่รู้ขนาดจริงลงบนผิวเสา แล้วให้มาตราส่วนมาจากภาพเอง ไม่ต้องรู้ระยะ ไม่ต้องรู้ทางยาวโฟกัส ไม่ต้อง calibrate กล้อง ต้นทุนเกือบเป็นศูนย์
และได้ของแถมที่เซนเซอร์วัดระยะให้ไม่ได้: marker มี 4 มุมจึงแก้ความเอียงของกล้องได้ด้วย ซึ่งเป็นแหล่งความคลาดเคลื่อนที่ใหญ่กว่าเรื่องระยะเสียอีก (เอียง 30° ทำให้ผิด 7.2%)
โค้ดที่ทดสอบแล้วอยู่ในภาคผนวก ก. — วัดได้คลาดเคลื่อน 0.26% บนภาพทดสอบ
5. สิ่งที่ DJI ทำไม่ได้จริง ๆ และต้องยอมรับ — การบินใต้ท้องสะพาน ใต้ deck คือสภาพแวดล้อม GNSS-denied โดยนิยาม RTK ใช้ไม่ได้ vision positioning ก็ล้มเหลวกับผนังคอนกรีตเรียบไร้ texture งานวิจัยรายงานว่า RTK fix ล้มเหลวเมื่ออยู่ห่างสิ่งกีดขวาง 0–5 m และต้องใช้เวลา re-fix 9–13 วินาที
ถ้าขอบเขตงานคือเสาตอม่อที่มองเห็นฟ้า → DJI พอ ถ้าต้องเข้าใต้ท้องสะพาน → ต้องเป็น Skydio หรือ Elios ซึ่งมีข้อจำกัดด้านการจัดหาในไทย

สิ่งที่เปลี่ยนไปจากความเข้าใจตั้งต้น

ความเข้าใจตั้งต้นสิ่งที่พบจริง
บินใกล้ = เห็นชัดขึ้นจริงในแง่ทัศนศาสตร์ แต่ผลรวมแย่ลง เพราะต้องปิดระบบกันชน เซนเซอร์วัดระยะแม่นน้อยลง และ downwash รบกวนที่ระยะใกล้ผนัง — ใช้เลนส์ tele แทนได้ผลเดียวกันโดยไม่มีข้อเสียเหล่านี้
รู้ระยะแล้วจะแปลง pixel → mm ได้ไม่พอ เพราะยังไม่รู้ว่ากล้องเอียงกี่องศาเทียบผิว ซึ่งทำให้มาตราส่วนแปรทั่วทั้งภาพ งานวิจัยที่ได้ความแม่นระดับมิลลิเมตรจึงใช้เลเซอร์ 4 จุด เพื่อแก้สมการระนาบ ไม่ใช่จุดเดียว
ต้องเขียนโปรแกรมควบคุมการบินเองเขียนได้ (waypoint KMZ, virtual stick) แต่ไม่ใช่คอขวดของโปรเจกต์ คอขวดจริงคือการให้มาตราส่วนที่เชื่อถือได้กับทุกภาพ ซึ่งแก้ได้ที่ขั้นตอนประมวลผล ไม่ใช่ที่การบิน
เอาภาพมารวมกัน (stitching) เป็นเป้าหมายเป็นเครื่องมือ ไม่ใช่เป้าหมาย — ถ้าวัตถุประสงค์คือให้ AI เห็นรอยแตกชัด ภาพเดี่ยวความละเอียดสูงพร้อมมาตราส่วนที่ถูกต้องก็เพียงพอ และแม่นกว่าการวัดบน orthomosaic ที่ผ่านการ resample มาแล้ว

ข้อเสนอแนะเชิงปฏิบัติ

  1. อย่าเพิ่งซื้ออะไร — ตรวจก่อนว่าโดรนที่ทีมวิจัย/ภาควิชามีอยู่แล้วมีเลนส์เทเลหรือไม่ ถ้ามี ก็เริ่มได้ทันที
  2. ทดสอบ EXIF ก่อนอย่างอื่น — ถ้ามี M4E/M4T/M30T ให้ถ่ายภาพหนึ่งใบแล้วรัน exiftool -a -G1 IMG.JPG ดูว่ามี field ระยะจาก laser rangefinder ติดมากับภาพหรือไม่ ถ้ามี จะประหยัดงานไปมาก (ยังไม่มีเอกสารยืนยัน — ต้องทดลองเอง)
  3. เริ่มจากผนังทดสอบในมหาวิทยาลัย ไม่ใช่สะพานจริง — พิสูจน์ให้ได้ก่อนว่าวัดรอยแตกที่รู้ความกว้างจริงได้แม่นกี่เปอร์เซ็นต์ ก่อนจะไปเจอปัญหา GPS/แสง/ลมที่หน้างานพร้อมกันทีเดียว
  4. เตรียม ground truth ตั้งแต่วันแรก — ซื้อ crack width comparator card และ feeler gauge ราคาไม่กี่ร้อยบาท ถ้าไม่มีค่าจริงมาเทียบ ตัวเลขทุกตัวที่รายงานก็พิสูจน์ไม่ได้

DJI SDK — เขียนโปรแกรมอะไรได้ อะไรไม่ได้

ภาพรวม: เขียนได้ 2 ที่เท่านั้น

คำถามตั้งต้นคือ "ลง software แยกลงโดรน DJI ได้ไหม เช่น software บังคับการบิน การวัดระยะ" คำตอบขึ้นกับว่า "ลง software ลงโดรน" หมายถึงอะไร

สิ่งที่อยากทำทำได้ไหมทำอย่างไร / ทำไมไม่ได้
แอปควบคุมการบินของตัวเอง (แทน DJI Pilot 2)ได้เขียนแอป Android ด้วย Mobile SDK V5 — แอปรันบนแท็บเล็ต/มือถือที่ต่อกับรีโมต ไม่ได้รันบนตัวโดรน
ต่ออุปกรณ์ของตัวเอง (เซนเซอร์ กล้อง คอมพิวเตอร์) เข้ากับโดรนได้เขียนโปรแกรมฝั่ง payload ด้วย Payload SDK V3 ผ่านพอร์ต E-Port / SkyPort — โปรแกรมรันบนคอมพิวเตอร์ที่คุณแขวนไว้กับโดรน
บินอัตโนมัติตามเส้นทางที่กำหนดเองได้สร้างไฟล์ KMZ/WPML เองแล้วส่งเข้า flight controller ผ่าน MSDK (IWPMZManager + IWaypointMissionManager)
ส่งคำสั่งบังคับแบบเรียลไทม์จากโค้ดได้Virtual Stick — ส่งคำสั่งที่ความถี่ 5–25 Hz แต่มีข้อจำกัดมาก (ดู 2.2)
อ่านค่าระยะจากเซนเซอร์กันชนได้IPerceptionManager.addObstacleDataListener() คืนระยะเป็นมิลลิเมตร (แต่ไม่มีสเปกความแม่นยำ — ดูบทที่ 3)

RTK

ทุกรุ่น DJI Enterprise ให้ตัวเลขเดียวกันเมื่อได้สถานะ RTK FIX: แนวราบ 1 cm + 1 ppm, แนวดิ่ง 1.5 cm + 1 ppm (1 ppm = 1 mm ต่อระยะห่างจากสถานีฐาน 1 กม.)

RTK ใช้กับโจทย์นี้ไม่ได้ ด้วยเหตุผลเชิงโครงสร้าง 3 ข้อ 1. RTK บอกตำแหน่งของโดรน ไม่ได้บอกระยะถึงผิววัตถุ — จะได้ระยะต้องรู้ตำแหน่งของผิวคอนกรีตในระบบพิกัดเดียวกันด้วย ซึ่งต้องมี as-built survey หรือ BIM ที่แม่นกว่านั้น
2. ใต้ท้องสะพานคือสภาพแวดล้อม GNSS-denied โดยนิยาม — ท้องคานบังท้องฟ้าไปเกือบหมด
3. Multipath — เสาคอนกรีตและโครงเหล็กสะท้อนสัญญาณ ทำให้ระยะที่วัดได้ยาวเกินจริงโดยที่ตัวรับไม่รู้ตัว

งานวิจัยรายงานว่า RTK fix ล้มเหลวบ่อยเมื่ออยู่ห่างสิ่งกีดขวางในระยะ 0–5 m และใช้เวลา re-fix ประมาณ 9–13 วินาทีหลังพ้นสิ่งกีดขวาง ควรยืนยันตัวเลขในเปเปอร์ต้นฉบับก่อนอ้างในเล่ม

คณิตศาสตร์ของการวางแผนบิน — GSD และระยะที่ต้องใช้จริง

ก่อนจะถามว่า "โดรนรุ่นไหนดี" ต้องตอบก่อนว่า ต้องการรายละเอียดกี่มิลลิเมตรต่อพิกเซล เพราะตัวเลขนี้ตัวเดียวกำหนดทั้งระยะที่ต้องบิน เลนส์ที่ต้องใช้ จำนวนภาพต่อเสา และความเร็วชัตเตอร์ที่ยอมได้

สูตรหลัก

GSD = D × 34.62 / (fequiv × Wpx) GSD หน่วย mm/pixel · D = ระยะกล้องถึงผิว (mm) · fequiv = ทางยาวโฟกัสเทียบ 35 มม. · Wpx = ความกว้างภาพเป็นพิกเซล
ที่มาของค่าคงที่ 34.62 — และกับดักที่ทำให้ผิด 4% สูตรมาตรฐานคือ GSD = D × pixel_pitch / f_actual ซึ่งต้องรู้ขนาดเซนเซอร์จริง — ตัวเลขที่ DJI ไม่ประกาศ (บอกแค่ "1/1.3 นิ้ว" ซึ่งไม่ใช่ขนาดจริง และค่าที่หาได้ตามเว็บก็ขัดกันเอง 9.6×7.2 กับ 9.8×7.3 mm)

ทางออกคือใช้นิยามของ equivalent focal length ซึ่งอิงเส้นทแยงมุมของฟิล์ม 35 มม. (43.27 mm) ไม่ใช่ความกว้าง → diag_sensor / f_actual = 43.27 / f_equiv
กล้อง DJI ทุกตัวในตารางนี้เป็นอัตราส่วน 4:3 (8064×6048, 8192×6144, 5280×3956) ซึ่งความกว้าง = 0.8 × เส้นทแยง จึงได้ 43.27 × 0.8 = 34.62

ถ้าใช้ 36 (ความกว้างฟิล์ม 35 มม.) จะได้ค่าที่ผิดไป 4% เพราะนั่นถูกต้องเฉพาะเซนเซอร์อัตราส่วน 3:2 เท่านั้น — เป็นข้อผิดพลาดที่เกิดง่ายมากและไม่มีอะไรเตือน

สูตรนี้เท่ากันทุกประการกับรูปที่เขียนด้วยเส้นทแยงมุมโดยตรง GSD = D × 43.267 / (fequiv × Wdiag,px) เพราะ Wdiag = 1.25 × W สำหรับเซนเซอร์ 4:3 — ใช้รูปไหนก็ได้ ผลเท่ากัน
หลักฐานว่า FOV ที่ DJI ประกาศเป็นเส้นทแยงมุมจริง ตรวจสอบกับสเปกของ DJI เอง (M4 wide, fequiv = 24 mm):

ถ้าตีความเป็น แนวนอน: 2·atan(18/24) = 73.7° → ห่างจากที่ประกาศ 10° ✗ ไม่ตรง

สามกับดักที่เจอจริงตอนทดสอบโค้ด

โค้ดในภาคผนวก ก. ถูกเขียนและรันจริง ระหว่างนั้นเจอบั๊กสามตัวที่ทุกตัวทำให้ผลลัพธ์ "ดูเหมือนถูก" แต่ผิด — บันทึกไว้เพราะเป็นกับดักที่คนทำงานนี้ต่อจะเจอซ้ำแน่นอน

กับดักที่ 1 — distance transform ให้ความกว้างเกินจริง 1 pixel เสมอ

วิธีมาตรฐานในการวัดความกว้างรอยแตกจาก binary mask คือใช้ cv2.distanceTransform แล้วคูณสอง แต่ distance transform คืน "ระยะถึงพิกเซลพื้นหลังที่ใกล้ที่สุด" ไม่ใช่ "ระยะถึงขอบ" — แถบกว้าง W พิกเซลจึงได้ค่าสูงสุด (W+1)/2 ทำให้ 2 × maxdist เกินจริงไป 1 pixel เสมอ สูตรที่ถูกคือ

widthpx = 2 × maxdist − 1

ตรวจสอบแล้วกับความหนา 3–8 พิกเซล ได้ค่าตรงเป๊ะทุกกรณี ที่ GSD 0.2 mm/px ความผิดพลาด 1 pixel นี้ = 0.2 mm ซึ่งใหญ่กว่ารอยแตกที่มาตรฐานถือว่ายอมรับได้ในหลายกรณี — ลืมลบ 1 คือรายงานผิดทั้งชุดข้อมูล

กับดักที่ 2 — warpPerspective เติมขอบด้วยสีดำ แล้วขอบดำถูกนับเป็นรอยแตก

ค่า default ของ borderValue คือ 0 (ดำ) พอ threshold หารอยแตก (ซึ่งดำ) ขอบภาพทั้งแถบก็เข้าเกณฑ์ไปด้วย ได้ "รอยแตก" กว้าง 140 mm ในการทดสอบ ต้องตั้ง borderValue เป็นสีพื้นผิวเสมอ

กับดักที่ 3 — ArUco ตรวจไม่เจอถ้า marker ชิดขอบภาพ

ArUco ต้องการ quiet zone (ขอบขาวรอบตัว marker) จึงจะ detect ได้ ถ้า rectify แล้ววาง marker ชิดมุมภาพพอดี จะ detect ไม่เจออีกเลย ผลคือโค้ดที่ตัด marker ออกจาก mask ทำงานพลาด แล้ว marker ทั้งก้อน (401×401 px) กลายเป็น "รอยแตก" ก้อนใหญ่ ข้อนี้ใช้กับการพิมพ์ด้วย: ต้องเว้นขอบขาวรอบ marker อย่างน้อย 1 ช่อง (= 1/6 ของด้าน) ห้ามตัดชิดขอบดำ

การรวมภาพและ photogrammetry สำหรับผิวแนวดิ่ง

คำถามที่ต้องตอบก่อนลงมือ: จำเป็นต้องรวมภาพจริงหรือ โจทย์ตั้งต้นบอกว่า "เอาภาพมารวมกัน" แต่ต้องแยกให้ชัดว่ารวมไปเพื่ออะไร

ถ้าเพื่อให้ AI เห็นรอยแตกชัดขึ้น → ไม่จำเป็นเลย โมเดล segmentation ทำงานบน tile ขนาด 256×256 หรือ 512×512 pixel อยู่แล้ว การรวมภาพไม่ได้เพิ่มข้อมูลใหม่ มีแต่ทำให้เสียรายละเอียดจากการ resample

สิ่งที่การรวมภาพมีไว้เพื่อ: (1) ระบุตำแหน่งว่ารอยแตกอยู่ตรงไหนของโครงสร้าง (2) ไม่นับรอยแตกเดียวกันซ้ำจากหลายภาพ (3) คิดปริมาณความเสียหายเป็นพื้นที่/สัดส่วนเพื่อเข้าเกณฑ์ T-BHI

กฎที่ควรยึด: วัดความกว้างรอยแตกบนภาพเดี่ยว วัดความยาว/พื้นที่/ตำแหน่งบน orthomosaic — เพราะ ortho ผ่าน resampling มาแล้ว ความคลาดเคลื่อนของความกว้างสูงมาก

ทำไม lawnmower จากด้านบนใช้กับงานนี้ไม่ได้

งานทำแผนที่แนวราบ (nadir grid) กล้องมองลงตั้งฉากกับพื้น ระยะกล้อง–วัตถุคงที่เกือบทั้งภาพ ผลคือ GSD คงที่ baseline ตั้งฉากกับแนวมอง และฉากมี texture ธรรมชาติเยอะ งานผิวแนวดิ่งเปลี่ยนทั้งสามข้อพร้อมกัน:

  • ระยะไม่คงที่ ถ้าผิวไม่เรียบสนิท (เสาโค้ง ตอม่อมีบัว คานมี haunch) → GSD ต่างกันภายในภาพเดียว → ค่าที่วัดได้ผิดถ้าไม่แก้ perspective
  • มุมตกกระทบเฉียง ถ้าเก็บด้วย nadir จะกลายเป็น grazing angle → ความคลาดเคลื่อนของ depth ระเบิด
  • ฉากไม่มี texture คอนกรีตทาสีหรือผิวแบบเรียบเป็นสีเทาทั้งแผ่น → feature detector หา keypoint ไม่ได้

ถ้าอยากบินใกล้กว่าระยะเบรก — อย่าปิดระบบ ให้ย่นระยะเบรกแทน

คำแนะนำที่พบทั่วไปคือ "ปิด obstacle avoidance" ซึ่งเป็นคำตอบที่หยาบเกินไป วิธีที่ถูกต้องคือ:

// ★ วิธีที่ควรใช้ — ยังมีระบบเบรกเป็นตาข่ายกันตาย แค่ขยับเส้นเข้ามาใกล้ผนัง
setObstacleAvoidanceBrakingDistance(distance, PerceptionDirection.HORIZONTAL, callback);
setObstacleAvoidanceWarningDistance(distance, PerceptionDirection.HORIZONTAL, callback);

// ปิดเฉพาะทิศที่หันเข้าผนัง ไม่ใช่ปิดหมด
setObstacleAvoidanceEnabled(false, PerceptionDirection.HORIZONTAL, callback);

// ทางเลือกสุดท้ายเท่านั้น เมื่อระยะเป้าหมาย < ระยะตรวจจับต่ำสุด (0.4 m)
setObstacleAvoidanceType(ObstacleAvoidanceType.CLOSE, callback);
// BRAKE  = ลอยค้างเมื่อเจอสิ่งกีดขวาง (ค่าเริ่มต้น)
// BYPASS = หลบเอง
// CLOSE  = ไม่เบรกไม่หลบ
สามข้อที่ต้องรู้ 1. ระยะตรวจจับต่ำสุดของ M4 series คือ 0.4 m (หน้า/หลัง), 0.5 m (ข้าง), 0.3 m (ล่าง) — ถ้าตั้งใจบินใกล้กว่านี้ เซนเซอร์บอดอยู่แล้ว ปิดหรือไม่ปิดก็ไม่ต่างกัน ความเสี่ยงเกิดตั้งแต่ตัดสินใจเข้าโซนบอดแล้ว
2. ห้ามใช้โหมด Sport (S) ใกล้โครงสร้างเด็ดขาด — โหมดนี้ปิด obstacle avoidance อัตโนมัติ และเพิ่มความเร็ว/ความไวไปพร้อมกัน เป็นส่วนผสมที่แย่ที่สุด
3. ทิศ บน เป็นทิศที่เซนเซอร์อ่อนที่สุดของโดรนทุกยี่ห้อ ซึ่งเป็นทิศที่ต้องใช้เมื่อบินใต้ท้องสะพานพอดี — ข้อมูลช่วงระยะทิศบนของ M4 series ยังไม่ยืนยัน ต้องเปิดคู่มือผู้ใช้ของรุ่นที่จะใช้จริง

ภาพรวม pipeline

ข้อควรระวังในการออกแบบ 3 ข้อ

1. Layer 0 ต้องเป็น primitive metrics ตามที่เอกสาร T-BHI ของโปรเจกต์เขียนไว้เอง ให้ AI วัดค่าดิบ (mm, m², %) โดยไม่ผูกกับมาตรฐาน แล้วค่อย map เป็นระดับ BMMS 0–5 ในชั้นถัดไป
ข้อดี: ถ้ากรมทางหลวงแก้เกณฑ์ ไม่ต้องเทรนโมเดลใหม่ และตรวจย้อนกลับได้ว่าทำไม AI ให้ระดับนั้น (audit trail)
ข้อเสียของการทำนายเลข T-BHI ตรง ๆ: ไม่มีทางอธิบายได้ว่ามาจากไหน ซึ่งจะถูกถามแน่นอนในการสอบ
2. Multi-Path Distress — ต้องคืนค่าเป็นสัดส่วน ไม่ใช่ระดับเดียว ถ้าใน element เดียวพบความเสียหายหลายชนิดที่ระดับต่างกัน ให้ใช้ระดับที่แย่ที่สุด และบันทึกสัดส่วนของแต่ละระดับด้วย เพราะสูตร EHI ต้องการ distribution ไม่ใช่ค่าเดียว
→ pipeline ต้องคืน "พื้นที่กี่ % อยู่ระดับ 5/4/3/2/1/0" ไม่ใช่ "ระดับ = 3"
3. แยกโหมดวัดกับโหมดสร้างโมเดลออกจากกัน ดูรายละเอียดในบทที่ 6 — จำนวนภาพต่างกัน ~5 เท่า การทำรอบเดียวให้ได้ทั้งสองอย่างจะได้ผลแย่ทั้งคู่

    """คืน 4 มุมของ marker ตัวแรกที่เจอ (เรียง TL,TR,BR,BL) หรือ None ถ้าไม่เจอ"""
    corners, ids, _ = _detector.detectMarkers(img)
    return None if ids is None else corners[0][0]


def scale_mm_per_px(img):
    """มาตราส่วนเฉลี่ยจากด้านทั้ง 4 ของ marker
    ใช้ได้เมื่อกล้องเกือบตั้งฉากกับผิว (เอียงไม่เกิน ~15 องศา)"""
    c = find_marker(img)
    if c is None:
        return None
    side = np.mean([np.linalg.norm(c[i] - c[(i + 1) % 4]) for i in range(4)])
    return MARKER_MM / side


def rectify(img, px_per_mm=2.0, margin_mm=20.0):
    """แก้ภาพเอียงให้กลับเป็นระนาบตรง (fronto-parallel)
    คืน (ภาพที่แก้แล้ว, mm/px ซึ่งคงที่เท่ากันทั้งภาพ)

    margin_mm: เว้นขอบขาวรอบ marker ในภาพผลลัพธ์ — ห้ามตั้งเป็น 0
    ArUco ต้องมี quiet zone รอบตัว ถ้า warp ให้ marker ชิดขอบภาพพอดี
    จะ detect ไม่เจออีกเลย และโค้ดที่ตัด marker ออกจาก mask จะพลาดทั้งก้อน
    """
    c = find_marker(img)
    if c is None:
        return None, None
    s = MARKER_MM * px_per_mm
    m = margin_mm * px_per_mm
    dst = np.float32([[m, m], [m + s, m], [m + s, m + s], [m, m + s]])
    H = cv2.getPerspectiveTransform(c.astype(np.float32), dst)
    h, w = img.shape[:2]
    # borderValue = สีพื้นกระดาษ ไม่ใช่ดำ — ไม่งั้นขอบดำจะถูกนับเป็น "รอยแตก" ตอน threshold
    out = cv2.warpPerspective(img, H, (w, h), borderValue=(235, 235, 235))
    return out, 1.0 / px_per_mm


def crack_width_px(mask):
    """ความกว้างรอยแตกเป็น pixel จาก binary mask

    distance transform คืน 'ระยะถึงพิกเซลพื้นหลังที่ใกล้ที่สุด' ไม่ใช่ 'ระยะถึงขอบ'
    แถบกว้าง W พิกเซลจะได้ค่าสูงสุด (W+1)/2  =>  W = 2*maxdist - 1
    ถ้าลืมลบ 1 จะได้ความกว้างเกินจริง 1 px เสมอ (ที่ GSD 0.2 mm/px = เกิน 0.2 mm)
    """
    dist = cv2.distanceTransform((mask > 0).astype(np.uint8), cv2.DIST_L2, 5)
    return 2.0 * float(dist.max()) - 1.0


def crack_width_mm(mask, mm_per_px):
    return crack_width_px(mask) * mm_per_px

    f'<svg xmlns="http://www.w3.org/2000/svg" width="{total}mm" height="{total + 8}mm" '
    f'viewBox="0 0 {total} {total + 8}">'

pipeline (12 ข้อ)

  • Effective resolution จริงของโหมด 48 MP บนเซนเซอร์ quad-Bayer ของ DJI ยังไม่ยืนยัน — ต้องวัดเองด้วย Siemens star / USAF 1951 target ใน Phase 0 ตัวเลข GSD ทั้งหมดในรายงานนี้เป็น nominal ถ้า effective ต่ำกว่า nominal 1.4x ต้องคูณระยะบิน D ด้วย 1/1.4
  • Actual focal length ของ DJI Mini 4 Pro (6.72 mm) และ Mavic 4 Pro ทุกเลนส์ ยังไม่ยืนยัน — DJI ไม่ประกาศในหน้า specs (ตรวจสอบแล้ว) ตัวเลข 6.72 mm มาจากฟอรัม/รีวิว จึงใช้ฟอร์ม FOV แทนในรายงานนี้ ถ้าต้องการยืนยันให้อ่านจาก EXIF ของภาพจริง (FocalLength tag)
  • ขนาดเซนเซอร์เป็น mm ของฟอร์แมต 1/1.3" และ 1/1.5" ยังไม่ยืนยัน — แหล่งอ้างอิงให้ค่าขัดกัน (9.6x7.2 vs 9.8x7.3 mm) ต้องดู datasheet ของเซนเซอร์รุ่นจริง (น่าจะเป็น Sony IMX ตระกูลหนึ่ง) หรือคำนวณย้อนจาก EXIF FocalLengthIn35mmFilm
  • DJI Matrice 4E/4T ไม่ประกาศ FOV ของกล้อง wide ในหน้า specs ที่ดึงมา — ต้องเปิดหน้า specs เต็มหรือคู่มือผู้ใช้เพื่อคำนวณ GSD ของรุ่นนี้
  • กฎ 'รอยแตกเล็กสุด = 3 x GSD' ยังไม่ยืนยันแหล่งปฐมภูมิ — พบใน secondary source ต้องหา primary reference (น่าจะเป็นงาน photogrammetry detectability หรือ Nyquist-based argument) ก่อนอ้างในวิทยานิพนธ์
  • ตาราง 4.9 ของ T-BHI (ค่าน้ำหนัก W_e ของแต่ละ element และการแบ่ง Primary/Secondary) ยังไม่ได้ดึงมาครบในรอบนี้ — ต้องเปิดหน้า 51-53 ของ PDF เพื่อได้ตารางเต็มก่อนเขียนโค้ดคำนวณ T-BHI
